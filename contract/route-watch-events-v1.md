# 판정보드 신호 스트림 v1

판정보드 화면과 서버가 함께 지키는 SSE 계약이다. 서버는 이 연결로 "판정보드가 기준으로 삼는 관측이 달라졌다"는 신호만 보낸다. 보드 데이터는 지금처럼 `GET /api/v1/routes/{routeId}/watch`([`route-watch-v1.openapi.json`](route-watch-v1.openapi.json))로 받고, 폴링도 그대로 둔다. 이 연결이 없거나 끊겨도 화면은 폴링으로 똑같이 동작한다.

OpenAPI는 이벤트 스트림 안의 모양을 적지 못하므로 이 문서가 원본이다. 주소, 상태 코드, 응답 형식은 서버가 만드는 Swagger 명세에도 나온다. 서버 시험(`WatchStreamContractTest`)이 실제 스트림과 서버가 만든 명세가 이 문서의 내용과 같은지 확인한다. 모양을 바꾸면 이 문서와 그 시험을 같은 PR에서 고친다.

## 켜짐

- `WATCH_STREAM_ENABLED=true`일 때만 켜진다. 기본값은 꺼짐이다.
- 꺼져 있으면 이 주소는 다른 없는 경로와 같은 404 `ENDPOINT_NOT_FOUND`이고 Swagger 명세에도 나오지 않는다. EventSource는 상태 코드를 읽지 못하므로, 화면은 서버가 꺼져 있는지를 응답으로 알 수 없다.

## 요청과 응답

| 요청 | 응답 | 뜻 |
| --- | --- | --- |
| `GET /api/v1/routes/{routeId}/watch/events` | 200, `Content-Type: text/event-stream`, `Cache-Control: no-store, no-transform` | 연결됐다. 서버가 닫을 때까지 열려 있다 |
| | 204, 본문 없음 | 연결 수가 상한에 닿았거나 서버가 내려가는 중이다. EventSource는 204를 받으면 스스로 다시 연결하지 않는다 |
| | 400 `INVALID_ROUTE_ID` | 노선 ID가 9자리 숫자가 아니다. 본문은 `/watch`의 400과 같다 |
| | 404 `ENDPOINT_NOT_FOUND` | 꺼져 있다 |
| `HEAD` 같은 주소 | 200과 헤더만 | 스트림을 열지 않는다. 화면은 보내지 않는다 |

- 403은 쓰지 않는다. CloudFront가 403을 `index.html` 200으로 바꾸기 때문이다.
- 서버는 노선이 실제로 있는지 확인하지 않고 연결을 받는다. 없는 노선이면 `ping`만 온다.
- 쿠키와 로그인 상태를 보지 않는다.

## 이벤트

스트림에 흐르는 글자다.

```
retry:4200
: connected

event:observation
data:{"observedAt":"2026-11-23T18:00:21.412935+09:00"}

event:ping
data:1

event:observation
data:{"observedAt":"2026-11-23T18:00:42.530118+09:00"}

```

| 줄 | 언제 | 내용 |
| --- | --- | --- |
| `retry:<밀리초>` | 연결 직후 한 번 | 3000에서 10000 사이이고 연결마다 다르다. 연결이 끊긴 뒤 EventSource가 다시 연결하기까지 기다리는 시간이다 |
| `: connected` | 연결 직후 한 번 | 주석이다. EventSource는 주석을 화면 코드에 넘기지 않는다 |
| `event:observation` | 아래 절 | `data`는 JSON 객체 하나이고 필드는 `observedAt` 하나다 |
| `event:ping` | 15초마다 | `data:1`. 연결이 살아 있음을 알린다 |

- `observedAt`은 그 노선의 `/watch` 본문에 있는 `observedAt`과 글자까지 같은 값이다. 오프셋이 붙은 ISO 8601 시각이다. 화면은 문자열이 아니라 시각으로 비교한다.
- `id:`는 쓰지 않는다. 서버는 놓친 신호를 다시 보내지 않는다.
- `retry:`, `event:`, `data:` 뒤에 공백이 없다. EventSource는 공백이 있는 줄과 같게 읽는다.

## observation이 오는 때

- 연결 직후에 하나 온다. 그 노선을 보는 다른 연결이 이미 있어서 서버가 현재 관측을 알고 있으면 `: connected`와 같은 쓰기로 온다. 그 노선의 첫 연결이면 서버가 다음 확인에서 DB를 읽은 뒤에 온다. 기본값으로 보통 1초 남짓이다.
- 서버가 확인하는 도중에 연결하면 연결 직후에 이전 관측을 받고, 2초 안에 그 확인이 찾은 새 관측을 하나 더 받을 수 있다.
- 그 뒤로는 `/watch`가 돌려줄 `observedAt`이 달라질 때마다 연결마다 하나씩 온다.
- 한 연결에 같은 `observedAt`이 연달아 두 번 오지 않는다. 서버는 `observedAt`을 시각으로 비교한다.

## 서버가 지키는 것

- 서버는 판정보드를 읽어 캐시에 넣은 뒤에 신호를 보낸다. 신호를 받고 조회한 `/watch`는 그 관측이나 더 새 관측을 돌려준다. 고르는 관측이 과거로 돌아가는 경우는 아래 절에 있다.
- 신호의 관측은 `/watch`와 같은 코드가 고른다.
- 읽지 못한 노선에는 신호를 보내지 않는다.

## 서버가 지키지 않는 것

- 신호는 `observedAt`이 달라질 때만 간다. 같은 관측에서 보드만 달라지는 드문 경우(그 노선의 첫 예보 실행, 활성 모델 교체)에는 가지 않는다. 그 변화는 폴링이 받는다.
- 달라졌다는 것은 새롭다는 뜻이 아니다. 서버가 고르는 관측이 과거로 돌아가면(노선 판본 교체, 그 노선의 첫 예보 실행) 더 옛 `observedAt`이 온다. 화면은 자기 값보다 새로울 때만 조회한다.
- 신호 뒤에 화면들이 한꺼번에 조회해도 판정보드를 다시 만들지 않는 것이 보통이지만 보장은 아니다. 캐시는 노선마다 마지막에 쓴 판정보드를 남기므로, 신호 직전에 시작한 `/watch`가 옛 판정보드를 나중에 쓰면 한 번 더 만든다.
- `/watch`가 503인 노선(관측이 오래됨, 모델 범위 밖)이나 없는 노선에 연결한 화면은, 그 노선에 이미 알린 관측이 없으면 `observation`을 받지 못한다. 01시에서 04시에는 수집 간격이 관측의 만료 시간과 같아서, 노선마다 약 10분에 한 번 잠깐 그렇다.
- 서버가 DB를 읽지 못하는 동안(장애, 테이블 잠금)에는 신호가 늦는다. 서버는 보는 노선을 한 번에 읽으므로, 한 노선의 예보 데이터 오류로 읽기가 통째로 실패해도 모든 노선의 신호가 늦는다. 그사이에 지나간 관측은 건너뛰고 가장 새 관측 하나만 알린다.
- 연결 직후의 `observation`은 서버가 그 노선의 연결들에 마지막으로 알린 관측이다. 그 관측이 그사이에 오래되어 `/watch`가 503일 수 있다.
- 판정보드 캐시(`BOARD_READ_CACHE_ENABLED`)를 끄면 "판정보드를 다시 만들지 않는다"는 기대가 사라지고, 확인은 DB 부하만 더한다.

## 값

| 값 | 기본 | 서버 설정 |
| --- | --- | --- |
| `ping` 간격 | 15초 | `watch.stream.heartbeat-interval` |
| 연결 수명 | 30분. 지나면 서버가 스트림을 정상 종료하고 EventSource가 `retry` 뒤에 다시 연결한다 | `watch.stream.timeout` |
| 연결 수 상한 | 서버 하나에 200 | `watch.stream.max-connections` |
| `retry` | 3000에서 10000밀리초 | 없음 |
| 서버가 새 관측을 확인하는 간격 | 앞 확인이 끝난 뒤 1초 | `watch.stream.detect-interval` |
| 확인의 조회 문장 하나에 주는 시간 | 1초. 잠금 대기를 포함한다. 1ms보다 짧으면 서버가 뜨지 않는다 | `watch.stream.read-timeout` |

## 화면 규칙

- 프론트 스위치가 켜진 빌드에서만 연결한다. 운영 서버 플래그를 켜기 전까지는 운영 빌드 스위치를 꺼 둔다. `EventSource`는 404를 다른 실패와 구분하지 못하므로, 스위치 없이 연결하면 서버 플래그가 꺼진 동안 모든 화면이 아래 재시도 규칙에 따라 404를 받으며 5분마다 계속 새로 연다.
- 화면이 가려지면 연결을 닫고, 다시 보이면 새로 연다. 가려진 화면의 연결은 저절로 끊기지 않으므로, 닫지 않으면 아무도 보지 않는 연결이 연결 수명(30분)이 끝날 때까지 연결 수 상한의 자리 하나를 차지한다. 기기가 잠들어 연결이 끊긴 경우에도 서버가 알아챌 때까지(두 번째 `ping` 쓰기, 로컬에서 24초) 자리를 차지한다. 다시 보일 때 폴링이 `/watch`를 바로 조회하는 동작은 그대로 둔다.
- 신호의 `observedAt`이 화면이 가진 `observedAt`보다 새롭고 폴링이 멈춘 상태가 아니면 `/watch`를 `no-cache`로 조회한다. 같거나 더 오래됐으면 조회하지 않는다.
- 더 오래된 신호는 두 경우에 온다. 하나는 다시 연결한 직후에 화면이 폴링으로 받은 관측을 서버가 아직 읽지 못했을 때이고, 다른 하나는 서버가 고르는 관측이 과거로 돌아가는 드문 경우(노선 판본 교체 등)다. 앞의 경우는 조회해도 더 새 판정보드를 받지 못한다. 뒤의 경우는 다음 폴링이 그 판정보드를 가져오므로, 그때까지 화면이 서버와 다른 판정보드를 잠깐 보여 줄 수 있다.
- 다시 연결됐다는 이유만으로 `/watch`를 조회하지 않는다. 연결 직후의 `observation`이 그 일을 대신한다.
- `ping` 간격의 두 배에 10초를 더한 시간(지금 40초) 동안 아무 이벤트도 오지 않으면 연결을 닫고 새로 연다. 마지막 이벤트 뒤 `ping`을 두 번 연달아 받지 못하면 닫는다는 뜻이고, 10초는 `ping`이 조금 늦게 도착할 때를 기다려 주는 여유다. 서버가 `ping` 간격을 바꾸면 이 값도 함께 바꾼다.
- `EventSource`가 닫히고 스스로 다시 연결하지 않으면 15초에서 30초 뒤에 새로 연다. 실패가 이어지면 간격을 두 배씩 늘리되 최대 5분까지만 늘리고, 그 뒤로는 5분마다 다시 연다.

### 화면이 보는 것과 할 일

`EventSource`는 응답 상태 코드를 읽지 못하므로 204와 404를 구분하지 못한다. 화면이 알 수 있는 것은 아래 세 경우뿐이다.

| 화면이 보는 것 | 이런 때 | 화면이 할 일 |
| --- | --- | --- |
| `error` 뒤 `readyState`가 `CONNECTING` | 연결이 끊기거나 서버가 스트림을 끝냄(연결 수명 30분, 서버 종료) | 기다린다. `EventSource`가 `retry` 뒤에 스스로 다시 연결한다 |
| `error` 뒤 `readyState`가 `CLOSED` | 204(연결 수 상한, 서버 종료 중), 404(서버 플래그 꺼짐), 그 밖에 200이 아니거나 `text/event-stream`이 아닌 응답 | 위 재시도 규칙대로 새로 연다 |
| 40초 동안 아무 이벤트도 없음 | 중간 장비가 연결을 조용히 끊음 | 연결을 닫고 새로 연다 |
