# 백엔드 DDD 전면 재설계 문서 (SAL-134)

최초 조사는 `dev` 6f70826 (2026-09-21, PR #67 포함)을 기준으로 진행했다. 1단계는 코드 변경 없이 현황을 조사하고 개선안을 제안하는 범위였다. 당시 D안은 팀에서 선택한 뒤 동작 변경 없는 PR로 나누어 적용하는 계획이었다. 2026-09-22에는 전면 재설계로 검토 범위를 넓혔으며 새 설계안에서 구조 변경·정확성 보강·데이터 전환을 구분해 정리했다.

재설계 전 조사 기준은 2026-09-23에 PR #70(SAL-133)까지 머지된 `9f9c75d`다. 편도 품질 조사, 예보 제공 상태, 용도별 자료 사용 조건, 기존 동시성 보강과 온라인 seed 제외를 반영했다. 기준 소스 330개의 이동·삭제 검토는 과거 기록으로 보존하고, 현재 구현의 모듈 집계와 주요 연결은 클래스 배치표 마지막 절에 별도로 정리했다. 아래 초기 검토 문서도 당시 기록으로 남긴다.

완료된 S3→RDS 이관 전용 기능은 제거했다. 별도 `forecast-math` 없이 온라인 계산을 forecasting 내부에 배치하고, 품질 정비용 `maintenance-app`과 호출 한도용 `api-call-quota`를 포함한 9개 목표 모듈로 구성한다. 기존 330개 파일은 유지·이동·삭제 대상을 모두 포함해 추적한다.

## 문서

2026-09-22 작성한 **[DDD 전면 재설계안](ddd/00-design.md)**은 기초 설명부터 프로젝트 설계까지 이어서 다룬다. 0절에서 DDD와 도메인 모델의 뜻, 예측 모델과의 차이, 객체의 상태·행동·책임을 설명한다. 이후 하나의 수집 배치가 수집·예보·평가되는 같은 사례로 경계 컨텍스트, 엔티티·값 객체, 애그리거트, 서비스·리포지토리, CQRS·이벤트를 풀어 쓴다. 각 개념을 선택한 이유를 설명한 뒤 모듈 구성과 실제 처리 흐름으로 연결한다.

실제 코드 근거와 유지할 동작은 [보존 계약](ddd/01-evidence.md), 스키마 변경·배포·롤백 순서와 검증 조건은 [전환 계획](ddd/02-migration-plan.md)에 정리했다. [전체 클래스 배치표](ddd/03-class-map.md)에서는 기존 production Java 파일별 목표 모듈을 확인할 수 있다. 설계 설명은 현재 소스의 이름과 저장 구조에 맞췄으며 실제 검증·운영 반영 상태는 [진행 기록](ddd/implementation-progress.md)에서 구분한다. [용어집](ddd/glossary.md)은 내부 모델 이름과 기존 HTTP·DB 식별자의 관계를 정리한다.

전면 재설계안은 업무 모델·코드·저장 구조를 함께 검토해 목표 구조를 정한 뒤 이관 방법을 설계한다. 전체 변경은 하나의 PR에서 검토할 수 있도록 작업 단위별 커밋으로 나눈다. 운영 반영은 쓰기를 중지한 정비 시간의 오프라인 일괄 전환으로 수행한다. 구·신 앱의 이중 쓰기·혼합 운영·앱별 독립 롤백은 채택하지 않았다. 실제 예보 입력 스냅샷 저장과 프론트엔드 수정은 이번 범위에서 제외한다.

## 최초 조사에서 수치를 낸 방법

- `backend/*/src/main/java` 의 `.java` 317개, `src/test`·`src/testFixtures` 146개를 스크립트로 읽었다. 빌드 산출물은 쓰지 않았다.
- 패키지·클래스 의존은 `import com.gustler…` 문과 같은 패키지 안의 단순 이름 참조를 합쳐 만들었다. 문자열·주석 안의 이름은 뺐다. 리플렉션·설정 파일로 이어지는 의존은 잡히지 않는다.
- 순환은 강한 연결 요소(Tarjan)로 찾았다. 패키지 순환과 클래스 순환을 따로 냈다.
- 컨벤션 수치는 정규식 집계다. 경계 사례가 몇 건 섞일 수 있어 경향을 보는 용도이고, 예시는 파일을 직접 읽고 골랐다.
- 스택·라이브러리 버전 정보는 학습 노트 13장 §1 전수표(로컬)에서 인용했고 다시 조사하지 않았다.

## 용어

- 포트: 도메인 쪽이 정의한 인터페이스. `processor.SeatForecastRepository`, `api.board.application.BoardQueryRepository` 같은 것.
- 어댑터: 포트 구현. `Jdbc*`, `Jpa*`, `Aws*` 접두 클래스.
- 순환: A → B → A 로 되돌아오는 의존. 패키지 수준과 클래스 수준을 구분한다.
- 동작 변경 없는 PR: 클래스 이동·이름 변경·규칙 추가만 있고, 테스트가 그대로 통과하며 응답·DB 쓰기·로그 형식이 바뀌지 않는 PR.

## 최초 조사와 D안의 범위 밖

- 프론트엔드.
- 스키마(Flyway)·배포 스크립트·CI 설정. 이관 PR이 이 파일들을 건드리지 않는 것을 검증 조건으로 둔다.
- 과거 관측 이관 도구(migration-tool)의 절차 로직. 순환 해소와 규칙 적용만 다룬다.

새 DDD 전면 재설계는 백엔드 코드·스키마·배포 구성과 완료된 이관 코드 제거까지 다룬다. 기준 코드 9f의 1158개 테스트 통과 결과와 재설계 후 검증을 구분하고, 코드 구현·DB 전환·배포의 진행 상태를 별도로 기록한다. 기존 DB 데이터와 Flyway 적용 이력은 보존한다.

## 현재 구현을 읽을 때의 범위

공개 진입점은 PublishPendingForecasts·EvaluateForecasts·RefreshDemandStatistics·ActivateModel 등 실제 타입을 기준으로 설명한다. 수집의 내부 시도 식별자는 CollectionAttemptToken이며, 발행·평가·품질 조사의 근거는 CollectionInputs의 입력 확정 계약으로 보호한다. 저장 구조에는 V17·V18과 새 발행·평가·통계·품질·모델 활성화 테이블이 반영돼 있다.

DDD 책임을 보완하면서 외부 관측 조회는 ObservationSource를 통해 받고 GBIS 변환은 infrastructure로 옮겼다. 수집 저장과 품질 훅의 순서는 ObservationLoader, 평가 입력 확정·저장·보정 순서는 ForecastEvaluationWriter가 담당한다. 품질 조사의 시작·재시작과 첫 이상 관측 선택은 도메인에서 판단한다. 관련 클래스 수와 연결은 배치표의 현재 구현 절에 반영했다.

실제 예보 입력의 별도 스냅샷은 저장하지 않는다. featureContractVersion의 선언과 Java 특징 정책이 같은 의미인지 강제하는 검증은 기존 미구현 범위로 남아 있다. 프론트엔드의 중첩 forecast 응답 불일치도 이번 변경에서는 수정하지 않았다. 백엔드 검증 결과를 이러한 범위의 완료로 넓혀 설명하지 않는다.

최종 테스트 수, 실제 JAR·배포 실행 결과와 운영 전환 여부는 [진행 기록](ddd/implementation-progress.md)을 확인한다. 문서 사이트는 이번 로컬 정합성 작업에서 갱신하지 않았다.
