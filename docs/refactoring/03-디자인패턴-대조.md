## 1. 패키지 구성 원칙

정의. 계층별은 `controller/service/repository` 가 최상위, 기능별은 `board/route/vehicle` 이 최상위, 도메인별은 경계 컨텍스트(`collector/processor`)가 최상위다. package-private 은 패키지 밖에 공개할 형만 `public` 으로 두는 것이다.

우리 코드.

| 모듈 | 지금 | 크기 |
| --- | --- | --- |
| api-app | 기능 → 계층 2단 | 패키지당 최대 11 파일 |
| worker-app | 컨텍스트(collector·processor) 평면 + `persistence.*` + `seatdistribution` | collector 50, processor 60 파일이 한 패키지 |
| migration-tool | 단계별(`source/archive/db`) + 루트 | db 21 파일 7,672 줄 |

package-private 은 seatdistribution 22/40, migration 15/48 이 쓰고, collector·processor 는 0/110, api 는 1/92 다. collector·processor 가 평면이라 밖에 내놓을 것과 아닐 것의 구분이 없다.

판정.

- 기능별 하위 패키지(worker-app): **도입하면 나아짐**. 01 §4 의 순환과 별개로, 60 파일 평면은 새 클래스가 어디에 속하는지 이름으로만 알 수 있다. collector 를 `gbis/upstream/quota/route/batch/schedule`, processor 를 `job/forecast/settlement/sameday/demand/trajectory/route/deployment` 로 배정해 클래스 의존 그래프를 다시 계산했다. collector 는 순환 없이 성립하고, processor 는 `SupportedForecastScope.digest()` 가 seatdistribution 의 package-private `Sha256` 을 쓰는 간선 하나만 남는다(04 §2-2 표). 첫 배정에서는 값 형(`TimeSlot`, `ForecastDistance`, `VehicleStopTarget`, `PendingForecastBatch`)이 `forecast` 에, 잡이 각 기능에 섞여 있어 10개 묶음이 한 덩어리로 묶였다. 값 형을 아래(`route`·`trajectory`·`demand`)로, 잡을 위(`job`)로 옮기니 풀렸다. 평면 패키지가 숨기던 방향이 나눌 때 드러난다는 뜻이다.
- 계층별 최상위(`…/service`, `…/repository`): **과함**. api-app 은 이미 기능 우선이고, worker-app 에서 계층을 최상위로 올리면 collector 와 processor 의 클래스가 한 패키지에 섞여 `PackageBoundaryTest` 가 잡던 경계가 사라진다.
- api-app 재구성: **손대지 않음**. 패키지당 11 파일 이하이고 계층 방향이 실측으로 깨끗하다(01 §3-1). 어댑터가 `http.ServiceUnavailableException` 을 던지는 3곳과 기능 루트에 예외를 두는 것은 컨벤션 문제라 04 규칙으로 다룬다.
- migration-tool: **순환만**. 루트의 CLI 3 파일(`MigrationCli`, `CliArguments`, `ApprovalGate`)을 `cli` 로 내리면 루트는 유틸만 남아 방향이 한쪽이 된다.

비용(04 §2 표에 상세). worker-app 기능별 분할은 main 113 파일 이동(collector 50, processor 60, seatdistribution 3), test 52 파일 이동, import 수정은 `persistence.*` 21 파일·seatdistribution 37 파일·migration-tool 4 파일. `git mv` 라 히스토리는 따라온다.

## 2. 포트·어댑터(헥사고날) 부분 적용

정의. 도메인이 필요한 것을 인터페이스(포트)로 선언하고 기술 구현(어댑터)이 그것을 구현한다. 의존은 어댑터 → 도메인 한 방향이다.

우리 코드. 이미 이 모양이다.

| 포트 | 어댑터 | 위치 |
| --- | --- | --- |
| `collector.ObservationRepository`, `CallQuotaRepository`, `RouteRegistry`, `CurrentRouteVersionRepository`, `RouteVersionRepository` | `Jpa*` 2, `Jdbc*` 3 | `collector.persistence.{jpa,jdbc}` |
| `processor.SeatForecastRepository`, `VehicleTrajectoryRepository`, `ArrivalObservationRepository`, `StopDemandStatisticsRepository`, `SameDayFullOutcomesRepository`, `ModelDeploymentRepository`, `RouteVersionRepository` | `Jdbc*` 7 | `processor.persistence.jdbc` |
| `processor.ForecastRuntime`, `SeatForecastModel`, `seatdistribution.CoefficientLookup` | `ActiveForecastRuntimeResolver`, `SeatDistributionForecastModel`, `CoefficientBundle` | `processor.seatdistribution` |
| `api.*.application.*QueryRepository` 3 | `Jpa*QueryRepository` 3 | `api.*.persistence.jpa` |
| `migration.source.SourceObjectStore` | `AwsSourceObjectStore` | `migration.source` |

javadoc 이 이미 "포트"라고 부른다(`processor.RouteVersionRepository` "processor 자기 형으로 읽는 포트"). 어댑터가 포트 패키지만 보고 어댑터끼리 의존하지 않는 것도 실측으로 맞다(01 §3-2).

경계가 흐린 곳 셋.

1. 포트 `ForecastRuntime` 의 반환형 `RuntimeSnapshot` 과 재료 record 의 구성요소 `SameDayFullOutcomes` 가 어댑터 패키지(seatdistribution)에 있다. 이것이 01 §4-1 순환이다.
2. api-app 어댑터 3개가 HTTP 층의 `ServiceUnavailableException` 을 만들어 던진다(`…/api/board/persistence/jpa/JpaBoardQueryRepository.java`). 어댑터가 응답 정책을 안다.
3. 상류 호출 쪽(`GbisLocationSource`, `GbisRouteSource`)은 설계 문서(`RealtimeObservationSource`)와 달리 포트 없이 구체 클래스다. 테스트는 `MockRestServiceServer` 로 HTTP 를 흉내 내므로 지금은 불편이 없다.

판정. **이미 있음**. 1번은 record 3개 이동으로 풀리고(도입하면 나아짐), 2번은 예외를 api 전용 데이터 접근 예외로 바꾸거나 서비스가 잡는 것으로 옮기는 규칙 문제다. 완전형(`application.port.in`, `adapter.out.persistence`, 유스케이스 인터페이스 `GetBoardUseCase`)은 **과함**이다. 포트 19개가 전부 구현 하나이고 두 번째 구현 계획이 없다. 인터페이스만 늘고 파일 수가 두 배가 된다.

비용. 1번: main 3 파일 이동 + `Sha256` 처리 + import 수정 main 10·test 9 파일. 2번: 어댑터 3 + 핸들러 1 + 테스트 3(`JpaBoardQueryRepositoryTest` 등). 3번: 안 함.

## 3. 전략

정의. 같은 일을 하는 알고리즘을 인터페이스 뒤에 두고 실행 시점에 고른다.

우리 코드.

| 자리 | 인터페이스 | 구현 | 고르는 방법 |
| --- | --- | --- | --- |
| 좌석 예보 모델 | `processor.SeatForecastModel` | `SeatDistributionForecastModel`(main), `ForecastJobTest.FixedSeatForecastModel`(test) | `ForecastRuntime.resolveActive()` 가 DB 의 ACTIVE 배포와 메모리의 계수 묶음 신원이 맞을 때 `RuntimeSnapshot` 으로 묶어 준다 |
| 당일 후보정 | `seatdistribution.FullChancePriorShift`, `FullChanceHurdle` | 계수 번들의 고정 식 | 번들 교체가 곧 전략 교체 |
| 캐시·신선도 | `BoardCachePolicy`, `VehicleCachePolicy`, `*FreshnessPolicy` | 구체 클래스 | 없음(하나) |
| 시간대 | `ForecastTimeSlot.of(batch, clock)` | 정적 | 없음 |

배정 메모의 `score_policy` 는 이 레포에 없다. 평가 사이트(`current_public/evaluation/score_policy.json`)의 채점 정책이고 worker 는 설계행렬 열 이름(`fill_rate_score`)만 안다.

판정. **이미 있음**. 모델 전략은 데이터(배포 행)로 고르는 전략이라 코드 분기가 없다. 정책 클래스에 인터페이스를 씌우는 것은 구현이 하나라 **과함**이다. 새 모델 방식이 들어오면 `SeatForecastModel` 구현을 하나 더 두고 `ActiveForecastRuntimeResolver.snapshotOf` 에서 번들 종류로 고르면 된다. 설계 문서 §7 "모델 방식을 갈아끼운다 → 새 모델 1 + 설정 1줄" 이 지금도 맞다.

## 4. 템플릿 메서드·콜백

정의. 고정된 절차를 한 곳에 두고 변하는 부분만 하위 클래스(템플릿 메서드)나 람다(콜백)로 받는다.

우리 코드.

- `JdbcClient` 자체가 콜백형이다. `.sql(SQL).params(...).query((rs, rowNum) -> ...)` 가 13곳, `.query(Long.class)` 9곳.
- `TransactionTemplate.execute(status -> ...)` (`RouteCatalogLoader.open`).
- `DatabaseConnections.transaction(environment, SqlWork)` (`…/migration/db/DatabaseConnections.java`) 가 손으로 쓴 템플릿이다. 커밋·롤백·예외 감싸기를 한 곳에 두고 `SqlWork<T>` 람다를 받는다.
- 반복되는 것: jdbc 어댑터 5 파일이 `ZoneOffset.UTC` 로 `OffsetDateTime → Instant` 를 변환하는 private `instantOf` 를 각자 가진다. `resultSet.getObject("response_received_at", OffsetDateTime.class)` 꼴이 7곳.

판정. **이미 있음**. 상속 기반 템플릿(`AbstractJdbcRepository`)은 **과함**이다. 어댑터 7개가 공유하는 절차가 없고 SQL 도 각자 다르다. 변환 도우미 하나(`Timestamps.instantOf(rs, column)`)를 `processor.persistence.jdbc` 에 두는 것은 **도입하면 나아짐**이지만 줄이는 코드가 20줄 안쪽이라 이관 PR 에 얹지 않고 다음 기능 PR 에서 처리해도 된다.

비용. 도우미 1 파일 + 어댑터 5 파일. 테스트 영향 없음.

## 5. 빌더·정적 팩토리

정의. 정적 팩토리는 생성자 대신 이름 있는 메서드로 만들고, 빌더는 여러 단계로 채운 뒤 만든다.

우리 코드.

- 정적 팩토리 `of` 32, `from` 29, `create` 2. 규칙이 있다. 다른 형에서 바꾸면 `from(BusLocation)`, 구성요소로 만들면 `of(...)`, 검증은 compact 생성자.
- 빌더 클래스 2개는 전부 migration-tool 이고 생성 빌더가 아니라 누적기다(`SourceInventoryBuilder`, `RdsObservationDeltaBuilder.BatchBuilder`). `.builder()` 호출 10곳은 Jackson `JsonMapper` 와 AWS SDK 라이브러리 것이다. Lombok `@Builder` 0.
- 구성요소가 많은 record: `VehicleObservation` 10, `ForecastProperties` 8, `SeatForecastInput` 6. 테스트가 이것을 만들 때 위치 인자를 길게 쓰고, 그래서 `ForecastInputFixture`·`CoefficientsFixture` 같은 픽스처가 있다.

판정. **이미 있음**. record 시대에 main 쪽 빌더는 **과함**이다. 불변 검증이 compact 생성자에 있어 빌더가 검증을 우회할 길을 만든다. 테스트 쪽 픽스처 빌더는 지금처럼 필요할 때 `*Fixture` 로 둔다.

## 6. 도메인 이벤트

정의. 한 곳의 상태 변화를 이벤트로 내고 다른 곳이 구독한다. 결합을 끊고 소비자를 늘리기 쉽다.

우리 코드. 배정 메모의 "정산 → 집계 갱신"은 이 자리다.

```
ArrivalLabelJob.settleArrivalLabels()   @Transactional
  ├─ seatForecastRepository.settle(settlements)      → List<SettledForecast>
  └─ sameDayFullOutcomesService.record(settled)       당일 성적 칸을 증분 갱신
```

`…/processor/ArrivalLabelJob.java` 가 두 호출을 한 트랜잭션 안에서 직접 한다. 셀 통계(`StopDemandStatisticsJob`)는 이벤트가 아니라 6시간 주기로 따로 돈다. `ApplicationEventPublisher` 0, `@EventListener` 는 `ApplicationReadyEvent` 1곳.

판정. **과함**. 이유 셋.

1. 생산자 1, 소비자 1이다. 셋째 소비자가 없다.
2. `record` 는 `settle` 과 같은 트랜잭션에 있어야 한다. `@TransactionalEventListener(AFTER_COMMIT)` 로 바꾸면 정산은 됐는데 성적이 안 오른 상태가 생기고, `BEFORE_COMMIT` 이면 지금과 같은데 간접층만 는다.
3. 스케줄러 스레드가 하나다(`spring.task.scheduling.pool.size` 미설정). 비동기 이벤트로 바꾸면 스레드 모델 결정이 먼저다.

다시 볼 조건. 정산 결과를 받는 곳이 둘 이상이 되거나(예: 알림, 지표), 셀 통계를 정산 직후 증분 갱신으로 바꾸기로 할 때.

비용(참고). main 3~4 파일, test 3 파일(`ArrivalLabelJobTest`, `SameDayFullOutcomesServiceTest`, `ForecastJobTest`).

## 7. 명령·조회 분리(CQRS)

정의. 쓰는 모델과 읽는 모델을 나눈다.

우리 코드. 모듈 수준에서 이미 나뉘어 있다.

| | 쓰기 | 읽기 |
| --- | --- | --- |
| 모듈 | worker-app | api-app(`@Transactional(readOnly = true)` 3 서비스, `*QueryService`, `*QueryRepository`) |
| 모델 | collector 엔티티(행동 있음), processor 는 SQL 직접 | 조회마다 다른 투영 엔티티(01 §8-1), 읽기 record(`BoardSnapshot`) |

포트 안에서는 읽기·쓰기가 섞여 있다. `SeatForecastRepository` 는 `save`·`markForecastCompleted`·`findPending`·`settle` 을 한 인터페이스에 두고 javadoc 에 "넷이 같은 행의 생애라 나누면 규칙이 갈라진다"고 적었다.

판정. **이미 있음**. 포트 단위 분리는 팀이 이유를 적고 거부한 결정이라 **과함**으로 둔다. api-app 의 투영 엔티티 3벌은 CQRS 의 읽기 모델이지 중복이 아니다. 합치면 조회 최적화 자유도가 줄고 설계 문서의 "두 조회가 표를 공유하지 않는다"가 깨진다.

## 8. 리포지토리 인터페이스 분리

정의. 큰 인터페이스 하나 대신 쓰는 쪽 기준으로 작은 인터페이스 여럿을 둔다.

우리 코드.

- 포트가 이미 쓰는 쪽 기준이다. `ObservationRepository` 6 메서드는 장부 단계 그대로이고, `RouteVersionRepository` 는 collector(쓰기 4 메서드)와 processor(읽기 2 메서드)에 따로 있다.
- Spring Data 인터페이스가 `JpaRepository` 가 아니라 `org.springframework.data.repository.Repository<>` 를 상속해 필요한 메서드만 드러낸다(`SeatForecastEntityRepository` 1 메서드, `ModelDeploymentEntityRepository` 2 메서드). `findAll`·`deleteAll` 이 어댑터 밖으로 새지 않는다.
- 어댑터 하나가 Spring Data 여럿을 조립한다(`JpaBoardQueryRepository` 가 5개 + `Clock`).

판정. **이미 있음**. 더 쪼갤 곳이 없다.

## 9. 값 객체

정의. 식별자 없이 값으로 같음을 판단하고 불변이며 스스로 검증하는 형.

우리 코드. record 로 이미 많다.

| 값 객체 | 검증 | 위치 |
| --- | --- | --- |
| `RouteId` | 9자리 숫자, 아니면 `InvalidRouteIdException` | api `route/` |
| `RemainingSeats`(sealed `Known`·`Unknown`), `VehicleSeat` | 음수 금지, 사유 필수 | collector, api vehicle |
| `SeoulDay`, `ForecastDistance`, `SeatDistribution`, `SameDayFullOutcomes`, `SupportedForecastScope`, `RouteStops`, `ObservationAttempt`, `RouteContentDigest` | compact 생성자 | processor, collector |
| `TimeSlot`, `ScoringState`, `CallQuota` | enum + 메서드 | processor, collector |

빠진 곳. 식별자가 원시형이다. 포트 시그니처의 `long routeVersionId`, `long batchId`, `String upstreamRouteId`(`ObservationRepository.markDispatching(long batchId, …)`, `RouteVersionRepository.readStops(long routeVersionId)`). api 는 `RouteId` 를 만들고도 어댑터에서 `routeId.value()` 로 풀어 쓴다.

판정. **이미 있음**. 식별자 값 객체(`RouteVersionId`, `BatchId`)는 **과함**이다. 포트 19개, SQL 매핑 전부, 테스트 수백 곳이 바뀌고 JDBC 경계에서는 결국 `long` 으로 풀어야 한다. 새 코드에서 두 식별자를 자주 섞어 넘기는 자리가 생기면 그때 그 자리만 감싼다.
