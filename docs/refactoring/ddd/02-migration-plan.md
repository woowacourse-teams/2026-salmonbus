# 구현·오프라인 데이터 전환·검증 계획

기준 소스는 PR #70이 병합된 `9f9c75db16fcdefc0944f0c6a40fa7c09e4e1d94`다. 백엔드 전면 재설계와 완료된 S3 이관 코드 제거가 승인됐으며, 전체 변경은 작업 단위별 커밋으로 나눈다. 현재 구현 이름은 [용어집](glossary.md), 최종 검증·운영 반영 상태는 [진행 기록](implementation-progress.md)을 기준으로 한다. 이 문서는 코드 작업의 구분과 앞으로 운영에서 실행할 전환 절차를 함께 정리한다. 코드가 존재한다는 사실과 운영 DB에 적용했다는 사실은 구분한다.

이번 운영 전환은 정비 시간에 관련 쓰기와 앱을 중지한 상태에서 한 번에 수행한다. 이중 쓰기, 구·신 앱의 혼합 운영, 앱별 독립 롤백은 구현하지 않는다. 기존 DB 데이터와 Flyway 적용 이력을 보존해 목표 구조로 옮기고, 실패하면 전환 전 DB와 대응 앱 릴리스를 함께 복구한다.

프론트엔드 수정과 실제 예보 입력·특징 벡터·보정값의 별도 스냅샷 저장은 범위에서 제외한다. 백엔드 HTTP 계약과 기존 원 관측·예측·평가·품질 자료는 유지한다. [설계안](00-design.md)은 이 선택의 업무 모델과 개념을 설명하고, 이 문서는 구현과 검증 순서를 정한다.

## 1. 변경 종류를 구분한다

| 종류 | 예 | 검증 |
| --- | --- | --- |
| 구조 변경 | Gradle 모듈, 포트, 순수 계산 분리, 패키지 이동 | 기존 계약·계산 출력·컴파일 경계 유지 |
| 내부 정확성 보강 | revision 검사, 중복 발행 거부, 모든 평가 CAS, 모델 명령 멱등 | 경쟁·실패 시나리오를 새 테스트로 고정 |
| 데이터 모델 전환 | 발행 테이블, 평가 근거 데이터, 세대 metadata, 활성 슬롯 | 원 데이터 대조·오프라인 전환·DB와 앱의 일괄 복구 |
| 외부 정책 변경 | 노선별 READY, 빈 발행 모델 표시, 캐시 변경 | 현재 계약과 다른 점 명시·별도 기능 변경 |

이번 전환에서는 첫 세 종류의 변경을 권장한다. 외부 정책은 기본적으로 기존 계약을 유지하며 모델 수학과 화면 의미도 함께 바꾸지 않는다.

## 2. 단계별 완료 기준

### 0. 현재 계약과 검증 기준 확정

- [근거 문서](01-evidence.md)의 C/F/API 계약을 기존 테스트에 연결한다.
- 구현 착수 전 `9f9c75d` 기준 1158개 테스트 PASS를 기준선으로 기록한다. 재설계 코드의 빌드와 테스트 결과는 각 구현 단위에서 별도로 남긴다.
- 정규화 입력 → 특징 → 확률, 빈 응답·실패·옛 버전·모델 승격 사례를 비교용 fixture로 확보한다.
- source·예측·평가·seed의 유일키, 참조 수, 미평가 수를 집계하는 read-only 비교 쿼리를 준비한다.
- PR #70의 편도 판정·조사 커서·품질 버전·용도별 view를 비교 대상에 포함한다. 기존 seed 장부와 온라인 통계 입력은 구분한다.
- 실제 모델 fixture로 계산 시간과 잠금 시간을 측정한다. 실제 예보 입력을 별도 저장하는 기능과 그 저장량 측정은 이번 범위에서 제외한다.

완료 기준: 현행 동작과 알려진 한계를 구분하고 다음 단계에서 유지할 동작을 확인할 수 있다.

### 1. 일회성 이관 코드를 정리하고 계산을 forecasting에 배치

- 별도 `forecast-math`는 만들지 않는다. 기존 12개 계산·값 타입을 forecasting.domain의 평가·통계·관련 값 패키지로 옮기고 계산 버전 계약도 통계 책임에 둔다.
- S3 inventory/export/archive, 반입·대조·롤백, 일회성 seed 및 임시 모델 전환 명령과 구현을 제거한다. 도메인 계산 자체는 현재 온라인 소비자를 확인해 유지한다.
- 완료된 이관 전용 테스트·fixture·실행 스크립트는 기능 제거와 함께 정리한다. 같은 계산을 사용하는 온라인 평가·통계 테스트와 PR #70의 품질 정비 테스트는 보존한다.
- 기존 migration-tool의 Worker 실행 앱 의존을 제거하고 품질 정비 실행 프로그램을 `maintenance-app`으로 구성한다.
- 온라인 통계는 편도 근거 없는 seed 합계를 읽지 않는 PR #70의 계약을 유지한다. 과거 cutover 이전이라도 품질 조건을 통과한 원본 평가 자료는 집계한다. 이관 도구의 계산 경로를 제거하면서 이 온라인 동작까지 삭제하지 않는다.
- 일회성 Java 38개는 삭제하고 `TripQualityMaintenance`의 업무 구현 1개는 forecasting으로 이동한다. CLI 지원 10개는 maintenance-app의 명령·설정·연결·정비 권한 확인으로 재구성한다. 한 chunk의 TX는 forecasting 유스케이스가 맡는다. CLI는 스케줄러와 Flyway를 자동 실행하지 않고 대상 DB 설정과 승인 조건을 확인한다. 별도 스키마 버전 사전 안내 기능은 없다.
- common의 `VehicleObservationsStored`는 observations의 공개 사건 계약으로 옮긴다. 관측 저장·조사 등록의 동일 TX 계약과 모듈 의존 방향을 함께 검증한다.
- 새 모듈을 추가할 때 `buildspec.yml`과 `deploy/rehearsal/digest.sh`의 sourceDigest 입력을 갱신한다.
- 각 앱이 runtime에 의존하는 모듈이 변경되면 해당 앱의 release digest도 반드시 바뀌게 한다. 의존하지 않는 모듈까지 같은 digest에 포함할지는 명시한다.
- 기존 `common`의 Flyway 자원 위치와 실행 앱을 유지하고 새 영역의 테이블 변경을 공통 migration 순서에 넣는다.

완료 기준: 새 모듈의 코드 한 줄만 바뀌어도 해당 앱 artifact를 새 버전으로 인식하는지 확인하는 검증을 통과한다. `install.sh`가 같은 digest의 옛 JAR를 재사용하는 경로까지 시험한다.

### 2. 노선·외부 호출 경계를 한 기능씩 옮긴다

- `route-catalog`, `api-call-quota`, `gbis-client`를 구성한다.
- 카탈로그 공개 진입은 `CurrentRouteVersion.currentVersionOf`다. 버전 교체·시간표 수정은 RouteVersionLoader와 Route.accept가 담당한다.
- GBIS 클라이언트는 HTTP·인증·JSON·외부 오류만 다루며 노선·관측의 내부형에 의존하지 않는다.
- 카탈로그와 관측의 변환 어댑터가 각자의 도메인값을 만든다. 관측은 ObservationSource·ObservationResponse를 사용하고, GbisObservationSource가 외부 조회 직후 시각을 확보한 다음 GbisObservationMapper로 정규화한다. 응용·도메인 계층에서 GBIS 타입을 참조하지 않는다.
- 노선 단위 잠금 안에서 현재 버전 확인 → 이전 버전 종료/flush → 새 버전·정류장 저장을 함께 처리한다. HTTP는 잠금을 잡기 전에 끝낸다.
- 현재 열려 있는 버전이 없을 때는 닫힌 최신 버전을 잘못 수정하지 않도록 해당 경로를 명시적으로 처리한다.
- 시간표를 같은 버전에서 수정하는 방식과 현재 bootstrap 정책은 유지한다.

완료 기준: 노선 하나의 최초 등록, 중복 등록, 버전 교체, 시간표 수정, 종료된 버전 변경 거부를 검증한다. 서로 다른 호출 한도 키도 보존된다.

### 3. 관측 도메인과 시도 token을 도입한다

- `CollectionBatch` POJO는 허용되는 상태 전이, 현재 시도, 사용 확정 규칙을 담당한다. JPA 엔티티는 매핑과 DB 동시성을 담당한다.
- 기존 `attempt_number`를 source revision으로 사용한다. 모든 쓰기 명령은 전달받은 revision을 현재 값과 비교해야 한다.
- `CollectionAttemptToken(batchId, attemptNumber)`을 reserve → dispatch → complete/abandon 전체에 전달한다.
- 계획 유일키 충돌, 동시 재열기, 뒤늦은 응답, 호출 한도 부족을 구별한다.
- 기존 완료 기록을 새 `inputConfirmedAt` 상태로 이관한다. 전환 중 쓰기는 중지하며 구 완료 marker와 새 상태를 이중으로 쓰는 코드는 추가하지 않는다.
- 정상 빈 응답·실패·필터 제외·DB 저장 실패를 각각 검증한다.
- ObservationLoader가 저장 전 품질 훅 → 배치 저장 → 새 StoredObservations에 대한 저장 후 훅을 조율한다. 저장소는 같은 결과에 빈 Optional을 반환해 중복 조사를 막는다. 정상 관측에 품질 조사 SQL을 추가하지 않는 계약도 유지한다.

완료 기준: 오래된 응답은 새 revision을 덮지 못한다. 같은 계획의 재시도와 호출 횟수 예약은 현재 정책을 유지한다.

### 4. 예보 발행을 업무 사실로 만든다

- `ForecastPublication`과 publication FK를 추가한다. 기존 예보 PK는 우선 유지한다.
- 품질 guard → 관측 공개 기능의 source 잠금 → 현재 revision 검사 → 품질 조건을 반영한 입력 읽기 → 계산 → 사용 확정/발행 기록 순서로 구현한다.
- 업무 포트의 `confirmInput`는 호출자의 TX에 참여해야 한다. 독립된 REQUIRES_NEW로 먼저 확정하면 발행이 실패했을 때 동작이 달라진다.
- 이미 발행된 source에 대한 재요청은 같은 발행을 반환한다. 예측값·generatedAt·모델을 덮는 UPSERT는 신규 경로에서 제거한다.
- 예측행이 0행인 완료도 header로 남긴다. 완료 여부는 예측행의 유무로 판단하지 않는다.
- 모델·통계·품질 버전과 발행 시각을 기록한다. 실제 보정값·계산 입력·특징 벡터의 별도 저장은 추가하지 않는다.
- 발행의 품질 버전과 판정 규칙을 식별 정보에 연결한다. 사후 제외는 예측값을 고쳐 쓰지 않고 현재 사용 조건으로 반영한다.
- `SeatRangeException`은 해당 차량의 모든 예측을 제외하고 다른 차량은 계속 처리한다. 모든 차량이 제외된 0행 완료와 범위 오류 외 예외의 전체 롤백을 구분한다.
- 새 발행 저장소를 유일한 발행 경로로 사용한다. 기존 데이터는 오프라인으로 한 번 이관하고 검증한다.

완료 기준: 발행 경쟁, 수집 재열기 경쟁, 계산 실패, commit 실패가 발생해도 일부만 발행되거나 근거가 바뀌지 않는다. 관측 수집 자체는 예보 실패로 롤백되지 않는다.

### 5. 평가·보정·세대·모델 수명주기를 완성한다

같은 PR 안에서 평가·보정, 통계, 모델 변경을 각각 검토할 수 있도록 커밋을 구성하고 의존 관계를 보존한다.

- `ForecastEvaluation`·`EvaluationResult`와 불변 평가 근거 데이터를 도입하고 기존 평가값을 이관한다.
- PR #70에서 모든 종결 UPDATE에 적용한 PENDING 조건을 새 평가 저장소에서도 유지한다. 품질 조건과 노선·차량·방향 검사를 보존한다. 종결 결과 수정은 일반 재시도와 구분한 별도 정정 유스케이스가 있어야 한다.
- ForecastEvaluationWriter가 노선 ID 순 품질 guard → canComplete → 도착 배치 잠금·입력 확정 → 평가 CAS → 보정 순서를 담당한다. 완료할 수 없는 평가에는 입력 확정과 보정을 수행하지 않는다. 누계가 없으면 새 평가까지 포함해 초기화하고, 이미 있으면 새 확정분만 더한다.
- 온라인 통계는 품질 조건을 통과한 원본 평가 자료만 집계하고, 근거를 확인할 수 없는 historical seed 합계는 다시 합산하지 않는다. 통계 metadata를 추가하되 현행 통계 writer TX·노선 잠금이 보호하는 세대 번호 할당을 유지한다.
- 품질 조사·판정·노선 품질 상태를 forecasting 안의 별도 책임으로 나눈다. start/restart와 차량별 첫 이상 선택은 도메인이 판단한다. 응용 서비스는 조회·저장·근거 입력 확정·품질 버전 갱신을 조율하고 기존 completed 값과 진행 중 조사 보존 규칙을 유지한다.
- 완전한 모델 식별 정보, 명령 ID, expected-active 버전, 준비된 runtime을 각각 분리해 다룬다.
- route/feature contract 검증은 단순 digest 문자열 확인과 전체 특징 parity 검증을 구분한다.

완료 기준: 이미 확정한 예측값은 바뀌지 않고 평가·보정은 한 번 반영된다. 이전 통계 세대와 모델 이력은 조회 가능하다.

품질 판정이 바뀌면 기존 예측값과 근거는 보존하면서 현재 보정·통계·학습에 사용할 자료를 다시 고를 수 있어야 한다. 진행 중인 조사와 정비 작업은 중단 위치부터 같은 정책으로 재개돼야 한다.

### 6. API 읽기 계약 전환과 legacy 제거

- API는 신규 발행·평가 구조를 읽되 기존 JSON·오류·시간·캐시 의미를 유지한다.
- 기준 JSON은 PR #70의 `forecast.status`를 포함한다. 원 관측에서 접근 차량을 먼저 고르고 예보 없음과 확률 0을 구분한다. API와 보정·통계·학습의 품질 필터를 서로 바꾸지 않는다.
- 프론트엔드 파일과 화면 동작은 수정하지 않는다. 기준 소스의 클라이언트 불일치는 별도 확인 사항으로 남기며 백엔드 계약 테스트를 화면 검증으로 취급하지 않는다.
- 같은 DB에서 공개된 query/view 계약을 사용한다. 쓰기 업무 모듈의 JPA 엔티티를 공유하지 않는다.
- 오프라인 backfill과 원 데이터 대조를 통과한 뒤 새 읽기 경로로 기동한다.
- 구 앱의 실행이 중지된 상태에서 모든 참조와 소비자를 전환한다. 구 marker·평가 열·FK의 제거는 데이터 대조와 참조 보존 조건을 확인한 뒤 수행한다.
- 마지막으로 common의 기존 두 경계 규칙을 새로운 모듈 규칙으로 바꾸고 설계·운영 문서를 갱신한다.

완료 기준: 전체 production 클래스 배치표가 실제 코드와 일치하며 허용하지 않은 모듈 참조와 구 쓰기 경로가 없다.

## 3. 잠금과 원자성 계약

| 경로 | 순서 | 실패 처리 |
| --- | --- | --- |
| 새 수집/재시도/자정 dispatch | 계획·batch 확보/잠금 → token/상태 검증 → budget key 정렬 예약 → 기록 | 같은 TX 롤백. 실제 HTTP는 commit 이후 |
| 이상 관측 저장+조사 등록 | 저장할 정규화 행 확인 → 품질 guard → batch 잠금/token 확인 → 관측 저장 → 조사 등록·품질 버전 변경 | 원 관측과 조사 요청을 함께 롤백. 정상 행에는 품질용 SQL 추가 없음 |
| 노선 버전 변경 | HTTP 완료 → route 잠금 → 현재 버전 재확인 → 닫기/신규 버전 저장 | 같은 버전 변경 시 경합은 재조회·멱등 처리 |
| 예보 발행 | 품질 guard → source batch 잠금 → revision/기존 발행 확인 → 입력 읽기/계산 → 입력 확정 → publication/예측행/평가 상태 | 전체 TX 롤백·제한된 DB 재시도 |
| 평가+당일 보정 | 응용 Writer에서 노선 ID 순 품질 guard → canComplete → 도착 입력 확정 → CAS → 보정 | 누계가 없으면 새 결과를 포함해 초기화하고 중복 가산하지 않음. 실패 시 전체 롤백 |
| 통계 공개 | 품질 guard → 계산용 일관된 입력 확보 → 현재 revision 조회 → 다음 revision·metadata·cells 저장 | 일부 세대 노출과 서로 다른 품질 버전의 혼합 금지 |
| 품질 조사·CLI 정비 | 품질 guard → 조사 진행 상태 확인 → 제한된 관측 읽기/판정 → 연결·판정·커서 저장 → 필요 시 품질 버전 변경 | 한 페이지 실패 시 함께 롤백, 다음 실행에서 같은 작업 재개 |
| 모델 활성화 | 파일 검증/준비 → active slot 잠금 → commandId/기대 버전 검사 → 기존 retire/새 activate | 메모리 준비물과 DB rollback 별도 취급 |

source 잠금 규약은 새 발행 경로뿐 아니라 재열기·dispatch·complete에도 적용해야 한다. 각 경로가 같은 batch 잠금과 token 검사를 사용해야 한다. 모든 경로를 한 버전으로 전환하기 전까지는 강화된 동시성 보장이 완성됐다고 볼 수 없다.

기준 코드의 품질 직렬화는 `route` 행의 FOR UPDATE였다. 현재 구현은 forecasting의 `RouteDataQuality`와 `route_data_quality`를 사용한다. 오프라인 전환 후 기동하는 모든 쓰기 경로가 같은 새 guard를 사용해야 한다. 구 경로를 동시에 실행하지 않으며, 노선 버전 번호·수집 시도 번호·품질 버전·통계 revision을 하나의 값으로 합치지 않는다.

평가 응용 Writer는 canComplete를 통과한 도착 관측의 batch를 `lockForObservation`으로 잠그고 `confirmInput`으로 확정한다. 저장소는 이후 CAS와 근거값 저장을 담당한다. 도착 관측 FK를 제거했어도 이 잠금은 유지한다. 품질 조사의 근거와 탐색 위치도 같은 입력 확정 계약을 사용한다. 각 경로는 품질 guard 뒤에 batch 잠금을 확보해야 한다.

DB 제약을 최종 방어 수단으로 두고 deadlock/serialization 실패에 대한 제한된 재시도, 충돌 로그·지표, 재시도 한도 소진(retry exhaustion) 처리를 설계한다. 이 재시도는 외부 HTTP를 자동 재호출하는 재시도와 분리한다.

여러 업무 모듈의 저장소는 같은 DataSource와 같은 Spring transaction manager에 참여해야 한다. JPA와 JDBC를 섞어 사용하더라도 서로 다른 연결에서 독립 커밋하지 않는지 실패 주입 통합 테스트로 확인한다.

## 4. 오프라인 스키마·데이터 전환

재설계 전 앱 기준은 V1~V16, historical migration은 V1~V4다. 기존 migration 내용·checksum·적용 이력을 유지하고 V17과 V18을 추가했다. 운영 전환에는 SAL-134 전환 실행기를 사용한다.

일회성 백필·대조·전환 실행 코드는 `backend/deploy/migrations/<change-id>`에 둔다. 상시 품질 정비 CLI에 특정 재설계의 전환 명령을 계속 남기지 않는다. 스키마 DDL은 Flyway에서 관리하고 실행 스크립트는 그 적용과 데이터 이전 순서를 조율한다.

| 대상 | 목표와 데이터 보존 조건 |
| --- | --- |
| 발행 | `UNIQUE(source_batch_id)`. source 시도·노선 버전·모델·통계·품질 식별 정보와 발행 시각을 기록한다. 0행 발행도 이관한다. |
| 예측 | 기존 `(vehicle_observation_id, target_stop_order)` 의미와 원 예측값을 보존하고 publication FK를 연결한다. |
| 평가 | 예측키당 평가 하나. 상태별 근거·시각·좌석의 NULL 조건과 PENDING 전이를 보존한다. |
| 통계 | 기존 계산 버전·revision·cell 값을 보존하고 완성된 `DemandStatisticsVersion`에 연결한다. |
| 활성 모델 | 기존 배포 ID·ACTIVE를 보존해 슬롯을 초기화한다. 전체 모델 식별 정보, 요청 ID와 expected-active 버전으로 활성화를 검증한다. |
| 수집 | 계획 유일키·현재 `attempt_number`·원 관측값을 보존하고 완료된 발행의 입력을 `inputConfirmedAt`으로 확정한다. |
| 품질 | 기존 편도 판정·조사 진행·두 탐색 위치·품질 버전·연결 간격·근거를 보존한다. 관측–편도 연결과 노선 품질 상태의 쓰기 책임은 forecasting으로 옮긴다. |

### 4.1 전환 절차

1. 복사 DB에서 사용할 전환 절차와 검증 쿼리를 먼저 완성한다. DB 백업과 대응하는 앱 릴리스의 복구 절차도 시험한다.
2. 운영 정비 시 API와 Worker, 실행 중인 maintenance-app을 중지한다. 수집·발행·평가·통계·품질 조사의 쓰기가 끝났는지 확인한다. `forecast.enabled=false`만으로 모든 쓰기가 멈췄다고 판단하지 않는다.
3. 백업을 확보하고 테이블별 행 수, 원 관측·예측·평가 값, 참조, ACTIVE, 품질 커서와 버전의 비교 기준을 기록한다.
4. 새 스키마를 적용하고 기존 완료 배치·예측·평가·통계·모델·품질 자료를 이관한다. 스크립트는 같은 작업의 재실행 여부를 식별하고 중복 데이터를 만들지 않아야 한다.
5. 기존 예측이 0행인 완료 배치에서 당시 모델을 알 수 없다면 현재 ACTIVE를 과거 사실로 채우지 않는다. `LEGACY_UNKNOWN`으로 구분한다. 같은 배치에 서로 다른 모델·generatedAt이 있다면 임의 MIN/MAX로 합치지 않고 진단 대상으로 남긴다.
6. 평가값과 도착 관측의 값·시각·노선 버전·차량·정류장·운행 상태·좌석 정보·편도·방향을 대조한다. 평가 근거에 별도 시도 번호 컬럼은 없다. 새 평가 근거에도 현재 품질 조건을 적용해 제외 자료가 다시 집계되지 않게 한다.
7. 편도 시작·근거 FK와 조사 cursor·anchor·boundary candidate까지 대조한다. 원 관측 참조를 보존하지 못한 상태에서 재수집 DELETE의 허용 범위를 넓히지 않는다.
8. API·보정·통계·학습의 용도별 품질 필터와 모든 새 조회·쓰기 경로를 확인한다. 원 데이터와 새 기록의 대조를 마친 뒤 사용하지 않는 구 컬럼·참조를 정리한다. 원 DB 데이터의 초기화·통삭제는 수행하지 않는다.
9. 같은 새 릴리스의 API와 Worker를 순서대로 기동하고 기능·배치 처리·품질 상태를 확인한다. 이때 구 앱은 기동하지 않는다.

실제 예보 입력의 별도 스냅샷은 만들지 않는다. 평가 근거와 기존 원 데이터의 보존을 이 결정과 혼동하지 않는다. 식별 정보만으로 과거 확률을 정확히 재현하는 기능은 완료 조건이 아니다.

### 4.2 기존 DB 자원의 보존

S3 이관 Java 코드 삭제는 이미 반입한 관측·출처·감사 기록과 적용 이력의 삭제를 뜻하지 않는다. 과거 모델·통계 제외 의미는 model_training_exclusion과 statistics_training_exclusion으로 이전한다. V18은 학습 view를 새 정의로 바꾸고 refresh_trip_quality_training_views 함수를 제거한다. 기존 historical history와 앱 history는 합치거나 중복 적용하지 않는다.

온라인 통계는 PR #70처럼 품질 조건을 통과한 원본 평가 자료를 사용한다. 편도 근거 없는 historical seed 합계는 재도입하지 않는다. 새 DB 설치와 기존 DB 전환에서도 같은 학습 제외 조건이 성립해야 한다.

## 5. 기동과 실패 시 복구

API → Worker는 DB 전환이 끝난 뒤 같은 새 릴리스를 기동하는 순서다. 구 API·신 Worker 또는 신 API·구 Worker 조합을 운영하는 호환 계층은 만들지 않는다. legacy marker와 새 발행을 이중으로 쓰거나 UNION fallback으로 섞어 읽는 경로도 추가하지 않는다.

전환 중 검증이 실패하면 새 쓰기를 시작하지 않는다. 부분 적용된 DB를 그대로 둔 채 구 앱만 실행하지 않고, 전환 전 백업과 대응 앱 릴리스를 한 단위로 복구한다. 새 앱 기동 이후 복구가 필요하면 먼저 모든 쓰기를 중지하고 추가 기록의 처리 범위를 확인한 뒤 준비한 복구 절차를 따른다.

실제 JAR 검증에는 API·Worker의 scan 범위, 수집과 스케줄 기동 조건, Flyway 적용 순서, DB 연결과 health 검사를 포함한다. 모듈 추가에 따른 sourceDigest 누락으로 옛 JAR가 재사용되지 않는지도 확인한다. 운영 DB 전환과 배포는 구현 완료와 별도로 실행·검증한다.

## 6. maintenance-app과 일회성 코드 제거

기존 migration-tool의 Java 49개 중 이관 전용 38개는 삭제한다. 품질 업무 구현 1개는 forecasting에 옮기고 CLI 지원 10개는 maintenance-app에서 역할에 맞게 재구성한다. 파일별 근거는 [전체 클래스 배치표](03-class-map.md)에 보존한다.

- 삭제 대상 기능은 S3 목록 수집·archive 생성/검증·반입·대조·이관 롤백, seed 적재/검증, 임시 모델 교체다. 관련 전용 테스트·fixture·설정·SDK 의존도 소비자를 확인해 제거한다.
- 남는 기능은 품질 preview·처리 재개·상태 조회다. CLI는 명령을 typed command로 변환하고 forecasting 공개 유스케이스의 typed result를 출력한다. 구체 JDBC 저장소를 직접 생성하지 않는다.
- 한 chunk의 트랜잭션은 Spring이 관리하는 forecasting 유스케이스가 책임진다. CLI의 반복 전체를 하나의 TX로 감싸지 않는다. Worker와 CLI는 같은 품질 guard와 진행 상태를 사용한다.
- maintenance-app은 `AnnotationConfigApplicationContext`에 필요한 품질·관측 입력·DB·트랜잭션 구성만 등록한다. Boot 자동 구성·스케줄러·모델 적재·Flyway를 실행하지 않는다. 별도 DB 스키마 사전 안내 기능은 없으며 스키마 불일치는 실제 조회·처리 오류로 종료된다.
- preview는 최근 32개 배치의 표본이다. 처리 명령은 호출당 1~100개 배치 발견과 제한된 차량 조사로 진행하며 고정한 until·연결 간격을 바꾸지 않는다. `completed=false`를 항상 즉시 처리할 자료가 더 있다는 뜻으로 해석하지 않는다.
- 일회성 DDD 전환 코드는 상시 품질 CLI와 분리한다. 이미 끝난 S3 도구의 plan hash나 archive 구조를 범용 운영 기반으로 유지하지 않는다.

| 모델 검증 | 구조·계수·특징 순서·golden 출력, 전체 모델 식별 정보 | 선언된 feature 계약 버전의 의미 일치까지 검증한다고 오인 |
| API | 원 관측의 최대 3대 선정, target+sourceRow 연결, AVAILABLE의 확률 0과 UNAVAILABLE, 품질 필터 후 모델 선택, 최신 실패·5분 경계 | 차량 소실·예보 부재와 0% 혼동·표시 모델 변경 |
| 품질 조사 | start/restart·차량별 첫 이상 선택, completed 보존, 정상 관측 추가 SQL 0건, 관측/조사 동시 롤백, 70/71·10분·32배치 경계와 재개 | 정상 수집 부하·조사 소실·문제 편도 앞부분 누락·잘못된 보류 해제 |
| 품질 전환 | 품질 변경 뒤 보정·통계·학습 재사용 차단, 불변 근거의 사후 제외, DB view와 모델 상한 일치, 전환 후 모든 쓰기 경로의 같은 guard 사용 | 제외 자료 부활·잠금 보호 소실·분류와 계산 기준 불일치 |
| 정비 | 같은 작업 재개, lock/statement timeout, 수집 유지+예보 중지 시 품질 writer 상태, historical 설치 순서 | 중복·누락·품질 쓰기 중 이관·학습 필터 누락 |
| 오프라인 전환·복구 | 복사 DB의 전체 이관·행과 값 대조·참조 검사·백업 복구, 실제 JAR | 원 데이터 손실·잘못된 앱/DB 조합으로 기동 |
| 배포 | 신규 모듈만 변경해 digest/JAR 달라짐, scan 범위·Flyway·CLI gate | 새 코드 미배포·기동 실패 |
| 자원 | 배치별 TX/lock 시간·정산 처리량·조회 계획 | 작은 DB pool·메모리·저장량 초과 |

기존 테스트의 기대값은 새 구현에 맞춰 일괄 변경하지 않는다. 계약을 의도적으로 변경한다면 변경 이유와 이전·이후 기대값을 별도로 제시한다. 기능 보존은 테스트 개수뿐 아니라 검증하는 계약과 결과를 기준으로 확인한다.

## 8. 설계 검토 범위와 남은 확인

이 문서의 검토 범위는 업무 경계, 객체 책임, 전체 코드 배치 후보, 데이터 소유권, 트랜잭션·경쟁 처리, API 보존 계약, 스키마 이관·배포·롤백 계획이다. 각 항목의 설계안 작성과 교차 검토를 마쳤다.

2026-09-23에는 PR #70의 최종 머지 코드·SQL·관련 테스트를 읽고 위 계획을 갱신했다. PR 작성자의 빌드 보고와 이 문서 검토에서 직접 실행한 검증은 구분한다. 이번 재검토에서 애플리케이션 build/test나 운영 DB 정비를 실행하지는 않았다.

구현 착수 전 기준 코드의 1158개 테스트가 통과했다. 이후 재설계 코드의 build/test, 오프라인 전환 리허설, 운영 부하 측정과 실제 배포 결과는 [진행 기록](implementation-progress.md)에서 별도로 갱신한다. 기준선 통과를 새 구현의 통과로 취급하지 않는다.

## 9. 제공되는 전환 실행기와 남은 운영 확인

[전환 실행기](../../../backend/deploy/migrations/SAL-134/README.md)는 `inspect → prepare → backfill → verify → finalize` 명령을 제공한다. prepare는 V17까지 적용하고 finalize는 검증을 거쳐 V18로 전환한다. advisory lock, 백업 ID 대조, 원 데이터의 양방향 비교와 V18 savepoint 미리보기를 사용한다.

`--writers-stopped`와 `--backup-id`는 운영자의 확인을 기록하는 인자다. 실행기가 모든 프로세스를 종료하거나 실제 백업의 복원 가능성을 자동 검증하는 것은 아니다. 앱 정지·백업·복구 확인은 운영 절차에서 수행한다. 운영 전환 완료 여부는 이 문서의 명령 존재 여부가 아니라 실행 기록으로 판단한다.

현재 발행·평가의 `@Transactional`은 격리 수준을 따로 지정하지 않는다. 품질 guard와 원 관측 batch 잠금, 같은 TX에서의 저장으로 일관성을 보호한다. 통계 input_checkpoint는 NULL로 저장되므로 체크포인트만으로 중복 산출을 제거하는 기능은 검증 항목에 포함하지 않는다.
