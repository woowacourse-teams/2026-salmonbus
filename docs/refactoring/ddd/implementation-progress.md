# 구현 범위와 검증 기록

기준 소스는 `9f9c75db16fcdefc0944f0c6a40fa7c09e4e1d94`다. 이 문서는 승인된 범위와 실제 완료한 검증을 구분한다. 문서에 목표 이름을 반영한 것을 코드 구현 완료로 표시하지 않는다.

## 승인된 구현 범위

- 백엔드 전체 업무 모델·코드 구조·저장 구조를 재설계한다. 프론트엔드는 수정하지 않는다.
- 3개 경계 컨텍스트, 같은 PostgreSQL, [용어집](glossary.md)의 9개 Gradle 모듈을 사용한다.
- 완료된 S3 이관 전용 Java 38개와 해당 기능 전용 테스트·설정·의존을 제거한다. 기존 DB 데이터와 적용 이력은 보존한다.
- 품질 업무 구현은 forecasting, 명령 실행은 maintenance-app이 담당한다. 일회성 DDD 전환 작업은 `backend/deploy/migrations/<change-id>`에서 별도로 관리한다.
- 운영 전환은 수집·예보·평가·통계·품질 조사와 정비 CLI의 쓰기를 중지한 상태에서 일괄 수행한다. 이중 쓰기, 구·신 앱 혼합 운영, 앱별 독립 롤백은 구현 범위에 넣지 않는다.
- 실제 예보 입력·특징 벡터·보정값의 별도 저장은 제외한다. 발행 식별 정보와 기존 원 데이터, 평가 근거는 보존한다.
- 모델 레지스트리와 활성화 요청은 전체 모델 식별 정보, 요청 식별자, 요청이 전제한 활성 버전을 사용한다.
- 변경 이유와 의존 관계를 따라 검토할 수 있도록 작업 단위별로 커밋한다. 커밋·스테이징 여부는 실제 실행 기록으로 별도 남긴다.

## 운영 전환의 완료 조건

정비 중에는 구·신 앱을 섞어 기동하지 않는다. DB 전환과 데이터 대조를 마친 뒤 새 API와 새 Worker를 차례로 기동한다. API → Worker는 같은 새 릴리스의 기동 순서이며 구 Worker와의 호환 운영을 뜻하지 않는다.

실패하면 일부 앱만 이전 버전으로 돌리지 않는다. 전환 전 DB 백업과 대응하는 앱 릴리스를 한 단위로 복구한다. 백업 생성·복구 절차와 검증 결과가 준비되기 전에는 운영 전환을 완료한 것으로 표시하지 않는다.
