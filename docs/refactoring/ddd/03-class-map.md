# 기준 소스의 이동·삭제 계획과 현재 구현 연결

기준: PR #70(SAL-133) 병합 커밋 `9f9c75d`, 2026-09-23. [설계안](00-design.md)에 따라 기존 클래스의 위치와 책임을 정리한 **설계 배정**이다. 완료된 S3→RDS 일회성 이관 코드는 삭제 대상으로, 현재 품질 정비에 필요한 코드는 유지 대상으로 구분했다. 의존 규칙에 맞추려면 책임을 나눠야 하는 클래스도 표시했다. 1~5절은 기준 소스 330개의 이동·삭제를 검토한 기록이다. 당시 후보 이름과 분해 계획을 보존하며 최종 파일 목록으로 취급하지 않는다. 6절은 이 브랜치의 src/main 코드에서 다시 확인한 모듈 집계와 주요 연결이다. 검증 결과는 [진행 기록](implementation-progress.md), 현재 구현 이름은 [용어집](glossary.md)에서 확인한다.

클래스를 옮기는 이유는 설계안의 개념별 설명에서 확인할 수 있다. 업무 영역은 경계 컨텍스트, 상태와 값의 구분은 엔티티·값 객체, 계산과 실행 순서의 분리는 도메인 서비스·응용 서비스로 설명했다. 아래 배정은 그 책임 구분을 코드 위치에 반영한 결과이며, 패키지 이동만으로 도메인 설계가 끝난다는 뜻은 아니다.

집계 범위는 `backend/*/src/main/java/**/*.java`다. 실제 파일 수는 api-app 97, worker-app 182, migration-tool 49, common 2로 총 **330개**다. PR #70에서 최초 기준 `6f70826`보다 13개 늘었으며 그 사이 삭제된 파일은 없다. 아래의 삭제 표시는 이번 재설계의 목표다. 중첩 record·enum은 별도 파일로 세지 않았으며 test·testFixtures·generated·SQL·YAML은 집계에서 제외했다.

## 1. 집계와 표 읽는 법

각 기존 파일을 한 행씩 정리했다. **주 배정 모듈**은 그 파일의 주요 책임을 맡을 모듈이다. 아래 수치는 기존 파일의 배정과 삭제 대상을 나타내며, 책임을 나누면서 다른 모듈에 추가될 코드는 비고와 §4에 적었다. 분해 후의 최종 파일 수는 이 표에 포함하지 않았다. `business`·`integrations`는 디렉터리를 묶는 용도로만 사용하고 실제 Gradle 프로젝트는 아래 9개로 구성한다. 기존 330개 중 292개를 재배정하고 일회성 이관 코드 38개를 삭제한다.

API 97개는 전용 읽기 모델을 유지한다. api-app은 `common`과 공개 DB projection query 계약을 사용하며 **쓰기 업무 모듈 JAR에 의존하지 않는다**. 같은 테이블을 읽더라도 API JPA 투영과 업무 쓰기 JPA 엔티티는 각자의 책임에 맞게 유지한다.

`RouteStop`, `RouteStops`, `RouteVersionRepository`, `ObservedVehicle`, `SeatUnknownReason`, `ObservationBatchJpaEntity`는 이름이 같아도 소속 모델에 따라 의미가 다르다. 각 모델에 따로 두고 경계 mapper에서 필요한 값만 변환한다. common으로 통합하지 않는다.

### 운영 정비 도구 — 기존 `migration-tool` 49개 중 품질 업무 1개·CLI 지원 10개 재구성·38개 삭제

유지할 책임은 품질 정비 3개 명령의 의존 경로를 기준으로 골랐다. 품질 업무 구현 1개는 forecasting으로 옮기고 CLI 지원 10개는 maintenance-app에서 재구성한다. CLI 지원 파일에는 이관 전용 기능과 정비에 필요한 기능이 함께 있어 파일 전체가 아니라 이관 부분만 제거한다. `삭제`는 Java 코드의 제거 대상이다. 이미 반입된 관측, seed·감사 기록, historical SQL 자원·적용 이력과 학습용 DB view를 함께 삭제한다는 뜻은 아니다. 해당 DB 자원의 소유권·설치 경로·남은 소비자는 별도로 확인한다.

## 3. 책임을 나눠야 하는 경계

1. **GBIS**: DTO만 담는 `GbisLocationResult`는 gbis-client에 둔다. `UpstreamRoute`를 담는 `GbisRouteResult`는 catalog의 SourceResult와 외부 raw 결과로 나눈다. `GbisRouteSource`에서는 HTTP·JSON 처리를 gbis-client로 옮기고, 노선의 의미를 해석하는 코드는 catalog adapter에 둔다. gbis-client는 업무 모듈을 역참조하지 않는다.
2. **호출 한도와 수집 주기**: `CallQuotaLedger`의 `GbisProperties` 의존을 제거한다. Worker가 설정을 바인딩한 뒤 연결·인증값과 BudgetPolicy를 나눠 주입한다. 순수 계산인 `CollectionPhase`·`CollectionSchedule`은 observations가 소유한다. 기동 시 호출 한도를 검증할 때는 공개 schedule·호출량 계약값을 사용하므로 budget은 observations 내부 스케줄을 import하지 않는다.
3. **진입과 업무**: `*Job`, `CollectionScheduler`, `AdaptiveCollectionTrigger`, `BundleStartupLoader`는 스케줄·기동 부분만 Worker에 남긴다. 발행·평가·통계·모델 준비는 forecasting.application으로 추출한다. 표에서는 진입 책임을 기준으로 Worker에 배정했으며, 업무 흐름을 담은 본문은 분리 대상이다.
4. **노선·관측 읽기**: processor의 `JdbcArrivalObservationRepository`·`JdbcVehicleTrajectoryRepository`·`JdbcRouteVersionRepository`는 공개 조회를 받아 쓰는 adapter 역할에 따라 forecasting에 배정했다. 원 SQL에서 데이터를 읽는 책임은 각 owner의 공개 조회 구현으로 옮기고, forecasting에는 내부 계산형으로 변환하는 mapper를 둔다.
5. **순수 계산**: 기존 12종은 별도 라이브러리 없이 forecasting.domain의 `evaluation`·`statistics`·`sharedvalue` 패키지에 둔다. 평가 5종, 통계 4종, 내부 공유값 3종으로 나누되 모두 앱·JPA·스케줄러에 의존하지 않는다. `StopDemandStatisticsJob.CURRENT_CALCULATION_VERSION`은 forecasting 내부의 신규 `DemandCalculationVersion`으로 추출하며, 기존 파일 수에 더하지 않는다. 일회성 seed 재생이 제거되므로 이 계산을 CLI와 공유하기 위한 별도 모듈은 필요하지 않다.
6. **번들**: ModelBundleProperties와 기동 hook은 Worker에 둔다. codec·파일 읽기는 forecasting.infrastructure.bundle, 순수 모델은 forecasting.domain이 맡는다. 파일 표현이 domain에 노출되지 않도록 LoadedBundle 변환을 분리한다.
7. **운영 정비**: 기존 migration-tool의 이관 전용 38개는 삭제한다. `TripQualityMaintenance`의 업무 흐름과 SQL은 forecasting으로 옮기고 CLI 지원 10개는 maintenance-app에서 재구성한다. 유지할 품질 preview·처리 재개·상태 조회는 typed command/result로 연결한다. 한 chunk의 TX와 품질 guard는 forecasting 유스케이스가 책임진다. CLI는 필요한 빈만 등록하고 스케줄러·Flyway 자동 실행을 제외하며, 일회성 전환 코드는 `backend/deploy/migrations/<change-id>`에서 별도로 관리한다.
8. **품질**: `VehicleObservationsStored`는 observations.api에 둔다. forecasting의 동기 수신은 관측 저장과 같은 TX에서 조사 요청을 남긴다. 편도 판정·역방향 탐색은 순수 계산, 조사 cursor·chunk·잠금은 응용 흐름과 저장 구현으로 나눈다. 원 관측 조회는 observations가, 자료를 예보·평가·보정·학습에 사용할 수 있는지 판단하는 규칙은 forecasting이 책임진다. 원 관측 보존과 품질 판정 이후의 제외를 함께 유지한다.

## 5. 배치표 검증

PR #70 병합 커밋의 production Java 목록과 대조해 330개 파일이 중복 없이 모두 포함되어 있는지 확인했다. 추가된 13개도 각 파일의 기존 위치와 목표 책임을 기록했다. 각 파일은 9개 모듈 중 하나 또는 삭제 대상으로 배정했다. forecasting은 기존 배정 104개와 품질 업무 구현 1개를 합한 105개다. migration-tool 49개는 forecasting으로 옮길 1개, maintenance-app에서 재구성할 CLI 지원 10개, 삭제 38개로 나눴다. 링크는 같은 커밋의 소스 경로와 대조했다. 이번 검토는 배치표의 누락과 연결 경로를 확인한 범위까지다. 구현 착수 전 9f 기준 1158개 테스트가 통과했으며 재설계 후 검증은 별도다. 이 표의 330개는 기준 소스의 계획 검토 수치다. 현재 파일 수와 주요 연결은 아래에서 별도로 대조했다.

노선·관측 이력은 forecasting의 JDBC 조회 어댑터가 공유 DB의 테이블·view를 읽는다. 모든 읽기를 Java 공개 API 호출로 바꾼 구조는 아니다. 입력 잠금·확정과 수집 저장의 품질 연동은 공개 인터페이스를 사용한다. API 앱은 common 외의 업무 모듈을 runtime 의존에 넣지 않고 별도의 조회 모델을 유지한다.

이 절은 소스의 이름·경로·연결을 확인한 결과다. 전체 테스트와 JAR·배포 검증의 최종 결과는 진행 기록에서 관리하며 운영 DB 전환 완료를 뜻하지 않는다.

이번 책임 보완에서는 application의 CollectionResponseMapper를 제거하고 GBIS 조회·변환을 infrastructure로 옮겼다. 새 ObservationSource·ObservationResponse·StoredObservations와 ForecastEvaluationWriter는 현재 집계에 포함한다. 기준 330개 이동·삭제 기록은 이 추가 변경과 구분해 유지한다.
