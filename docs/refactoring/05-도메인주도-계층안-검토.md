# 05. 도메인 주도 계층안(D안) 검토

팀 논의에서 나온 제안은 "수집·처리·api 세 컨텍스트는 그대로 두고, 그 아래를 도메인 주도 방식으로 나누자"다. 04 의 A·B·C안과 같은 방법(클래스 의존 그래프를 후보 배정으로 접어 방향·순환·위반을 셈)으로 검토했다. 결론은 §7 에 있고, 04 제안서의 추천안은 이 결과로 갱신했다.

경로에서 `src/main/java/com/gustler/backend/` 는 `…/` 로 줄였다.

## 1. 제안을 둘로 나눠 읽는다

"도메인 주도 방식"은 두 가지를 뜻할 수 있다.

| | 뜻 | 성격 | 이 문서 |
| --- | --- | --- | --- |
| (가) 계층 구조 | 컨텍스트 → 계층(domain · application · infrastructure · config) → 도메인 개념 | 패키지 문제. 이동만으로 되고 동작이 안 바뀐다 | 실측해서 트리·비용·규칙을 냈다(§3~§5) |
| (나) 전술 패턴 | 애그리거트, 행동을 가진 엔티티, 애그리거트당 리포지토리, 도메인 이벤트 | 모델 문제. 트랜잭션 경계와 SQL 에 닿는다 | 어디에 맞고 안 맞는지만 판정했다(§6) |

(가)는 2단계에서 할 수 있다. (나)는 자리마다 다르고 일괄 도입은 지금 설계와 부딪히는 곳이 있다.

## 2. 우리 코드를 DDD 용어로 읽으면

| DDD 용어 | 우리 코드 | 비고 |
| --- | --- | --- |
| 경계 컨텍스트 | `collector`, `processor`, `api`(+ `migration`) | 모듈·패키지로 이미 갈라져 있고 서로 못 부른다 |
| 유비쿼터스 언어 | javadoc·로그의 판, 자리, 장부, 회수, 세대, 신원 | 코드 이름(`reserve`, `conclude`, `settle`, `revision`)과 짝이 맞는다 |
| 값 객체 | record 238개 선언, compact 생성자 검증 | 03 §9 |
| 도메인 서비스 | `ArrivalLabelResolver`, `StopDemandAggregator`, `VehicleTrajectoryAssembler`, `SeatForecastDesignMatrix`, `ObservationBatchConclusion.from` | javadoc 이 "DB 를 안 탄다"고 표시한 순수 계산. Spring 애노테이션 없음 |
| 응용 서비스 | `*Job`, `*Ledger`, `*Loader`, `ObservationCollector`, `ForecastBatchWriter`, `SameDayFullOutcomesService` | `@Component`·`@Transactional` 이 여기에만 있다 |
| 리포지토리(포트) | 인터페이스 19개 | 03 §2 |
| 인프라 | `persistence.jpa`·`persistence.jdbc`, `Gbis*` 클라이언트, `seatdistribution`(계수 파일 적재) | |
| 부패 방지 계층 | `collector.dto`(GBIS JSON 형) + `VehicleObservation.from(BusLocation)`·`CollectedObservations.from` | 상류 값이 우리 값으로 바뀌는 자리 |
| 애그리거트 | 이름은 없다. 트랜잭션 경계로 보면 관측 판(판+행), 노선 판본(판본+정류장), 셀 통계 한 세대 | §6 |
| 도메인 이벤트 | 없음 | 03 §6 |
| 조회 측 | api-app 전체(읽기 전용 투영) | DDD 의 CQRS 조회 측은 도메인 모델을 요구하지 않는다 |

도메인 계층에 들어갈 후보 92개 클래스(collector 36, processor 56)를 세었더니 `org.springframework`·`jakarta.persistence`·`lombok` import 가 0 이다. Jackson 애노테이션이 붙은 GBIS DTO 4개만 걸린다. 계층이 이름만 없을 뿐 실체는 이미 갈라져 있다는 뜻이다.

api-app 은 이미 이 계층이다. 이름만 다르다.

| DDD 계층 | api-app 패키지 | 파일 |
| --- | --- | --- |
| presentation | `*/controller`, `*/dto`, `http`(핸들러·valve·필터) | 15 + 11 |
| application | `*/application` | 18 |
| domain | `*/domain`, 기능 루트(`RouteId`, 예외 4개) | 21 |
| infrastructure | `*/persistence/jpa` | 26 |

migration-tool 은 계층으로 나누지 않는다. 절차 스크립트 성격이라 A안 범위(순환 해소)만 한다.

## 4. 실측 — 계층 간선과 위반

허용 방향은 presentation → application → domain, infrastructure → domain(포트 구현), config → 모두(배선), application → config(설정값 읽기)로 두었다. 이 배정으로 worker-app·api-app 의 클래스 의존 그래프를 접었다.

허용 방향 안의 간선(요지): collector application → domain 26, infrastructure → domain 41, config → application 3, application → config 2. processor application → domain 38, infrastructure.persistence → domain 37, infrastructure.model → domain 21, config → infrastructure.model 3. api presentation → application 8·domain 18, application → domain 35, infrastructure → application(포트·읽기 모델) 10·domain 16.

위반은 다섯 가지이고 전부 이동으로 풀린다.

| # | 위반 | 간선 | 고치는 법 | 비용 | 동작 |
| --- | --- | --- | --- | --- | --- |
| V1 | api domain → http | 8 | 기능 루트 예외 4개가 `ApiException`·`ErrorCode` 를 상속한다. `http` 를 둘로 나눈다. `api.error`(`ApiException`, `ErrorCode`, `ErrorResponse`, `ServiceUnavailableException`)와 `api.http`(핸들러, valve, 필터, `RequestId`, `ErrorHeaders`, 설정). domain → error 를 허용 | 이동 4, import 수정 약 12 | 없음 |
| V2 | api infrastructure → http 3, application → http 1 | 4 | `ServiceUnavailableException` 이 `api.error` 로 가면 규칙상 통과. 어댑터가 응답 정책을 아는 문제 자체는 G7 그대로 | 0 | 없음 |
| V3 | collector application → infrastructure.gbis | 2 | `ObservationCollector` → `GbisLocationSource`, `RouteCatalogLoader` → `GbisRouteSource` 가 구체 클래스를 본다. 상류 호출 포트 `LocationSource`·`RouteSource` 인터페이스를 `domain.gbis` 에 뽑고 application 이 그것을 본다. 다른 포트와 같은 아웃바운드 포트이고, 설계 문서의 `RealtimeObservationSource`·`RouteReferenceSource` 를 되살리는 것이다. 테스트는 `@MockitoBean GbisLocationSource` 와 직접 생성이라 그대로 돈다 | 신규 2, 수정 4 | 없음 |
| V4 | processor domain.deployment → infrastructure.model | 1 | `SupportedForecastScope.digest()` 의 `Sha256`. common 으로(B안과 같음) | 이동 1 | 없음 |
| V5 | infrastructure → application 상수 | 2 | `ObservationBatchJpaEntity` → `CollectionSchedule.CURRENT_STRATEGY_VERSION`, `JdbcStopDemandStatisticsRepository` → `StopDemandStatisticsJob.CURRENT_CALCULATION_VERSION`. `CollectionSchedule` 은 순수 계산이라 domain.schedule 로, 계산 규칙 판 상수는 domain.demand 로 | 이동 1, 수정 4(migration-tool 2 포함) | 없음 |

배정하면서 잡은 함정 하나. GBIS DTO 4개를 결과형과 같은 `domain.gbis` 에 넣으면 `upstream → gbis`(`VehicleObservation.from(BusLocation)`) 와 `gbis → upstream`(`GbisRouteResult` 가 `UpstreamRoute` 를 든다) 이 맞물려 순환이 된다. DTO 를 `domain.gbis.dto` 로 따로 두면 gbis → upstream, gbis → dto, upstream → dto 한 방향이다. 지금처럼 별도 패키지를 유지한다.

도메인 개념 사이 방향(순환 없음). collector: batch → gbis·upstream, route → upstream, gbis → upstream·dto, upstream → dto. processor: forecast → {demand, deployment, route, sameday, settlement, trajectory}, sameday → settlement, settlement → route·trajectory, route → trajectory, demand → route, deployment → route.

도메인 순수성. 위 배정의 domain 92개 중 Spring·JPA·Lombok import 0. Jackson 애노테이션은 `domain.gbis.dto` 4개뿐이다. 이 DTO 는 상류의 공개 형식이라 domain 에 두되 순수성 규칙에서 `com.fasterxml.jackson.annotation` 만 예외로 둔다(G12). 변환을 클라이언트 쪽으로 옮겨 `GbisLocationResult.Success` 가 `VehicleObservation` 을 들게 하는 길도 있지만 테스트 7개의 검증 자리가 옮겨가므로 2단계 범위 밖으로 둔다.

## 5. D안에서 켤 수 있는 ArchUnit 규칙

B안의 슬라이스 순환 규칙에 둘이 더 붙는다.

```java
// 계층 방향 (컨텍스트마다 하나씩)
layeredArchitecture().consideringOnlyDependenciesInLayers()
    .layer("domain").definedBy("com.gustler.backend.processor.domain..")
    .layer("application").definedBy("com.gustler.backend.processor.application..")
    .layer("infrastructure").definedBy("com.gustler.backend.processor.infrastructure..")
    .layer("config").definedBy("com.gustler.backend.processor.config..")
    .whereLayer("domain").mayOnlyBeAccessedByLayers("application", "infrastructure", "config")
    .whereLayer("application").mayOnlyBeAccessedByLayers("config")
    .whereLayer("infrastructure").mayOnlyBeAccessedByLayers("config");

// 도메인 순수성 (worker-app 만, G11)
noClasses().that().resideInAPackage("..domain..")
    .should().dependOnClassesThat().resideInAnyPackage(
        "org.springframework..", "jakarta.persistence..", "lombok..");

// 도메인 개념 사이 순환 금지
slices().matching("com.gustler.backend.(*).domain.(*)..").should().beFreeOfCycles();
```

세 규칙 모두 §4 의 V1~V5 를 고친 직후 통과한다. api-app 은 계층 규칙만 걸고 순수성 규칙은 안 건다. `ErrorCode` 가 `HttpStatus` 를 알고 api 의 도메인 예외가 그것을 상속하기 때문이다. api-app 은 조회 측이라 도메인이 얇고, 이 의존을 끊으려면 `ErrorCode` 를 둘로 가르는 리팩토링이 하나 더 필요하다(G11).

## 6. 전술 패턴은 어디에 맞나

| 후보 애그리거트 | 지금 트랜잭션 경계 | 판정 |
| --- | --- | --- |
| 관측 판(`observation_batch` + `vehicle_observation`) | `JpaObservationRepository.concludeWithRows` 가 판과 행을 함께 저장하고, `ObservationBatchJpaEntity` 가 `markDispatching`·`conclude`·`reopen` 을 가진다 | 이미 애그리거트 모양이다. 다만 장부 단계가 `REQUIRES_NEW` 로 나뉘어 "한 애그리거트 = 한 트랜잭션"과 일부러 다르다(죽은 프로세스가 남길 수 없는 기록). 원칙에 맞추면 설계가 깨진다 |
| 노선 판본(`route_version` + `route_stop`) | `RouteVersionLoader.load` 가 `TransactionTemplate` 한 블록 | 애그리거트로 부를 수 있다. 엔티티 행동은 없고 값 + 포트로 충분하다 |
| 하루 호출 한도(`daily_call_quota`) | SQL 한 문장의 원자 갱신 | 팀이 JPA 를 거부한 자리("flush 시점이 흐려지면 한도가 흐려진다"). 값 객체 + 포트 유지 |
| 셀 통계 한 세대(`stop_demand_statistics` revision) | 어댑터 `append` 가 한 세대를 한 트랜잭션으로 | 집합 쓰기. 루트 객체는 이미 `StopDemandGeneration` record |
| 예보(`seat_forecast`) | batch 단위로 쓰고(`ForecastBatchWriter`) 행 단위로 회수한다(`ArrivalLabelJob` → `settle`) | 경계가 둘이라 애그리거트 하나로 못 잡는다. `UPSERT`·`LIMIT` 집합 처리가 맞는 자리 |
| 모델 배포(`model_deployment`) | `LOCK TABLE` + 문장 둘 | 상태기계가 SQL 에 있다. 엔티티 행동으로 옮길 이유가 없다 |
| api 조회 | 읽기 전용 | 조회 측. 투영 record 유지 |

정리하면 collector 의 두 애그리거트(관측 판, 노선 판본)는 이름만 붙이면 되고, processor 는 집합 처리 파이프라인이라 애그리거트·엔티티 행동을 강제하면 `JdbcClient` SQL 설계와 부딪힌다. 도메인 이벤트는 03 §6 의 판정 그대로다. 그래서 D안 채택은 계층(가)까지이고, 전술 패턴(나)은 새 기능을 만들 때 자리마다 판단한다(G14).

## 7. B안과 비교, 결론

| | B안 기능별 하위 패키지 | D안 컨텍스트 → 계층 → 개념 |
| --- | --- | --- |
| 개념 분할 | 14개 | 같은 14개를 `domain` 아래에 |
| 계층 | 없음(개념 패키지 안에 잡·값·포트 혼재) | domain · application · infrastructure · config |
| main 이동(worker) | 113 | 175 (`persistence`·`seatdistribution` 을 `infrastructure` 아래로 옮기는 것 포함. 안 옮기면 154) |
| test 이동(worker) | 52 | 84 (안 옮기면 76) |
| 그 밖 | – | api `error` 분리 4, 상류 호출 포트 2 신설, 상수 이동 2 |
| 새 패키지 | 14 | 24 |
| ArchUnit | 슬라이스 순환 | 슬라이스 순환 + 계층 방향 + 도메인 순수성 |
| api-app 과 모양 | 다름 | 같음(이름 대응표, G13) |
| 위반 수정 | 1(Sha256) | 5(전부 이동, 동작 변경 없음) |
| 팀 익숙함 | 낮음(이름을 새로 정함) | 높음(팀 제안, 크루 관례) |
| 위험 | 없음 | 전술 패턴까지 밀어붙이면 processor 설계와 충돌. 계층까지로 선을 긋는다 |

결론. D안을 추천안으로 갱신한다. 근거는 셋이다. 도메인 계층이 실측으로 이미 순수하고(92개 중 Spring 0), 위반 5건이 전부 이동으로 풀리며, api-app 과 같은 모양이 되어 백엔드 전체가 한 어휘를 쓴다. B안은 D안의 `domain` 부분과 같으므로, 이동 규모가 부담이면 B안으로 후퇴해도 개념 분할은 그대로 남는다. 계층 이름은 크루 관례에 따라 `domain`·`application`·`infrastructure`·`config` 를 제안한다.

## 8. 참고 — 카카오페이 여신코어 DDD 글과의 대조

팀 논의의 참고 글은 카카오페이 기술 블로그 「백엔드 도메인 주도 설계」(여신코어 gaia)다. 뼈대는 D안·재설계안과 같고 세 군데가 다르다.

| 항목 | 카카오페이 | 이 제안 | 같은가 |
| --- | --- | --- | --- |

Java 에는 Kotlin `internal` 이 없다. 그 글이 모듈 경계로 막은 것을 여기서는 `infrastructure.persistence.jpa` 안의 package-private 과 ArchUnit 규칙 D1·D2 로 막는다. 모듈을 도메인마다 쪼개면(재설계 C안 계열) 모듈이 4개에서 9개가 되고, collector 와 processor 가 서로의 형을 모른다는 지금 경계가 "앱이 여러 도메인 모듈을 조합한다"는 그 글의 모양으로 바뀐다. 그 전환은 값보다 비용이 크다고 본다(04 §2-3).
