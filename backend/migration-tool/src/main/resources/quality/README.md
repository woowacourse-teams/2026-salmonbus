# SAL-133 편도 판정과 과거 자료 정리

현재 구현: [2026-09-22 변경 이력](../../../../../history/2026-09-22-SAL-133.md). 운영 DB에는 접속하거나 적용하지 않았다.

## 평소와 이상 발견 시의 차이

- 정상 수집은 이미 저장한 관측의 좌석값만 메모리에서 확인한다. 추가 판정 SQL이나 관측 키 쓰기가 없다.
- 70 초과를 발견하면 해당 차량의 조사 요청을 원본과 같은 트랜잭션에 저장한다. 조사 중 해당 차량의 자료 사용을 보류한다.
- 기본 10초마다 한 차량, 최대 32묶음씩 시작점을 역으로 찾고 시간순으로 재판정한다. 정상 다음 편도를 확인하고 조사가 최신 자료까지 따라잡혀야 보류를 해제한다.
- 기점/회차지 출발(state=2), GBIS 순번에 따른 방향 전환을 새 편도 근거로 사용한다. 단말기 초기화 확인 기능은 아니다.
- 이상이 속한 편도와 조사 중 경계를 확인하지 못한 구간은 제외한다. 정상 차량은 사전 편도 판정 없이 사용한다. 39 증가 자체는 제외하지 않고, 현재 제품 상한은 70이다.
- 연속 관측 연결은 기본 10분까지 허용한다. 초과하면 이전 편도와 연결하지 않고 경계 미확인으로 보류한다. 출발/방향 전환이 확인되면 시간과 관계없이 새 편도로 구분한다. 노선별 `maximum_observation_gap_seconds`와 `observation_gap_evidence`가 있으면 해당 설정을 우선한다. 임시 10분의 근거와 한계는 변경 이력에 기록한다.

## 원본과 파생 자료

원본 좌석·위치·시각과 저장 예측은 삭제/보정하지 않는다. 조사 차량에만 기존 `vehicle_trip_key`를 저장하고 `vehicle_one_way_trip`에 편도 상태를 둔다. `trip_quality_rebuild`는 판본·차량당 진행 행 하나다. 빈 차량 ID는 수동 발견 작업을 뜻한다.

신규 V15의 품질 버전 기본값은 1이다. 이상 등록·조사 완료 시 같은 노선의 유효 버전을 올려 이전 보정·통계·학습 재사용을 막는다. 정상 차량의 기존 API 예보는 일괄 삭제하지 않는다. 통계는 유효한 원본 라벨로 다시 만들며 원본 근거가 없는 seed 합계는 복원하지 않는다. 외부 학습기의 view 사용, 기존 모델 재학습은 별도 작업이다.

## 과거 자료 정리

1. V14 다음 V15 적용 순서와 앱 호환을 확인한다. 이 브랜치의 V15는 미배포 상태에서 수정했으므로 이미 적용한 개발 DB의 checksum도 확인한다.
2. `quality-preview`는 **최근 32묶음 표본**의 묶음·관측·70 초과 수만 반환한다. 전체 이상 건수나 최종 제외 편도 수가 아니다.
3. `quality-rebuild`는 호출당 1~100묶음에서 이상 차량을 발견하고, 한 차량의 조사 페이지를 한 번 처리한다. 같은 판본·until·시간 정책으로 반복한다. 발견 중 해당 판본을 보류하며 다른 판본은 유지한다.
4. `quality-status`는 작은 조사 표의 상태와 진행 위치만 읽는다. `discoveryCompleted`는 지정 범위에서 이상을 찾는 작업의 완료이며, `completed`는 차량 조사까지 끝났다는 뜻이다. 다음 편도 근거가 없으면 조사는 대기한다.
5. 진행 중 범위/시간 정책 변경은 거부한다. 같은 완료 요청은 다시 처리하지 않는다. 종료 시 대형 관측 표의 키를 일괄 해제하지 않는다. 새 범위/정책으로 완료된 수동 발견 작업을 초기화하는 기능은 없다.
6. 통계는 기존 정기 작업(기본 6시간)으로 재생성한다. 즉시 재집계, 과거 예측 재발행, 모델 재학습은 별도 운영 작업이다.

명령 형태(운영 미실행):

```text
quality-preview --config <설정파일> --route-version <판본ID> --until <UTC시각>
quality-rebuild --config <설정파일> --route-version <판본ID> --until <같은UTC시각> --batch-limit 20
quality-status --config <설정파일> --route-version <판본ID>
```

기존 `target.kind`, `database.env-file` 설정과 운영 쓰기의 승인 영수증(`--approval`, action=`ACADEMY_TRIP_QUALITY_REBUILD`)을 유지한다. preview/status는 읽기 전용이다. CLI는 문장 500ms/잠금 100ms를 설정하며 오류 시 해당 호출을 롤백한다. 자동 조사에는 트랜잭션 2초 제한도 있다. 문장 제한은 호출 전체 CPU/메모리의 상한이 아니다. until은 수집이 끝난 범위를 사용하고 과거 원본을 동시에 적재하지 않는다.

## 검증 경계

격리 PostgreSQL에서 정상 SQL 0, 차량별 보류/복귀, 중단·롤백·재개, 잠금 시간 초과, API/저장소와 DDL을 검증했다. 실제 실행 JAR와 LOCAL 설정 파일로 preview/rebuild/status, 원본 보존, 반복 요청과 잘못된 요청의 상태 보존도 확인했다. 전체 Gradle build와 실제 Testcontainers 검증도 통과했으며, 최종 리포트는 1,139개 성공/실패·스킵 0이다. 세부 결과는 변경 이력에 기록한다. 운영 규모·동시 요청·운영 승인/권한과 실제 운영 적용은 별도 확인 대상이다.

## 시간 기준의 근거 수집

`travel-intervals.sql`은 원본 테이블만 읽으므로 V15 설치 전에도 조회할 수 있다. 노선 판본 하나·6시간부터 시작한다. `statement_timeout=15s`, `max_parallel_workers_per_gather=0`으로 조회하고 테이블/인덱스/임시 테이블을 만들지 않는다. 이 제한이 DB 자원 사용량을 보장하지는 않는다. 오류로 세션이 transaction 안에 남으면 `ROLLBACK;`으로 끝낸다.

1. 같은 차량의 연속 관측 간격을 시간대별로 확인한다. 한 정류장 평균 이동 시간을 최대 관측 간격으로 바로 쓰지 않는다.
2. 같은 회차지에서 순번 변화 없이 도착/출발 상태만 반복된 응답은 한 방문으로 센다. 조회 시작에 걸친 첫 방문은 출발 시각이 잘렸을 수 있어 제외한다.
3. A→B 출발 간격은 반대편 출발까지의 시간으로 종점 대기를 포함한다. A→B→A를 모두 관측한 경우만 왕복 후보로 집계한다. A→A만 보인 경우는 반대편 출발 누락 후보로 따로 센다.
4. 가장 짧은 왕복 후보 10건의 시각과 최대 관측 공백을 확인한다. 관측 최솟값을 물리적으로 가능한 최소 운행 시간이라고 단정하지 않는다. 시간 범위/날짜를 늘려 재확인한 뒤 제한값을 결정한다.
5. 정상 수집 간격은 충분히 허용하면서 왕복 소요시간보다 짧은 연결 제한을 검토한다. 시간대별 수집 주기 차이도 확인한다. 조건을 넘은 관측은 이전 편도와 연결하지 않는다.

psql에서 설정할 변수의 형식(아래 값은 예시):

```text
\set route_version_id 123
\set from_at '2026-09-21 08:00:00+09:00'
\set until_at '2026-09-21 14:00:00+09:00'
\i /path/to/travel-intervals.sql
```

현재 SQL은 검토/작성 단계이며 실제 운영 결과나 기준값을 확보했다는 의미는 아니다.
