# SAL-133 편도 판정과 과거 자료 정리

이 파일과 SQL은 실행 절차다. 운영 DB에서는 실행하지 않았다. 2026-09-21 후속 작업에서 일회용 로컬 PostgreSQL로 저장소와 재판정 로직을 검증했다.

## 무엇을 판정하는가

- `OneWayTripClassifier`가 원본 관측을 편도에 연결한다. 단말기 초기화 확인 기능은 아니다.
- 기점/회차지 출발(state=2)을 새 편도의 시작으로 삼는다. 반복된 출발 응답은 같은 편도다.
- GBIS의 정류소 순번과 회차 지점으로 방향 전환을 확인해도 새 편도로 구분한다. 출발/방향 전환을 먼저 확인하고 같은 편도의 연속 관측을 연결할 때만 설정된 시간 기준을 적용한다.
- 중간부터 보인 차량, 새 편도 경계 없이 설정된 연결 시간을 초과한 관측, 설명되지 않는 순번 역행은 `BOUNDARY_UNCONFIRMED`로 사용을 보류한다.
- 잔여석 70은 허용한다. 70 초과를 발견하면 연결된 편도 전체를 `EXCLUDED`로 바꾼다. 실제 좌석값이 틀렸다는 확정 판정이 아니라 현재 모델의 자료 사용 정책이다.
- `route_version.maximum_observation_gap_seconds`는 관측 두 개를 연결할 수 있는 최대 간격이다. 한 정거장 평균 이동 시간과 동일한 값이 아니다. 숨은 회차를 같은 편도로 연결하지 않을 근거를 실제 분포/운행 지식으로 확인해야 한다.
- 시간 정책이 없어도 출발/방향 전환/순번 진행으로 판정한다. 같은 회차지의 반복 출발은 기존 편도를 유지한다. 운영 시간 기본값은 넣지 않았다.
- 시간 정책이 없으면 공백의 길이만으로 연결을 끊지 않는다. 관측 사이에 전체 회차가 누락되고 같은 방향의 더 큰 순번으로 다시 나타나면 이전 편도와 잘못 연결할 수 있다. 방향 판단은 운행 횟수나 단말기 초기화의 증명이 아니다. 검토한 시간 정책은 이 누락 위험을 줄이는 추가 조건이다.

## 책임과 저장 구조

- worker `processor`: 순수 판정(`OneWayTripClassifier`)과 묶음 조회/저장(`TripQualityRepository`). `ForecastJob`이 모델 확인 전에 최근 품질 판정을 실행한다. 별도 품질 스케줄러는 없다.
- common V15: 새 테이블은 편도와 재판정 진행 상태 두 개다. 연결은 기존 `vehicle_trip_key`, 시간 정책은 `route_version`, 품질 버전은 `route`에 둔다. 원본 좌석/위치/시각은 유지하고 파생 편도 키만 갱신한다.
- worker `processor.ForecastBatchWriter`: 판정 후 노선 잠금을 얻어 일관된 상태의 통계·보정 자료로 계산한다. 판정은 별도 transaction으로 먼저 저장되어 일반 모델 오류가 이를 되돌리지 않는다.
- worker `processor`: 궤적·최대 좌석·실제 결과 연결·보정·통계 조회에서 사용 가능 관측을 선택한다. 앞차의 위치는 남기고 좌석만 모름으로 처리한다. 다른 차량을 앞차로 대체하지 않는다.
- `StopDemandStatisticsWriter`: 한 노선의 자료 조회부터 통계 저장까지 한 transaction. 제외 변경과 통계 저장이 섞이지 않게 같은 노선 잠금을 사용한다.
- API: 관측 차량 목록은 유지하고 제외/보류된 관측의 예보 행만 연결하지 않는다. `/vehicles`는 원본을 유지한다.
- migration-tool `TripQualityMaintenance`: 같은 판정기로 과거 자료를 처리하고 batch 커서부터 재개한다.

## 이후 계산과 기존 산출물

`quality_revision`은 계산 재료의 유효 상태를 표시한다. 기존 예측·통계 행은 0으로 남고 새 계산 상태는 1부터 시작한다.

사용하던 편도가 제외되면 같은 **노선(route)**의 버전을 올린다. 세부 입력 기여 기록이 없어 보수적으로 같은 노선의 이전 예측은 당일 보정/학습 재료에서 제외하고, 이전 통계 세대도 읽지 않는다. 다른 정상 차량의 과거 API 응답까지 일괄 삭제하지 않는다. 유효 관측에서 다시 집계한 통계와 새 예측부터 재사용한다. 새 당일 보정 자료가 50건 쌓이기 전에는 기존 모델의 기본 보정 규칙을 따른다.

- 실제 좌석 통계는 유효한 출발·결과 관측이 같은 편도인 과거 라벨로 재집계할 수 있다. 예측 확률 자체를 쓰지 않으므로 보정 재사용 조건과 구분한다.
- 가져온 seed 합계에는 편도별 원본 근거가 없어 섞지 않는다. 원본이 없는 seed 부분은 복원하지 못한다.
- 유효한 표본이 없으면 통계를 생성하지 않는다. 이전의 무효 세대로 되돌아가지 않고 빈 통계를 사용한다.
- 정리 도구는 예측을 새로 발행하거나 원본 값을 보정하지 않는다. 기존 모델 계수도 재학습하지 않는다.
- `training_eligible_*` 기존 모델 릴리스 제외 조건에 편도/계산 자료 버전 조건을 추가한다. 외부 학습기가 이 view를 실제 사용하는지는 별도 확인 대상이다.

## 실행 전 확인할 순서

1. `travel-intervals.sql`에 노선 판본·좁은 날짜 범위를 지정해 읽기 전용으로 관측한다. 차량별 재관측 간격의 시간대별 평균/p50/p95/p99, 정류소 진입 간격, 회차지 출발 간격과 가장 짧은 왕복 후보를 본다. 긴 공백은 정체와 관측 누락이 섞일 수 있다.
2. 시간 제한을 사용할 경우 노선 판본의 `maximum_observation_gap_seconds`와 `observation_gap_evidence`에 검토한 간격과 근거를 기록한다. 미설정 상태에서도 GBIS 기반 판정과 과거 자료 정리를 실행할 수 있다. 예제 테스트의 60초를 운영 설정으로 복사하지 않는다.
3. common V15와 앱 변경의 적용 순서를 준비한다. 이 브랜치에는 V14가 없지만 병행 SAL-132 작업에서 사용하므로, 병합 시 Flyway 순서를 확인한다. V15 적용 후 나중에 더 낮은 번호를 넣는 배포는 피한다.
4. 기존 migration-tool 실행 방식으로 `quality-preview`를 실행해 처리량을 확인한다. 이 결과는 원본/범위 초과/미판정/기존 산출물 건수이며, 최종 제외 편도 수를 미리 확정한 결과는 아니다.
5. `quality-rebuild`를 같은 판본·until로 반복한다. 한 호출의 batch-limit은 1~100이다. 시작 후 해당 판본은 사용 보류되고 다른 판본은 유지된다. 같은 노선의 과거 보정·통계는 보수적으로 사용 중단된다. 진행 중 시간 정책 변경은 거부한다. 미설정으로 시작한 뒤 정책을 추가하는 경우도 변경에 해당한다.
6. `quality-status`로 최종 상태별 관측/편도 수를 확인한다. 완료 후 같은 요청을 반복하면 0건 처리한다. 새 범위/정책으로 다시 시작하는 기능은 이번 도구에 없다.
7. worker의 정기 통계 집계(기존 기본 6시간)를 통해 새 세대를 만든다. 그 전까지 무효 통계는 사용하지 않는다. 즉시 재집계가 필요하면 `StopDemandStatisticsWriter.recompute`를 노선별로 실행하는 별도 운영 절차가 필요하다.

명령 형태(미실행):

```text
quality-preview --config <설정파일> --route-version <판본ID> --until <UTC시각>
quality-rebuild --config <설정파일> --route-version <판본ID> --until <같은UTC시각> --batch-limit 20
quality-status --config <설정파일> --route-version <판본ID>
```

기존 설정의 `target.kind`, `database.env-file`을 사용한다. 운영 대상 쓰기는 기존 이관 도구의 승인 영수증 방식(`--approval`, action=`ACADEMY_TRIP_QUALITY_REBUILD`)을 유지한다. 사전 조사와 상태 조회는 읽기 전용 transaction이다. 잠금 대기 3초/문장 30초 제한을 둔다. 오류 시 해당 호출 전체를 rollback하고 커서부터 재시도한다. 다른 이관 작업으로 과거 관측을 동시에 추가하지 않는다. until은 이미 수집이 끝난 과거 범위를 선택한다.

정리 범위 뒤의 기존 편도 연결은 완료 시 해제해서 미확정으로 보류한다. 최신 관측은 실시간 작업에서 다시 판정하며, 이전에 완료 표시가 된 예보를 자동 재발행하지 않는다.

## 검증 경계

Java 컴파일과 단위/Mockito/MockMvc/패키지 경계 검사, 일회용 PostgreSQL의 DDL/view/JPQL·저장소·API·재판정·롤백/재개 검증을 수행했다. 운영 DB에는 접속하지 않았다. 전체 Gradle, 실제 CLI 설정/승인 절차, 운영 규모의 비용과 동시 잠금 대기는 미검증이다. 최신 결과는 backend/history/2026-09-21-SAL-133.md를 참고한다.

## 시간 기준의 근거 수집

`travel-intervals.sql`은 원본 테이블만 읽으므로 V15 설치 전에도 조회할 수 있다. 노선 판본 하나·6시간부터 시작한다. `statement_timeout=15s`, `max_parallel_workers_per_gather=0`으로 조회하고 테이블/인덱스/임시 테이블을 만들지 않는다. 이 제한이 DB 자원 사용량을 보장하지는 않는다. 오류로 세션이 transaction 안에 남으면 `ROLLBACK;`으로 끝낸다.

1. 같은 차량의 연속 관측 간격을 시간대별로 확인한다. 한 정류장 평균 이동 시간을 최대 관측 간격으로 바로 쓰지 않는다.
2. 같은 회차지에서 순번 변화 없이 도착/출발 상태만 반복된 응답은 한 방문으로 센다. 조회 시작에 걸친 첫 방문은 출발 시각이 잘렸을 수 있어 제외한다.
3. A→B 출발 간격은 반대편 출발까지의 시간으로 종점 대기를 포함한다. A→B→A를 모두 관측한 경우만 왕복 후보로 집계한다. A→A만 보인 경우는 반대편 출발 누락 후보로 따로 센다.
4. 가장 짧은 왕복 후보 10건의 시각과 최대 관측 공백을 확인한다. 관측 최솟값을 물리적으로 가능한 최소 운행 시간이라고 단정하지 않는다. 시간 범위/날짜를 늘려 재확인한 뒤 제한값을 결정한다.
5. 정상 수집 간격은 충분히 허용하면서 왕복 소요시간보다 짧은 연결 제한을 검토한다. 시간대별 수집 주기 차이도 확인한다. 조건을 넘은 관측은 이전 편도와 연결하지 않는다.

psql에서 설정할 변수의 형식(아래 값은 예시):

```text
\set route_version_id 123
\set from_at '2026-09-21 08:00:00+09:00'
\set until_at '2026-09-21 14:00:00+09:00'
\i /path/to/travel-intervals.sql
```

현재 SQL은 검토/작성 단계이며 실제 운영 결과나 기준값을 확보했다는 의미는 아니다.
