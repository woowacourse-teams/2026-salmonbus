# SAL-321 탈퇴 회원의 Amplitude 기록 삭제 요청

## 동작

회원 삭제와 같은 트랜잭션에서 `analytics_deletion`에 공개 ID와 시도 횟수를 저장한다. 저장에 실패하면 회원 삭제도 롤백한다. 회원 삭제 트랜잭션이 끝나면 기존 카카오 연결 해제와 같은 방식으로 탈퇴 호출자가 전송을 시도한다. 카카오는 `MeController`, 애플은 `AppleWithdrawal`에서 호출한다. 프로세스가 종료되거나 전송이 실패하면 주기 작업이 남은 기록을 처리한다. 별도 이벤트나 실행기는 두지 않는다.

`POST https://amplitude.com/api/2/deletions/users`에 프로젝트 API 키와 시크릿 키로 Basic 인증하고 `user_ids`를 보낸다. `ignore_invalid_id=true`로 분석 기록이 없는 회원도 성공으로 처리한다. 외부 호출의 연결 제한은 3초, 요청 응답 제한은 5초다.

실패하면 탈퇴를 되돌리지 않고 시도 횟수를 늘린다. 성공하면 대기 기록을 지운다. 실패한 기록은 횟수로 포기하거나 보관 기간만으로 삭제하지 않는다. 기본 재시도 시각은 매 5분의 15초이며, 한 번에 최대 100명을 한 요청으로 보낸다. 시도 횟수가 적은 기록부터 처리한다.

여러 서버가 같은 기록을 동시에 보내지 않도록 `FOR UPDATE SKIP LOCKED`로 잠근다. HTTP 호출 동안 잠금을 유지하므로 실행 중에는 DB 연결 하나를 쓴다. 즉시 시도는 동기 호출이라 외부 응답이 올 때까지 탈퇴 응답도 기다린다. Amplitude가 접수한 뒤 DB 커밋 전에 프로세스가 종료되면 같은 ID가 다시 전송될 수 있다. 즉시 전송이나 여러 서버의 요청이 겹쳐 Amplitude의 초당 1회 제한에 걸린 429도 실패로 남겨 다음에 시도한다.

## 환경별 설정

API 프로세스가 읽는 환경 파일에 다음 이름으로 설정한다. 키 값은 저장소나 로그에 남기지 않는다.

| 환경 변수 | 값 |
| --- | --- |
| `AUTH_ENABLED` | `true` |
| `AMPLITUDE_API_KEY` | dev는 프로젝트 852649, 운영은 프로젝트 852648의 API 키 |
| `AMPLITUDE_SECRET_KEY` | 같은 프로젝트의 시크릿 키 |

로그인 기능이 켜져 있으면 삭제 요청도 기본으로 전송한다. 별도의 활성화 환경 변수는 받지 않는다. 키가 비어 있으면 기동을 거절한다. 각 서버의 실제 키 등록과 재시작은 이 코드 변경에 포함하지 않았다.

## 배포 후 확인

1. dev 프로젝트에서 시험 계정의 로그인과 분석 이벤트 수집을 확인한다.
2. 탈퇴 후 회원 삭제, 해당 공개 ID의 Amplitude 삭제 작업 접수, 대기 기록 삭제를 확인한다.
3. 시험 환경에서 외부 요청 실패를 만들고 탈퇴 완료와 대기 기록의 시도 횟수 증가를 확인한다. 정상 인증으로 되돌린 뒤 재시도 성공과 기록 삭제를 확인한다.
4. Session Replay 삭제 범위는 실제 dev 프로젝트에서 별도로 확인한다. 요청 접수가 실제 삭제 완료를 뜻하지 않는다.
5. 처리방침 4절과 5-2의 대기 기록 설명은 별도 게시 문서에서 확인한다. 이 작업에서는 처리방침을 게시하거나 수정하지 않았다.

SQL 조회 시 공개 ID를 화면이나 로그에 출력하지 않고 대기 건수와 실패 횟수만 확인한다. ID는 성공할 때까지 요청을 다시 보낼 수 있는 유일한 값이므로, 장애 중에 대기 테이블을 비우지 않는다.

## 병행 작업과 마이그레이션

CI의 연속 번호 검사에 맞춰 이 변경은 V47을 사용한다. 먼저 작성한 V48은 V47 공백 때문에 검증에 실패했다. 아직 병합하지 않은 `codex/route-operations`도 V47을 사용하므로, 두 작업을 합칠 때 병합 순서에 맞춰 아직 배포하지 않은 번호와 마이그레이션 순서 테스트 대상을 조정한다.

`codex/SAL-318-ci-fix`와 `application.yml`, `test-baseline.properties`가 겹친다. 다른 브랜치의 변경은 이 작업으로 복사하지 않았다. 단순화 후 이 작업의 테스트 증가분은 api-app 14개, member 5개다. 합칠 때 각 브랜치의 증가분을 더하고 전체 실행 결과와 대조한다.

## 검증 기록 (2026-10-29)

- 비동기 전송 보완 전 단위 테스트 19개 통과. HTTP 요청 형식, 302/400/401/429/500 및 연결 오류, 재시도 결과 처리를 확인했다. 전체 CPU 최고 37.9%였다.
- 비동기 전송 보완 후 재검증은 전체 CPU 42.6%를 감지해 중단했다. 프로세스를 종료했고 자동 재시도하지 않았다. 최종 코드의 통과 결과로 앞선 19개를 사용하지 않는다.
- 실제 DB의 원자성, 동시 처리, 실패 후 성공을 다루는 통합 테스트 5개를 작성했지만 실행하지 않았다. 단순화하면서 중간 저장소 인터페이스와 서비스, 그 저장소 모의 객체만 검증하던 테스트 6개를 제거하고 JDBC 구현 한 곳으로 합쳤다.
- 이후 사용자 요청으로 이벤트와 실행기를 제거했다. 카카오 및 애플 호출 연결과 설정, JDBC 트랜잭션 경계를 정적 검토했고 `git diff --check`를 통과했다. 단순화한 코드의 컴파일 및 테스트는 실행하지 않았다.
- 전체 `clean build`, 배포 훅 컨테이너 리허설, 실행 JAR 패키징 검증은 실행하지 않았다. VM이나 컨테이너를 시작하지 않았다.
- dev/운영 키 등록, dev Amplitude 실연동, Session Replay 삭제는 미확인이다.

근거: [SAL-321](https://higgs95.atlassian.net/browse/SAL-321), [Amplitude User Privacy API](https://www.amplitude.com/docs/apis/analytics/user-privacy).

## PR #215 CI 실패 수정

- 원격 CI에서 테스트 5개가 실패했다. MigrationOrderTest 4개는 V47 공백과 이전 작업을 가리키던 테스트 대상 목록이 원인이었다. 마이그레이션을 V47로 바꾸고 대상 목록을 analytics_deletion으로 맞췄다.
- AppleLoginConfigurationTest 1개는 애플 탈퇴 설정에 필요한 AmplitudeDeletionJob을 시험용 컨텍스트에 등록하지 않아 실패했다. 모의 객체를 등록했다.
- 포크 PR의 읽기 전용 토큰으로 테스트 결과 체크 생성이 거절됐다. 포크에서만 action-junit-report의 annotate_only를 켜 로그와 잡 요약을 유지한다. 테스트 실행이나 실패 판정은 건드리지 않는다.
- 로컬 빌드와 테스트는 CPU 중단 후 다시 실행하지 않았다. 수정한 커밋의 검증은 원격 CI 결과로 별도 확인한다.

## 삭제 전송 기본 활성화

사용자 요청으로 AMPLITUDE_DELETION_ENABLED 환경 변수 연결을 없애고 전송 기본값을 true로 바꿨다. AMPLITUDE_API_KEY와 AMPLITUDE_SECRET_KEY는 서버 비밀 설정으로 유지한다. API 통합 테스트에서만 전송을 비활성화한다. 서버 키 등록과 실제 API 재시작은 수행하지 않았다.

## 리뷰 반영과 인증 키 확인 (2026-10-30)

즉시 전송과 주기 재시도를 같이 맡는 클래스 이름을 AmplitudeDeletionProcessor로 바꿨다. 외부 호출 중 DB 연결과 행 잠금을 유지하는 구조는 이번 범위에서 유지하며, 임대 후 외부 호출 방식과 반복 실패 감지는 후속 과제로 둔다. 심각한 성능 저하를 실측한 결과는 없다.

운영 서버의 /etc/salmonbus/api.env와 실행 중인 salmonbus-api 프로세스에서 AMPLITUDE_API_KEY, AMPLITUDE_SECRET_KEY 모두 미등록임을 읽기 전용으로 확인했다. 비밀값은 출력하지 않았으며 서버 설정과 서비스를 변경하지 않았다. dev 서버는 미확인이다. 기본 활성화된 새 코드를 운영에 배포하기 전에 운영 프로젝트 852648의 API Key와 Secret Key를 등록해야 한다. dev는 프로젝트 852649의 키 쌍을 사용한다. 프론트용 WEBPACK_AMPLITUDE_API_KEY만으로는 서버 삭제 API를 인증할 수 없다.
