# 예보 저장량 축소와 운영 이관 준비

예보 행에는 발행 당시 정원만 JSON에 기록하고, 기존 모델 배포 ID와 노선 판본으로 정산 근거를 조회한다. 이전 예보는 행에 들어 있는 정산 근거를 그대로 읽는다. 이관 후보를 고르는 쿼리는 응답 시각이 있는 배치와 없는 배치의 최솟값을 각각 구한다. 2026-11-12 운영의 읽기 전용 계획에서 양쪽 모두 `ix_batch_recent_history`를 사용했다. 실행 시간과 날짜 범위 내 원본을 읽는 이관 쿼리의 처리량은 운영에서 측정하지 않았다.

## 예보 포맷 전환

1. V79와 두 포맷을 읽는 worker를 먼저 배포한다. 기본 설정인 `FORECAST_COMPACT_SETTLEMENT_WRITE=false`로 기존 worker가 정산할 수 있는 JSON을 쓴다. 모델의 예측값, 정산 입력, 출처 필드는 유지하고 저장용 추론 벡터는 제외한다.
2. v2, v3 출퇴근, v3 확장 시간대에서 같은 예보를 두 포맷으로 정산했을 때 `label_value`와 `parameter_hash`가 모두 같은지 확인한다. 운영에서 기존 예보 정산과 worker 기동을 확인하고 해당 worker 패키지를 롤백 대상으로 보존한다. 이후 별도로 승인한 전환에서 `FORECAST_COMPACT_SETTLEMENT_WRITE=true`를 적용한다.
3. 전환 후에도 기존·신규 예보 정산과 대기열 추이를 확인한다. 새 포맷을 쓴 뒤에는 두 포맷을 읽는 worker로 복구한다. v1.7.0 worker가 정원만 저장한 예보의 대기 작업을 처리하면 v2는 `MISSING_REAL_STOP_CONTRACT`, v3는 `INPUT_PROFILE_MISMATCH`로 종결하고 대기 작업을 삭제한다. 두 포맷을 읽는 worker를 다시 시작해도 그 라벨은 자동으로 복구되지 않는다. 자세한 복구 절차는 [운영 RUNBOOK](../deploy/RUNBOOK.md#예보-정산-저장-형식-롤백)을 따른다.

## V79 적용 순서

2026-11-12 dev RDS의 Flyway 이력을 읽기 전용으로 조회했다. 마지막 적용 기록은 `V78__confirmed_history_cursor_index.sql`이고 V79와 V80 기록은 없었다. [PR #310](https://github.com/woowacourse-teams/2026-salmonbus/pull/310)은 dev 대상으로 별도의 V79를 추가한다.

1. #325의 `V79__model_settlement_context.sql`을 main에 먼저 적용하고, 해당 커밋을 dev에 반영한다.
2. #310을 병합하거나 dev DB에 적용하기 전에 dev를 기준으로 갱신하고 `V79__incremental_alighting_settlement.sql`을 `V80__incremental_alighting_settlement.sql`로 변경한다. 배포 직전에 dev의 적용 이력을 다시 확인한다.
3. 최종 트리에서 V79와 V80 파일이 하나씩 존재하고, V79 적용 DB에 V80이 이어서 적용되는지 검증한다. 이미 #310의 V79가 적용된 DB를 발견하면 병합·배포를 보류하고 DB별 적용 이력을 대조한다.

## 운영 이관과 원본 삭제

1. 현재 RDS 여유와 쓰기 속도를 읽기 전용으로 확인한다. 기존 인덱스를 사용하는 후보 조회부터 점검하고, 여유 공간을 늘리거나 인덱스를 생성하기 전에 이관 전용 검증을 준비한다. `ARCHIVE_DELETE_ENABLED=false`를 유지한다.
2. 별도로 승인한 이관 전용 실행에서 KST 오늘·어제를 제외한 표본 작업의 매니페스트와 데이터 파일을 S3에서 다시 읽어 장부의 SHA-256과 행 수를 확인한다. 날짜 범위 원본 조회도 제한 시간 안에 끝나는지 확인한다. 제한 시간에 걸리면 반복 실행을 중지하고 해당 쿼리의 계획을 점검한다. 정원만 있는 예보와 모델·노선 정산 근거를 별도 DB로 복원해 정산 결과를 검증한다. 같은 모델 배포 ID의 여러 파일에서 노선별 근거를 합쳐 보존한다.
3. 원본 삭제를 검토할 때 `backend/deploy/sql/check-operational-archive-indexes.sql`로 필요한 인덱스의 정의와 유효 여부를 확인한다. 누락 인덱스 생성에 필요한 공간이 확인된 뒤에만 `prepare-operational-archive-indexes.sql`에서 필요한 항목을 트랜잭션 밖에서 하나씩 실행한다. 동일 이름의 무효 인덱스는 재실행 전에 별도로 처리한다.
4. 승인 후에만 삭제를 활성화한다. 앱은 삭제 전 매니페스트와 파일을 다시 확인하고, 파일 해시와 DB 원본이 일치하는 행만 삭제한다. 첫 작업의 `PURGED_FILE`, `DONE`, DB 장부를 대조하고 동일한 24시간의 예보 INSERT/DELETE, TOAST·인덱스 크기, RDS 여유 공간을 비교한다.

현재 운영 후보 등록은 기존 앱에서 10초 제한에 걸렸다. 운영 원본 삭제, 인덱스 생성, S3 복원, 새 후보 조회의 운영 실행은 이 변경에서 수행하지 않았다.

## 운영 I/O 확인과 배포 순서

- `main` 병합은 API와 worker를 배포한다. archive 앱은 같은 커밋에서 생성한 별도 패키지를 사용한다. worker의 구 포맷 호환 배포가 먼저이며, 실제 저장량 축소를 크게 적용하는 전환은 두 포맷을 읽는 리비전을 확보한 뒤 수행한다.
- 이관 메타데이터가 참조할 모델 배포 ID는 이미 읽은 예보 페이지에서 가져온다. 메타데이터 쿼리는 같은 날짜의 예보를 다시 스캔하지 않고 10초 문장 제한과 병렬 실행 제한을 적용받는다.
- 운영 읽기 전용 계획에서 예보 페이지 쿼리는 날짜 조건을 인덱스 범위에 모두 넣지 못하고 정렬을 사용했다. 페이지 크기는 출력 행 수 제한이다. 실행 중 읽는 행 수나 DB I/O의 상한은 아니다. 운영 예보 배포와 이관 전용 검증은 별도 시점에 수행하고, 이관을 시작하기 전에 기존 RDS 쓰기 지연, 디스크 대기열, EBS I/O 및 처리량 잔량을 기록한다. 제한 시간 초과가 반복되거나 잔량이 지속적으로 감소하고 평시보다 쓰기 지연이 늘면 archive 앱을 중지하고 해당 쿼리의 계획과 범위를 확인한다.
