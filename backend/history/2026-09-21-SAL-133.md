# 2026-09-21 — SAL-133 백엔드 변경 이력

작성·해석 기준: [README](README.md).

- 기록 기준: 2026-09-21 KST, 기준 커밋 `9b06bfc` 대비 변경. 같은 날 C(API) 구현·커밋 결과까지 갱신했다.

- 상태: worker와 C(API) 구현·부분 테스트·로컬 코드 커밋 완료. 미배포이며 운영 적용 결과는 아니다. push·PR 게시는 하지 않았다.
- 코드 근거: worker `c05de268`, C 관측 조회 `cc41f113`, C 차량 유지·응답 변경 `fc87985c`.

## 배경: 실제 82석 사례

- 확인된 사실: 사용자 제공 DB 조회에서 2026-09-16 1650 노선의 잔여석 82 관측 12건을 확인했다. 2026-09-17 운영 로그에는 `정원은 1석부터 70석까지다: 82` 오류가 있었다.
- 코드상 영향: 모델의 `capacity`는 실제 차량 제원이 아니라 과거 관측 최대 잔여석이다. 현재값이 정상으로 돌아와도 과거 최대값 82 때문에 입력 검증이 실패할 수 있었다.
- 미확인: 위 DB 관측과 운영 로그가 같은 차량·관측 묶음인지는 연결하지 못했다. 단말기 초기화가 원인이라는 설명은 가설이다.

## 1. 좌석 범위 오류를 전용 예외로 구분

- 대상: `SeatDistributionInput`, `SeatRangeException`.
- 변경 전 → 후: 좌석 범위 오류도 일반 `IllegalArgumentException`으로 처리 → `SeatRangeException`으로 구분하고 거부된 필드·값·허용 범위를 제공.
- 이유: 82석 같은 범위 오류만 차량별로 처리하고 다른 계산·설정 오류는 숨기지 않기 위해서다.
- 결과: 현재 잔여석 0~70, `capacity` 1~70의 기존 제한은 유지한다. 70은 실제 차량 제원 상한을 뜻하지 않는다.

## 2. 범위 오류 차량의 예보만 제외

- 대상: `ForecastBatchWriter.forecastsOfVehicleOrEmpty()`.
- 변경 전 → 후: 한 차량의 범위 오류로 같은 관측 묶음 전체의 저장 중단 → 해당 차량의 모든 대상 정류장 예보만 제외하고 다른 차량 계산 계속.
- 이유: 과거 최대값 82인 차량 하나 때문에 정상 차량의 예보까지 저장하지 못하는 문제를 막기 위해서다.
- 결과: 실패 차량이 중간에 계산한 결과도 저장 목록에서 제외한다. 정상 결과의 저장 요청 후 `forecast_completed_at`을 기록하며, 모두 제외된 경우도 완료를 기록한다. 일반 계산·DB 오류는 전파한다.
- 완료의 의미: 모든 차량에 대한 생성 또는 제외 판단 종료. 모든 차량의 예보 생성 성공을 뜻하지 않는다. 완료된 관측 묶음은 기존 대기 조회에서 재선택되지 않는 구조이며, 실제 DB 검증은 남아 있다.

## 3. 예보 제외 사유를 로그로 기록

- 대상: `ForecastBatchWriter`의 `event=forecast_vehicle_skipped` 로그.
- 변경 전 → 후: 제공받은 82석 오류 로그만으로 원인 관측 식별 불가 → 제외할 때 관측 묶음 ID·관측 ID·모델 배포 ID·현재 잔여석·과거 최대값·거부된 필드와 값·허용 범위를 한 번 기록.
- 이유: 다음 범위 오류에서 어떤 관측과 모델 입력이 예보 제외를 일으켰는지 추적하기 위해서다.
- 결과: 진단 전용 DB 저장은 추가하지 않았다. 표준 Logback 출력 예외 사례는 테스트했지만 운영 로그 전달·보존은 미검증이다.

## 4. 예보 처리 클래스의 패키지 이동

- 대상: `ForecastBatchWriter`.
- 변경 전 → 후: `com.gustler.backend.processor` → `com.gustler.backend.forecast.prediction`.
- 이유: 차량별 모델 호출·오류 처리·저장 순서를 담당하는 코드의 위치를 명확히 하기 위해서다.
- 결과: 호출부 import와 writer 테스트 위치를 함께 정리했다. 기존 트랜잭션 경계는 유지했다.

## 5. 모델 계약과 범위 예외의 패키지 정리

- 대상: `SeatForecastModel`, `SeatRangeException`.
- 변경 전 → 후: 기존 `SeatForecastModel`을 `processor`에서 `forecast.model`로 이동. 이번 작업에서 새로 만든 `SeatRangeException`도 최종적으로 `forecast.model`에 배치.
- 이유: 모델 입력 검증 계약을 예보 처리 순서와 구분하기 위해서다.
- 결과: 관련 import를 정리했다. 구체 모델은 기존 `processor.seatdistribution`에 유지하며 전체 패키지 개편은 보류했다.

## 6. 예보 유무와 별개로 보드의 차량 관측 조회

- 대상: `BoardQueryRepository.findObservedVehicles()`, `JpaBoardQueryRepository`, 신규 `BoardVehicleObservationEntityRepository`·`BoardVehicleObservation`, 보드용 `VehicleObservationJpaEntity`.
- 변경 전 → 후: 보드에서 예보 행으로만 차량 목록 구성 → 선택한 관측 묶음과 노선 판본의 차량 관측을 별도로 조회.
- 이유: 좌석 범위 오류 등으로 예보를 만들지 못한 차량도 실제로 접근하고 있을 수 있다. 앞선 worker 수정만으로는 API의 차량 누락을 해결할 수 없었다.
- 결과: 차량 ID·원본 행 번호·통과 정류장 순번을 조회용 객체로 전달한다. 기존 DB 열을 매핑했으며 스키마는 변경하지 않았다. DB 조회 장애는 `ServiceUnavailableException`으로 전파하며 예보 없음으로 처리하지 않는다.

## 7. 관측된 접근 차량을 유지하고 대상 정류장별 예보 연결

- 대상: `BoardQueryService.getBoard()`·`toStopState()`·`forecastOf()`, `ApproachingVehicle`, 신규 `VehicleForecast`.
- 변경 전 → 후: 유효한 예보 행이 있는 차량만 정렬해 반환 → 관측된 접근 차량을 정렬하고 각 차량에 예보 제공 상태를 연결.
- 이유: 예보 미생성과 차량 부재를 구별하기 위해서다. 차량 ID가 없는 관측도 구분하도록 대상 정류장 순번과 관측 묶음 안에서 유일한 원본 행 번호로 예보를 연결한다.
- 결과: 통과 정류장 순번 기준 앞쪽 1~12정류장, 승차 가능 정류장, 거리순 최대 3대 정책을 유지한다. 예보가 없는 차량도 3대 제한에 포함한다. 최신 예보 처리 완료 묶음 선택·5분 신선도·모델 일관성 검사는 유지한다.
- 상태 판단: 유효한 예보는 `VehicleForecast.Available`, 예보가 없거나 확률이 비유한값·범위 밖이면 `Unavailable`이다. 기대 잔여석만 유효하지 않으면 기존처럼 그 값만 생략한다.

## 8. 예측 제공 상태를 forecast 응답으로 표현

- 대상: `ApproachingVehicleResponse`, 신규 `ForecastResponse`.
- 변경 전 → 후: 차량 응답 최상위의 `seatAvailableProbability`·`expectedSeats` → `forecast.status`와 `forecast` 내부 예측값.
- 이유: 예보가 없는 차량에 잘못된 기본 확률을 부여하지 않고, 프론트가 예측 제공 상태를 명시적으로 구분할 수 있게 한다.
- 결과: 예보가 있으면 `status=AVAILABLE`, `seatAvailableProbability`, 선택적 `expectedSeats`를 반환한다. 예보가 없으면 `status=UNAVAILABLE`만 반환한다. 확률 0은 유효한 예보이며 미제공으로 바꾸지 않는다.
- 현재 좌석과 구분: `/vehicles` 코드는 변경하지 않았다. 합성 테스트에서 잔여석 82 관측이 `/vehicles`에는 82로 유지되고, 예보 행이 없는 동일 차량은 `/board`에서 `UNAVAILABLE`로 반환되는 것을 확인했다. 실제 1650 관측을 재사용한 테스트는 아니다.
- 호환성: 현재 프론트는 이전 최상위 예측 필드를 사용하므로 새 API만 배포하면 호환되지 않는다. 사용자는 프론트 변경을 별도로 전달할 예정이며, 프론트 수정과 공개 API 명세 반영은 이번 코드 커밋에 포함하지 않았다.

### 기점 관측 누락과 순번 전환의 실제 조회 근거

- 근거: 사용자가 같은 6시간 범위에서 실행해 전달한 두 추가 조회 결과. DB 직접 접속/변경은 하지 않았다.
- 확인: 1650 기점 순번 1은 관측 5건 모두 state=0, 출발 state=2는 0건. 3330 기점 순번 1은 관측/출발 각 1건. 마지막 순번(1650 89, 3330 85)은 두 노선 모두 관측 0건. 반면 안양역 회차 순번의 출발 표시는 1650 316건, 3330 106건이다. 집계만으로 기점 관측이 없는 원인은 확정하지 않는다.
- 확인: 기점 출발을 필수로 요구한 앞선 조회에서는 양쪽 출발을 연결한 편도/왕복 표본이 0건이었다. 1650 동일 회차지 재출발 후보 8건은 220.38~255.33분이며 반대편 출발 누락을 포함할 수 있다.
- 확인: 순번 전환 조회에서 1650 87/88→1/2, 3330 83/84→2/3이 실제 나타났다. 출력은 ORDER BY route_name, observed_at LIMIT 50이므로 전체 전환 수/분포로 해석하지 않는다.
- 실제 예: 1650 차량 221000029는 14:15:29.774753 순번 88에서 14:17:27.892438 순번 2로 바뀌었고, 간격은 1.97분이었다. 이는 전체 왕복 시간이 아니라 기점 직전부터 다음 출발 구간까지의 관측 공백이다. 221000027의 88→2 공백은 55.73분이었다. 긴 공백도 앞선 편도에 이어 붙이기보다 새 편도 경계 후보로 구분해야 한다.
- 계산: 1650 같은 차량의 반복된 앞 순번 재등장 시각 차이는 221000027 242.34분(2→2), 221000054 254.51분(2→2), 221000028 224.28분(2→1)이다. 마지막 사례는 정류소 순번도 다르므로 동일 지점 왕복 시간으로 단정하지 않는다. 표본 최솟값은 물리적 최소 운행 시간의 증명이 아니다. 이번 출력에서 3330의 동일 차량 반복 재등장은 확인되지 않았다.
- 판단: 새 편도 경계(회차 출발/노선 끝→앞 순번 전환)를 먼저 판단하고, 같은 편도 관측을 연결할 때 시간 제한을 적용하는 방향의 근거다. 기점 순번 1의 state=0만으로 출발 완료를 확정하지 않는다. 이후 2/3으로 진행하는지 함께 확인할 필요가 있다.

- 결과: 같은 편도를 계속하는 30대 묶음의 품질 판정은 이전 코드 경로상 97 SQL → 합성 테스트에서 5 SQL. 차량 1대도 5 SQL, 1대/30대 중 한 차량이 제외로 전환되면 각각 7 SQL, 재판정 요청은 1 SQL이다. 전체 예측 작업의 SQL 수나 CPU/메모리 감소율이 아니다. 수정되는 관측 행 자체는 남는다.
- 결과: 처음 나타난 차량은 작은 편도 테이블에 연결 가능한 판정이 있는지 먼저 확인한다. 판정된 편도가 없으면 큰 과거 관측 탐색을 실행하지 않는다. 새 인덱스는 편도 테이블에만 둔다. 직전 원본이 미판정이면 더 오래된 적격 관측으로 건너뛰지 않는 정책은 유지한다.
- 변경 전 → 후: 별도 `TripQualityJob` 삭제 → 기존 `ForecastJob`의 모델 확인 전에 품질 판정. 모델이 없거나 이후 예측 계산이 실패해도 판정은 독립 트랜잭션으로 유지한다. 최근 5분/활성 노선당 최대 20묶음 범위는 유지한다. 궤적은 이미 읽은 품질 상태를 재사용하여 적격 ID 추가 SQL 1회를 제거하고 제외 차량의 최대 잔여석 조회도 생략한다.
- 변경 전 → 후: `ForecastBatchWriter`, `SeatForecastModel`, 신규 `SeatRangeException`을 `processor`로 복귀. 신규 편도 판정 클래스/테스트도 기존 processor 안에 둔다. 구체 모델은 기존 `processor.seatdistribution`을 유지한다. 이번 패키지 원복으로 git status에는 이미 커밋된 경로 삭제와 복귀 경로 추가가 함께 보인다. 제품 Java 클래스 수는 이전 작업 상태보다 1개 감소했고, 제품 Java 줄 수는 거의 같으므로 코드량을 대폭 줄였다고 표현하지 않는다.
- 유지한 기능: 해당 편도 앞선 관측까지 제외, 정상 차량/다음 편도 유지, 저장 예측의 API 제공 중단, 현재 좌석 보존, 결과 라벨/보정/통계/학습 재사용 차단, 과거 재판정/중단/재개. 노선 품질 버전 무효화와 근거 없는 seed 합계 제외의 기존 보수적 영향은 유지한다.
- 수정: 합의한 순서대로 출발/방향 전환을 시간 조건보다 먼저 판단한다. 같은 편도 연결에만 선택적 시간 제한을 적용한다. 실제 DB 검증에서 발견한 재판정 커서의 integer→Long JDBC 변환 오류와 커밋하는 파라미터 테스트 간 자료 격리도 수정했다.

### 축소 후 검증 결과와 한계

- 검증: Java 21/캐시 JAR javac + JUnit 순차 실행. DB 없는 단위/Mockito/MockMvc/패키지 경계 137개 성공. 격리 PostgreSQL 저장소 79개, API 계약 10개, 과거 재판정/SQL 호출 수/독립 트랜잭션 5개, ForecastJob 15개 성공. 중복 실행한 PackageBoundaryTest 2개를 제외한 고유 테스트 246개 성공, 실패/스킵 0.
- 방법: Testcontainers 기본 실행 대신 임시 테스트 설정으로 일회용 PostgreSQL 18.6에 연결했다. 저장소/API 테스트 본문은 그대로 실행했고, 과거 재판정은 실제 커밋/롤백/재개를 실행했다. `REQUIRES_NEW`는 실제 Spring 트랜잭션 프록시로 외부 예측 트랜잭션 실패 뒤 제외 상태가 유지되는지 확인했다. 실제 CLI 설정/승인 영수증 경로 전체를 실행한 것은 아니다.
- 실행 계획: 500묶음 × 30대 = 15,000개 합성 관측에서 현재 묶음 30대의 직전 관측 조회를 확인했다. 최종 코드에서 기존 차량은 관측 묶음/차량 인덱스를 사용했고, 처음 나타난 차량은 과거 관측 탐색 노드가 실행되지 않았다. 로컬 단일 실행은 각각 0.465ms/0.301ms였지만 따뜻한 캐시·작은 합성 자료라 운영 성능 근거로 확대하지 않는다. 긴 관측 공백과 운영 규모는 별도 검증 대상이다.
- 자원: 컨테이너 1개, CPU 1개/메모리 128MiB 제한. 최초에는 DB 파일도 tmpfs에 두었는데 합성 자료 준비의 대량 UPDATE 중 누적된 메모리 사용으로 OOM이 발생했다. 해당 컨테이너를 삭제하고 같은 메모리 제한에서 임시 디스크 저장으로 바꿔 검증을 완료했다. 교체 컨테이너의 OOMKilled=false, 완료 후 관측 사용량 34.91MiB를 확인했다. 이는 최고 사용량이나 RDS/개별 쿼리 메모리가 아니다. JVM은 ActiveProcessorCount=1과 heap 256/384MiB를 사용했다.
- 실행기 한계: ForecastJob/패키지 경계 17개는 성공 결과 출력 후 스케줄러 스레드가 남아 로컬 실행기를 종료했다. 테스트 결과와 프로세스 종료 코드는 구분한다. 이후 임시 실행기는 성공/실패 결과를 출력하고 종료하도록 보완했다.
