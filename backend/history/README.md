# 백엔드 변경 이력 작성·해석 규칙

## 목적

- AI와 개발자가 이 기록만으로 무엇을 왜 변경했고 어디까지 검증했는지 설명할 수 있게 한다.
- 코드의 상세 수정 이력은 Git으로 확인하고, 이 디렉터리에는 동작 변화·판단 근거·검증 결과를 기록한다.

## 작성 규칙

- 파일명은 `YYYY-MM-DD-이슈키.md`로 작성한다. 이슈키가 없으면 짧은 작업명을 사용한다.
- 상단에 기록 날짜·시간대, 비교 기준 커밋, 변경 요약, 구현·커밋·배포 상태를 적는다.
- 소제목 하나에 변경 사항 하나를 기록하고, 대시 목록으로 `대상`, `변경 전 → 후`, `이유`, `결과`를 적는다.
- 대상은 실제 클래스·메서드·패키지·API 이름으로 명시한다.
- 이유에는 확인한 실제 사례를 넣는다. 실제 관측·로그와 설명용 예시·재현 테스트 입력은 구분한다.
- 결과에는 바뀐 동작과 영향 범위를 적는다. 테스트 결과와 운영 결과는 구분한다.
- 마지막에 수행한 검증·미검증·미구현을 기록한다. mock 저장소 테스트를 실제 DB 검증으로 표현하지 않는다.
- 비밀값·개인정보·불필요한 원본 로그는 기록하지 않는다. 상세 자료가 필요하면 근거 문서를 연결한다.
- 상태가 바뀌면 확인 날짜와 근거를 함께 갱신한다. 이전 기록 시점의 상태를 현재 상태처럼 설명하지 않는다.

## AI가 변경 이력을 설명할 때

- `무엇이 달라졌는가 → 왜 바꿨는가 → 무엇을 확인했는가 → 무엇이 남았는가` 순서로 설명한다.
- 확인된 사실·코드 분석·원인 가설을 구분한다. 기록에 없는 원인이나 완료 상태를 추정하지 않는다.
- 구현 완료를 커밋·배포·운영 복구 완료로 해석하지 않는다. 별도 응급 조치의 결과를 미배포 코드의 효과로 설명하지 않는다.
- 현재 상태를 질문받으면 기록 시점을 밝히고, 확인 가능한 최신 코드·Git·검증 근거와 대조한다. 대조하지 못하면 미확인으로 표시한다.

## 기록 양식

```markdown
# YYYY-MM-DD — 이슈키 변경 이력

- 기록 기준: 날짜·시간대, 기준 커밋.
- 요약: 핵심 동작 변화.
- 상태: 구현 / 커밋 / 배포 상태.

## 변경 사항 하나

- 대상: 실제 코드 또는 API 이름.
- 변경 전 → 후: 입력·조건에 따른 동작 차이.
- 이유: 실제 사례와 해결할 문제.
- 결과: 적용한 동작과 영향 범위.

## 검증 및 남은 작업

- 검증: 실행한 테스트·환경·결과.
- 미검증: 확인하지 못한 범위.
- 미구현: 합의했지만 아직 적용하지 않은 변경.
```
