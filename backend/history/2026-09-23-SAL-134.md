# 2026-09-23 — SAL-134 변경 이력

- 기록 기준: 2026-09-23, Asia/Seoul. 비교 기준은 PR #70이 반영된 `9f9c75db16fcdefc0944f0c6a40fa7c09e4e1d94`다.
- 요약: 완료된 S3→RDS 이관 기능을 제거하고 노선 관리·관측 수집·탑승 예보의 업무 모델과 저장 책임을 분리했다.
- 상태: 코드 구현과 단위별 로컬 커밋을 진행했다. 최종 검증 결과와 커밋 목록은 [구현 기록](../../docs/refactoring/ddd/implementation-progress.md)에 남긴다. 운영 DB 적용·원격 push·PR 게시·문서 사이트 갱신은 수행하지 않았다.

## 실행 앱과 업무 모듈 분리

- 대상: `backend/settings.gradle`, `business/*`, `integrations/gbis-client`, `api-app`, `worker-app`, `maintenance-app`, `common`.
- 변경 전 → 후: Worker 안의 수집·계산·저장 코드를 업무 모듈로 옮겼다. Gradle 프로젝트는 9개이며 `business`와 `integrations`는 디렉터리다. Worker에는 기동·설정·스케줄을 두고 다른 모듈의 공개 API로 업무를 실행한다.
- 이유: 같은 품질 조사 규칙을 자동 작업과 수동 명령이 공유해야 한다. 정비 명령 때문에 Worker의 모델 적재나 스케줄이 기동되지 않도록 실행 구성을 분리했다.
- 결과: 도메인 규칙은 Spring·JPA·JDBC에 의존하지 않는다. 저장 어댑터는 도메인 객체와 별도 매핑을 사용한다. API 실행 클래스패스의 프로젝트 의존은 API와 common뿐이다. 정비 앱은 필요한 JDBC·트랜잭션·품질 기능만 등록한다.

## 완료된 이관 기능 제거

- 대상: 기존 `migration-tool`의 Java 49개와 전용 자원·스크립트·테스트·AWS SDK 의존.
- 변경 전 → 후: S3 목록·archive·반입·대조·롤백·historical seed·임시 모델 전환에만 쓰던 Java 38개를 제거했다. 품질 조사 업무는 forecasting에 두고 나머지 명령 실행 지원은 maintenance-app에서 재구성했다.
- 이유: 해당 S3→RDS 이관은 완료됐으며 온라인 계산과 품질 정비만 계속 필요하다.
- 결과: 공개 정비 명령은 `quality-preview`, `quality-rebuild`, `quality-status`다. DB에 남아 있는 반입 출처·감사·seed·제외 기록과 Flyway 적용 이력은 삭제하지 않는다. 기존 서비스 V1~V16 SQL도 변경하지 않았다.

## 노선 버전과 호출 횟수 예약

- 대상: `Route`, `RouteVersion`, `JpaRouteRepository`, `DailyCallQuota`, `ApiCallQuota`.
- 변경 전 → 후: 노선 행을 잠근 뒤 최신 버전을 다시 읽고 도메인 규칙에 따라 시간표 변경 또는 버전 교체를 수행한다. GBIS 통신과 일일 호출 횟수 예약은 별도 모듈이 담당한다.
- 이유: 테스트에서 같은 노선의 첫 등록과 같은 개편을 동시에 실행하고, 새 정류장 저장이 실패하는 경우를 재현했다. 서로 다른 버전을 중복 생성하거나 이전 버전만 종료된 상태를 남기면 안 된다.
- 결과: 이전 버전 종료와 새 버전·정류장 저장을 함께 커밋한다. 종료된 버전은 같은 digest라는 이유로 현재 버전으로 반환하거나 수정하지 않는다. 호출 횟수 예약은 호출자 트랜잭션에 참여하며 서울 날짜 변경 시 재예약하는 기존 동작을 유지한다.

## 수집 시도와 입력 확정

- 대상: `CollectionBatch`, `CollectionPlan`, `CollectionAttemptToken`, `CollectionInputs`, `JpaObservationRepository`.
- 변경 전 → 후: 배치 ID와 시도 번호를 함께 전달하고 예약·전송·완료 단계의 상태를 도메인 객체가 검증한다. 예보·평가·품질 조사에서 사용한 원 관측은 `confirmInput`으로 확정한다.
- 이유: 이전 HTTP 응답이 늦게 도착해 새 수집 결과를 덮거나, 계산 근거로 사용한 관측이 재수집으로 바뀌는 경쟁을 막아야 한다.

## 예보 발행과 평가의 저장 책임

- 대상: `ForecastPublication`, `ForecastEvaluation`, `EvaluationResult`, `DemandStatisticsVersion`과 JDBC 저장소.
- 변경 전 → 후: 발행 정보·예측값·평가 상태·통계 버전 정보를 각각 저장한다. 입력 확정과 발행·예측·평가 대기행 생성은 같은 트랜잭션이다. 평가는 `PENDING`일 때만 확정한다.
- 이유: 같은 배치를 다시 계산해 과거 예측을 덮거나, 평가 재실행으로 당일 누계를 두 번 더하면 안 된다. 테스트에서는 발행 도중 예외, 경쟁 발행, 통계 생성 경쟁, 보정 반영 실패를 재현했다.
- 결과: 배치당 발행은 하나다. 예측 0행도 발행으로 기록하고, 좌석 범위 오류는 해당 차량의 예측만 제외한다. 평가 근거의 도착 정류장은 원 관측의 `stop_order`를 보관한다. 통계 버전 정보와 셀은 품질 잠금 아래 함께 저장한다. 입력 전체 복사나 특징 벡터 추가 보관은 하지 않는다.

## DDD 재검토 후 책임 분리 보완

- 대상: `TripQualityInvestigation`, `QualityObservationBatch`, `ObservationSource`, `GbisObservationSource`, `ObservationLoader`, `ForecastEvaluationWriter`, `ArrivalLabelResolver`.
- 변경 전 → 후: JDBC가 판단하던 품질 조사 시작·재시작 규칙을 도메인으로 옮겼다. 수집 응용 코드는 GBIS 타입 대신 업무 소유 조회 계약을 사용한다. 관측 저장소의 품질 연동과 평가 저장소의 입력 확정을 응용 서비스로 옮겼고, 평가에 사용할 관측의 시간 조건도 도메인에서 검사한다.
- 이유: 앞선 구현은 동작 검증을 마쳤지만 조사 재시작 정책을 바꿀 때 JDBC 코드를 수정해야 했다. GBIS 응답 구조가 바뀌면 응용 메서드의 입력 타입도 영향을 받았고, 수집·평가의 실행 순서 일부가 저장소 안에 있어 유스케이스를 따라가기 어려웠다.
- 결과: `start/restart`가 차량별 첫 이상을 근거로 새 조사를 만들거나 기존 조사를 유지한다. 완료 여부는 기존 DB의 `completed` 값을 복원해 판단한다. 단계 이름으로 과거 완료 여부를 추정하지 않는다. `GbisObservationSource`는 HTTP 종료 직후 수신 시각을 기록한 다음 정규화하며, 정규화 오류를 응답 미수신으로 바꾸지 않는다.
- 결과: `ObservationLoader`가 품질 잠금 → 배치 저장 → 새 저장 결과의 품질 조사 등록을 같은 트랜잭션에서 수행한다. `ForecastEvaluationWriter`는 노선 ID 순서의 품질 잠금 → 완료 가능 여부 확인 → 도착 배치 잠금·입력 확정 → 평가 CAS → 새 결과의 보정을 조율한다. 중복 요청은 사용하지 않는 도착 배치를 확정하거나 누계를 다시 반영하지 않는다. 계산 시각 이전과 같은 시각의 후보는 `ArrivalLabelResolver`가 판정 전에 제외한다.
- 구조 검증: 응용·도메인에서 GBIS 타입에 의존하거나 JPA·JDBC 저장 어댑터에서 공개 업무 API를 호출하면 ArchUnit이 실패한다. 저장 어댑터가 공개 인터페이스를 구현하는 것과 불변 결과 타입을 사용하는 것은 허용한다. DB 스키마와 HTTP 응답 계약은 유지했다.

## 업무 테스트의 소유 모듈 이관

- 대상: `worker-app/src/test`의 업무 테스트 85개와 리소스 1개, 각 업무 모듈의 테스트 구성, `business/*/build.gradle`, `RuntimeProcessSeparationTest`.
- 변경 전 → 후: 모듈을 나눈 뒤에도 업무 테스트는 worker-app에 남아 Worker 컨텍스트로만 돌았다. 이를 route-catalog·observations·forecasting·api-call-quota·gbis-client로 옮기고, worker-app에는 기동·스케줄·설정과 모듈 연결을 확인하는 테스트만 남겼다. 각 모듈은 자기 구성만으로 Testcontainers PostgreSQL 위에서 통합 테스트를 실행한다.
- 이유: 테스트가 worker-app에 있으면 모듈을 단독으로 빌드할 때 그 모듈의 업무 규칙이 검증되지 않는다. 모듈 경계가 생산 코드에만 있고 검증에는 없는 상태였다.

- 결과: api-call-quota의 테스트 구성이 자동구성을 손으로 나열하면서 Testcontainers 접속 정보를 등록하는 `ServiceConnectionAutoConfiguration`과 `TestcontainersPropertySourceAutoConfiguration`을 빠뜨려 `CallQuotaLedgerTest` 20개가 컨텍스트 적재에 실패했다. 두 자동구성을 넣어 32개 전부 통과한다. 이관이 들여온 불필요한 `project(':common')` 의존 3건과 과한 `spring-boot-flyway` 스코프도 정리했다.
- 검증: `./gradlew build` 통과, 1,356개 실패·오류·스킵 0. `build.gradle`이 소스 지문 입력이라 Worker digest가 바뀐다. 배포 훅 리허설을 다시 실행해 확인했다.

## 전수 감사 지적 반영

- 대상: 업무 모듈 네 개의 테스트 구성, `CallQuotaPolicy`, `ArrivalLabel`, `JdbcForecastEvaluationRepository`, `CollectionPhase`, `DemandStatisticsVersion`, forecasting `domain.model`·`domain.publication`, `ModelRoute`, `RouteStops`, `JdbcRouteVersionRepository`, `UpstreamRoute`, `JdbcRouteRegistry`, `CollectObservations`, `worker-app/build.gradle`, 주석 7줄.

- 이유: 모듈이 공개하지 않은 내부 빈을 테스트가 직접 조립하면 운영 배선이 바뀌어도 모듈 테스트가 통과한다. 한도가 API별인데 설정은 하나였고, 같은 도착 적격 규칙이 SQL 두 곳에 복사돼 한쪽만 고치면 조용히 어긋난다. 도메인 개념 패키지가 서로를 참조해 변경 영향 범위를 가늠하기 어려웠다.
- 결과: 전체 1,370개 테스트가 통과한다. DB 스키마와 HTTP 응답 계약은 바꾸지 않았다. `CallQuotaPolicy`는 값이 같은 현재 설정을 `sameForEveryApi`로 만들어 동작이 같다.
- 미반영: 정원 산출·편도 방향·이상 관측 판정이 Java와 SQL에 두 벌로 있는 문제, 노선정보 조회 실패의 재시도 간격, 상류 결측 행 처리는 모두 동작이나 정책이 바뀌므로 이번 리팩토링에 넣지 않았다. 관측 저장 포트와 노선 애그리거트의 재설계도 별도 범위다. 근거는 [구현 기록](../../docs/refactoring/ddd/implementation-progress.md)에 남겼다.

## DDD 관점 평가 후 구조 보완

- 대상: `api-app`의 `persistence` 패키지 3개, 새 `ApiPackageBoundaryTest`, `forecasting.domain.model` 11개 클래스, 설계안·용어집, `JdbcRouteVersionRepository` 주석.
- 변경 전 → 후: 조회 API를 경계 검사 안으로 넣고 패키지 어휘를 업무 모듈과 맞췄다. 학습 산출물의 수명주기를 `domain.deployment`로 갈라 "모델"의 두 뜻을 분리했다. 품질 view 7개를 공개 조회 계약으로 문서에 올리고 Flyway 파일의 소유 판단 기준을 적었다.
- 이유: 생산 코드 98개인 조회 API가 모든 계층·경계 규칙 밖에 있어, 지금 깨끗한 것이 규약이 아니라 우연이었다. 예보 규칙을 고치려는 사람이 배포 이력 11개까지 들어 있는 50개짜리 패키지에서 시작해야 했다. view 안의 업무 판정은 어느 문서에도 계약으로 적혀 있지 않았다.
- 결과: 전체 1,370개 테스트가 통과한다. 옮긴 파일 45개는 package·import 줄을 뺀 내용이 이전과 동일하다. 운영 코드에서 바뀐 것은 사실과 다르던 주석 한 곳뿐이다. DB 스키마와 HTTP 응답 계약은 바꾸지 않았다.
- 미반영: 편도 방향·정원 산출이 Java와 SQL에 두 벌인 문제와 `FORECAST_STALENESS`의 환경변수 조합은 고치면 계산 결과나 운영 동작이 달라져 이번 범위에 넣지 않았다.

## 검증 및 남은 범위

- 검증: Java 21·PostgreSQL 18 Testcontainers의 규칙·저장·동시성 테스트, 실제 API·Worker·정비 JAR 실행, DB 전환 ZIP 실행, Docker 배포 hook 리허설. 최종 명령·건수는 [구현 기록](../../docs/refactoring/ddd/implementation-progress.md)에서 확인한다.
- 미검증: 운영 규모의 전환 시간과 잠금 시간, 실제 백업/PITR 복원, 운영 환경의 승인·권한, 외부 학습 저장소의 직접 SQL 사용. 운영 DB에는 접속하지 않았다.
- 별도 범위: 프론트의 기존 응답 소비 불일치는 수정하지 않았다. PR #70의 HTTP 응답 계약은 유지한다. 기존 모델 선언의 정규화·시간·정원·통계 정책이 실제 계산 코드와 모두 일치하는지를 강제하는 검증은 이번에 추가하지 않았다. 계산식과 golden 결과는 유지했다.
