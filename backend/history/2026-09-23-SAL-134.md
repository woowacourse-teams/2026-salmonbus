## 실행 앱과 업무 모듈 분리

- 대상: `backend/settings.gradle`, `business/*`, `integrations/gbis-client`, `api-app`, `worker-app`, `maintenance-app`, `common`.
- 변경 전 → 후: Worker 안의 수집·계산·저장 코드를 업무 모듈로 옮겼다. Gradle 프로젝트는 9개이며 `business`와 `integrations`는 디렉터리다. Worker에는 기동·설정·스케줄을 두고 다른 모듈의 공개 API로 업무를 실행한다.
- 이유: 같은 품질 조사 규칙을 자동 작업과 수동 명령이 공유해야 한다. 정비 명령 때문에 Worker의 모델 적재나 스케줄이 기동되지 않도록 실행 구성을 분리했다.
- 결과: 도메인 규칙은 Spring·JPA·JDBC에 의존하지 않는다. 저장 어댑터는 도메인 객체와 별도 매핑을 사용한다. API 실행 클래스패스의 프로젝트 의존은 API와 common뿐이다. 정비 앱은 필요한 JDBC·트랜잭션·품질 기능만 등록한다.

- 대상: `ForecastPublication`, `ForecastEvaluation`, `EvaluationResult`, `DemandStatisticsVersion`과 JDBC 저장소.

## DDD 재검토 후 책임 분리 보완

- 대상: `TripQualityInvestigation`, `QualityObservationBatch`, `ObservationSource`, `GbisObservationSource`, `ObservationLoader`, `ForecastEvaluationWriter`, `ArrivalLabelResolver`.
- 변경 전 → 후: JDBC가 판단하던 품질 조사 시작 규칙을 도메인으로 옮겼다. 수집 응용 코드는 GBIS 타입 대신 업무 소유 조회 계약을 사용한다. 관측 저장소의 품질 연동을 응용 서비스로 옮겼고, 평가에 사용할 관측의 시간 조건도 도메인에서 검사한다.
- 이유: 앞선 구현은 동작 검증을 마쳤지만 조사 시작 정책을 바꿀 때 JDBC 코드를 수정해야 했다. GBIS 응답 구조가 바뀌면 응용 메서드의 입력 타입도 영향을 받았고, 수집·평가의 실행 순서 일부가 저장소 안에 있어 유스케이스를 따라가기 어려웠다.
- 결과: 조사 등록은 dev처럼 완료되지 않은 조사가 있는 차량만 건너뛰고 나머지는 새 조사로 덮어쓴다. 저장된 단계는 `SEARCH_START`면 시작점 탐색, 그 밖이면 순방향 재판정으로 읽는다. 응답 해석과 수신 시각 기록은 dev처럼 결과 저장(`collection_save_and_commit`) 안에서 한다.
- 결과: `ObservationLoader`가 관측 저장 → 이상 관측이 있을 때의 품질 잠금·조사 등록을 같은 트랜잭션에서 수행한다. `ForecastEvaluationWriter`는 저장할 때 노선 ID 순서로 잠근 뒤 평가 CAS → 새 결과의 보정을 조율한다. 중복 요청은 누계를 다시 반영하지 않는다. 계산 시각 이전과 같은 시각의 후보는 `ArrivalLabelResolver`가 판정 전에 제외한다.
- 구조 검증: 응용·도메인에서 GBIS 타입에 의존하거나 JPA·JDBC 저장 어댑터에서 공개 업무 API를 호출하면 ArchUnit이 실패한다. 저장 어댑터가 공개 인터페이스를 구현하는 것과 불변 결과 타입을 사용하는 것은 허용한다. DB 스키마와 HTTP 응답 계약은 유지했다.

## 업무 테스트의 소유 모듈 이관

- 대상: `worker-app/src/test`의 업무 테스트 85개와 리소스 1개, 각 업무 모듈의 테스트 구성, `business/*/build.gradle`, `RuntimeProcessSeparationTest`.
- 변경 전 → 후: 모듈을 나눈 뒤에도 업무 테스트는 worker-app에 남아 Worker 컨텍스트로만 돌았다. 이를 route-catalog·observations·forecasting·api-call-quota·gbis-client로 옮기고, worker-app에는 기동·스케줄·설정과 모듈 연결을 확인하는 테스트만 남겼다. 각 모듈은 자기 구성만으로 Testcontainers PostgreSQL 위에서 통합 테스트를 실행한다.
- 이유: 테스트가 worker-app에 있으면 모듈을 단독으로 빌드할 때 그 모듈의 업무 규칙이 검증되지 않는다. 모듈 경계가 생산 코드에만 있고 검증에는 없는 상태였다.
- 결과: 모듈별 테스트 수가 worker-app 929→50, forecasting 63→692, observations 28→203, route-catalog 5→58, api-call-quota 12→32, gbis-client 27→30으로 바뀌었다. 옮기기 전후의 테스트 메서드 이름을 전수 대조해 소실이 없음을 확인했다. 품질 훅이 있어야 성립하는 모듈 간 시나리오 2개는 observations 단독으로는 검사 대상이 비어 통과하므로, worker-app의 `ObservationQualityIntegrationTest`가 실제 배선에서 확인하도록 한 곳으로 모았다.
- 결과: api-call-quota의 테스트 구성이 자동구성을 손으로 나열하면서 Testcontainers 접속 정보를 등록하는 `ServiceConnectionAutoConfiguration`과 `TestcontainersPropertySourceAutoConfiguration`을 빠뜨려 `CallQuotaLedgerTest` 20개가 컨텍스트 적재에 실패했다. 두 자동구성을 넣어 32개 전부 통과한다. 이관이 들여온 불필요한 `project(':common')` 의존 3건과 과한 `spring-boot-flyway` 스코프도 정리했다.
- 검증: `./gradlew build` 통과, 1,356개 실패·오류·스킵 0. `build.gradle`이 소스 지문 입력이라 Worker digest가 바뀐다. 배포 훅 리허설을 다시 실행해 확인했다.

## 전수 감사 지적 반영

- 대상: 업무 모듈 네 개의 테스트 구성, `CallQuotaPolicy`, `ArrivalLabel`, `JdbcForecastEvaluationRepository`, `CollectionPhase`, `DemandStatisticsVersion`, forecasting `domain.model`·`domain.publication`, `ModelRoute`, `RouteStops`, `JdbcRouteVersionRepository`, `UpstreamRoute`, `JdbcRouteRegistry`, `CollectObservations`, `worker-app/build.gradle`, 주석 7줄.
- 변경 전 → 후: 모듈마다 제각각이던 통합 테스트 부팅 방식을 모듈 전용 애너테이션으로 맞추고, 테스트 구성이 빈 목록을 손으로 적는 대신 모듈이 공개한 Spring 구성을 가져오게 했다. 호출 한도를 API별로 모델링했다. 평가 확정 여부 판단을 도메인으로 올리고 도착 후보 적격 SQL 중복을 없앴다. 수집 단계 판정이 한국 시간대 상수를 쓰게 했다. 예보 도메인의 `model`과 `publication` 패키지 순환을 끊고, 포트와 구현에서 갈려 있던 노선 식별자 이름을 `sourceRouteId` 하나로 통일했다.
- 이유: 모듈이 공개하지 않은 내부 빈을 테스트가 직접 조립하면 운영 배선이 바뀌어도 모듈 테스트가 통과한다. 한도가 API별인데 설정은 하나였고, 같은 도착 적격 규칙이 SQL 두 곳에 복사돼 한쪽만 고치면 조용히 어긋난다. 도메인 개념 패키지가 서로를 참조해 변경 영향 범위를 가늠하기 어려웠다.
- 결과: 전체 1,374개 테스트가 통과한다. DB 스키마와 HTTP 응답 계약은 바꾸지 않았다. `CallQuotaPolicy`는 값이 같은 현재 설정을 `sameForEveryApi`로 만들어 동작이 같다.

## 관측 신선도 창의 소유와 불변식

- 결과: 값을 공유하지 않고 방향 있는 불변식(예보 창 ≥ 조회 창)을 드러내는 쪽을 골랐다. `common`에 업무 값을 넣지 않았고 api-app의 런타임 의존과 DB 스키마·HTTP 응답도 그대로다. 좁힌 설정이 계약 테스트에서 실패하는 것과 환경변수 주입이 기동을 멈추는 것을 각각 확인했다.
- 운영 영향: 배포 설정 어디에도 `FORECAST_STALENESS`가 없어 기존 배포는 영향받지 않는다. 앞으로 운영에서 이 값을 바꾸려면 코드 변경과 배포가 필요하다.

- 이유: 저장 어댑터가 유스케이스를 조율하고, 저장소 하나가 두 애그리거트를 쓰고, 같은 규칙의 짝을 서비스 네 곳이 손으로 맞추고 있었다. 예보의 하위 도메인이 서로를 참조해 순환이 있었다. 모듈마다 따로 든 저장 값은 빌드가 대조하지 않았다.
- 점검 반영: 조회 앱의 노선·모델 배포 저장소를 다른 조회 저장소처럼 읽기 전용 `Repository`로 좁혔다. 예보 대상 관측 판단(`isForecastEligible`)을 JDBC 조회에서 `TrajectoryObservation`으로 옮겼다. 품질 JDBC 어댑터를 다른 어댑터와 같은 `infrastructure.jdbc`에 두고, 통계 정정 요청 포트는 `DemandStatisticsRebuildRequestStore`로 불렀다. 관측·노선 JPA 매핑에 남은 `Collector*` 이름을 업무 이름으로 바꾸고, 관측 모듈 구성은 응용 서비스를 명시적 Import 한 경로로만 등록한다.
- 결과: SQL 문장은 그대로다. 같은 트랜잭션 안에서 순서가 바뀐 곳은 둘이다. 평가 대기 행을 예측마다 끼워 넣지 않고 예측을 모두 넣은 뒤 넣고, 이상 관측 등록에서 품질 버전을 정정 요청보다 먼저 올린다. 둘 다 같은 노선 잠금 안이라 결과가 같다. 예보 하위 도메인은 도메인·응용 계층을 함께 봐도 순환이 없고 ArchUnit이 이를 검사한다. worker 규칙은 구성 패키지와 테스트 위치, `@Repository` 어댑터까지 본다. 잔여석 미제공 사유·수집 결과·실패 사유·평가 상태·편도 상태는 각 모듈의 값이 스키마 CHECK와 같은지 테스트가 확인한다. 트랜잭션 필수 표시 통일, gbis-client의 api 분리, DB 시간 제한 방식 통일, 방향·배포 상태·캐시 시간처럼 스키마 기준이 없는 값의 대조는 하지 않았다. 조회 앱의 board·vehicle이 route의 읽기 매핑을 함께 쓰는 구조는 dev의 api-app 설계 그대로 뒀다.
