# SAL-134 DB 전환

이 실행기는 기존 V16 DB를 DDD 재설계의 저장 구조로 옮기는 일회성 도구다. API·Worker·정비 앱의 실행 JAR에는 포함하지 않는다. 정비 시간이 끝나고 결과 확인 및 복원 기간이 지나면 이 디렉터리와 전용 Gradle sourceSet을 함께 정리할 수 있다. 이미 적용한 서비스 Flyway SQL은 그대로 보존한다.

## 실행 전 확인

1. API와 Worker, 품질 정비 CLI 및 외부 학습·관리 작업의 DB 쓰기를 중지한다. 스케줄을 껐더라도 이미 실행 중인 작업이 모두 종료됐는지 확인한다.
2. **쓰기 중지 이후 시점**의 백업 또는 PITR 복원 지점을 확보한다. DB 복원과 구 버전 JAR 복원을 함께 할 수 있어야 한다.
3. Java 21과 전환 ZIP을 준비한다. ZIP을 풀면 이 문서와 `run.sh`, `lib/`가 같은 디렉터리에 있어야 한다.
4. 설정 예시를 작업 디렉터리 밖에 복사하고 `chmod 600`을 적용한다. DB 비밀번호는 `jdbc.password-env`에 지정한 환경 변수로 공급한다. URL에 비밀번호를 넣지 않는다.

`--writers-stopped`와 `--backup-id`는 운영자가 위 조건을 확인했다는 기록이다. 실행기가 다른 서버의 프로세스를 종료하거나 실제 백업의 복원 가능성을 검사하지는 않는다. `inspect` 결과의 DB 이름·주소와 운영 대상을 대조한다. `jdbc.expected-database`가 실제 DB 이름과 다르면 연결 직후 중단한다.

## 명령 순서

아래의 `/secure/sal134.properties`와 `post-stop-backup-20260923`은 실제 설정 경로와 복원 지점 식별자로 바꾼다. 한 전환에서는 같은 백업 식별자를 사용해야 한다.

```sh
bash run.sh inspect --config /secure/sal134.properties

bash run.sh prepare --config /secure/sal134.properties \
  --writers-stopped --backup-id post-stop-backup-20260923

bash run.sh backfill --config /secure/sal134.properties \
  --writers-stopped --backup-id post-stop-backup-20260923

bash run.sh verify --config /secure/sal134.properties \
  --writers-stopped --backup-id post-stop-backup-20260923

bash run.sh finalize --config /secure/sal134.properties \
  --writers-stopped --backup-id post-stop-backup-20260923
```

| 명령 | 처리 |
|---|---|
| `inspect` | DB 대상, Flyway 버전, 원본 건수, 전환 진행 상태 출력 |
| `prepare` | Flyway를 V17까지만 실행하고 원본 전체 SHA-256·건수·마지막 PK와 백업 식별 저장 |
| `backfill` | 기본 1,000개 PK 단위로 데이터를 복사하고 같은 트랜잭션에서 진행 위치 저장 |
| `verify` | 원본과 대상의 모든 값 및 조회 결과를 대조하고 검증 완료 기록 |
| `finalize` | 검증을 다시 수행한 뒤 Flyway V18 적용, 품질·학습 조회와 원 관측을 다시 대조 |

동시에 여러 실행기를 기동하면 PostgreSQL advisory lock을 획득한 하나만 진행한다. Flyway SQL에 대응하는 DDL 권한과 대상 자료를 읽고 쓸 수 있는 권한이 필요하다. 잠금 대기는 5초, SQL 문장 제한은 10분이다. SQL timeout이 나면 진행 기록을 확인하고 데이터 분포와 실행 계획을 점검한다.

## 중단과 재개

`backfill`의 데이터 변경과 진행 위치는 함께 커밋한다. 실패한 묶음은 모두 롤백된다. 원인을 해결한 뒤 같은 명령을 실행하면 마지막 커밋 다음부터 이어진다. `--chunk-size`는 1~10,000이며, 재개 시 바꿀 수 있다. `--max-chunks 3`은 세 묶음만 처리한 뒤 정상 종료하므로 리허설에서 중단·재개를 확인할 때 사용한다. 기본값 0은 제한 없이 완료할 때까지 처리한다.

`prepare`를 다시 실행해도 기존 기준점과 진행 위치를 덮어쓰지 않는다. 백업 식별과 현재 원본이 기존 기록에 일치해야 한다. 다른 백업이나 변경된 원본으로 작업하려면 검증 기록을 임의로 고치지 말고 기존 실행을 중단한 뒤 복원 절차로 돌아간다.

V18 적용 직후 연결이 끊긴 경우 `inspect`로 버전을 확인한다. `finalize`는 V18에서도 실행할 수 있으며, 이미 적용한 SQL을 반복하지 않고 품질·학습 조회와 원 관측을 대조한다. **이 대조가 끝나기 전에는 새 쓰기를 재개하지 않는다.**

## 자료를 옮기는 기준

- 기존 배치·관측·예측의 식별자와 원값은 보존한다. 좌석 수가 70을 넘는 과거 관측도 수정하거나 삭제하지 않는다.
- 한 배치의 예측들이 사용한 모델·통계 버전·품질 버전·생성 시각이 섞여 있으면 중단한다. 임의로 최소값이나 현재 모델을 고르지 않는다.
- 예측이 없는 과거 완료 배치는 모델을 복원할 수 없으므로 `LEGACY_UNKNOWN` 발행으로 기록한다.
- 발행에 사용한 배치, 기존 평가의 도착 관측 배치, 편도 판정과 품질 조사 커서가 참조한 관측 배치에는 입력 확정 시각을 기록한다. 재수집이 과거 근거를 지우는 것을 막는다. 발행 시각, 가장 이른 평가 시각, 가장 이른 품질 판정·조사 시각 순서로 남아 있는 기록을 사용하며, 참조한 적 없는 배치를 일괄 확정하지 않는다. 품질 자료의 관측 ID가 원 관측에 없으면 해당 ID를 알리고 중단한다.
- 평가의 상태와 도착 근거 값을 복사한다. 도착 시각은 도착 관측이 속한 배치의 `response_received_at`을 사용한다.
- 실재하는 편도에 연결된 관측만 `observation_trip_assignment`로 복사한다. 과거 `vehicle_trip_key`의 원값은 유지한다.
- 통계 셀은 변경하지 않고 같은 계산 버전·revision의 메타데이터를 묶는다. 과거 입력 체크포인트는 추정하지 않는다.
- 기존 모델·통계 학습 제외 기록을 새 영구 테이블로 복사한다. historical 감사·seed 테이블과 적용 이력은 삭제하지 않는다.

## 검증과 전환 실패

원본의 PK 순서로 각 행의 JSON을 읽어 SHA-256을 계산한다. JDBC fetch size를 사용하므로 전체 관측을 Java 메모리에 적재하지 않는다. 건수와 마지막 PK뿐 아니라 값 변경도 확인한다. 대상 자료는 누락·추가 행과 컬럼 값을 양방향 비교한다. 충돌한 PK를 무시하고 복사를 재개한 경우에도 최종 값이 다르면 검증에 실패한다.

검증 트랜잭션은 원본·대상 테이블의 잠금을 모두 획득한 다음 자료를 읽고, 검증 기록을 커밋할 때까지 잠금을 유지한다. 따라서 검증 중에 다른 쓰기가 끼어들어 오래된 기준으로 승인되는 일을 막는다. 이 동안 서비스 조회도 대기하므로 앱을 중지한 정비 시간에만 실행한다.

`verify`는 최종 V18 SQL을 트랜잭션의 savepoint 안에서 미리 실행한다. 이 상태에서 원 관측과 기존 품질·학습 view 전체 결과를 대조한 뒤 savepoint로 롤백한다. 따라서 검증 성공 후에도 실제 스키마는 V17이다. 실제 적용은 `finalize`의 Flyway 실행이 담당한다. 기존에 없던 historical 학습 view는 전후 비교 대상에서 제외하고 새 서비스 정의로 설치한다.

검증 이후 원본이나 대상 테이블에 쓰기가 발생하면 DB 트리거가 검증 완료를 취소한다. V18은 관련 테이블 잠금과 검증 완료 기록을 확인한 뒤에만 기존 컬럼을 제거한다. 비어 있는 새 DB는 데이터 전환 없이 V18까지 설치할 수 있다.

전환이 끝나면 API와 Worker를 새 버전으로 기동하되 자동 쓰기는 아직 중지한 상태로 둔다. API 응답, 모델 적재, 배포 식별 정보를 확인하고 원래 수집·예보 설정을 복원한다. **새 쓰기 재개 전 실패는 백업 DB와 구 JAR를 함께 복원한다. 새 쓰기 재개 뒤 구 JAR만 되돌리지 않는다.**

운영 DB 접속이나 전환은 CI에서 수행하지 않는다. PostgreSQL 18 Testcontainers의 기존 자료·빈 DB·중단 후 재개·값 변경·전환 실패 시나리오로 실행기를 검증한다.
