# 에이전트 규칙

이 폴더에서 일하는 코딩 에이전트(Claude Code, Codex)가 따르는 규칙입니다.

## 실패한 E2E를 고칠 때

healer 에이전트(Claude Code의 `playwright-test-healer`, Codex의 `playwright_test_healer`)와, 실패한 E2E를 고치는 모든 세션에 적용합니다. healer 정의의 workflow와 부딪히면 이 규칙을 따릅니다.

사람이 대화에서 의도한 변경이라고 확인하고 테스트의 기대값을 고쳐 달라고 하면, 그 세션은 5번부터 9번의 근거 확인을 건너뛰고 그 기대값을 고칩니다. 1번, 2번, 4번, 10번부터 13번은 그대로 지킵니다. 세션이 스스로 의도한 변경이라고 판단해 healer의 `제품 버그 의심`이나 `판단 못 함`을 뒤집지는 않습니다(3번).

### 고칠 수 있는 파일

1. `e2e/` 아래 파일만 고칩니다. `src/`, `playwright.config.ts`, `package.json`, 리포 루트의 `contract/`는 고치지 않습니다.
2. git 이력을 바꾸지 않습니다(commit, push, merge, rebase, reset, stash). 고친 테스트는 사람이 리뷰하고 커밋합니다.
3. healer가 `제품 버그 의심`이나 `판단 못 함`으로 보고하면, healer를 부른 세션도 테스트를 고치지 않고 그 보고를 사람에게 전합니다.

### 먼저 재현하기

4. 실패를 로컬에서 먼저 재현합니다.
   - Playwright MCP의 `test_run` 도구로 실패한 테스트만 돌립니다. `locations`에 실패한 파일과 줄(예: `e2e/board-map.spec.ts:645`)을, `projects`에 실패한 프로젝트(예: `chromium`)를 넣습니다.
   - 셸에서 `npx playwright test`나 `pnpm test:e2e`로 돌리지 않습니다. 셸 명령은 MCP 서버와 다른 설정을 쓸 수 있고, 기본 설정은 4173 포트를 써서 다른 서버와 겹칠 수 있습니다.
   - `test_run`을 쓸 수 없으면(도구가 없거나, 거부되거나, 응답이 없으면) 다른 방법으로 돌리지 않습니다. 테스트를 고치지 않고 `판단 못 함`으로 보고하고, 쓸 수 없었던 이유를 적습니다.
   - CI 실패 기록(trace, error-context, 스크린샷)이 주어지면 실패한 테스트마다 끝까지 읽습니다. 파일은 하나씩 열고, 긴 파일은 나눠서 끝까지 읽습니다. Claude Code에서는 Read 도구로 읽고, 셸 반복문이나 `cat`으로 묶어 읽지 않습니다. Codex처럼 Read 도구가 없으면 한 파일씩 읽는 명령으로 읽습니다. Read로 열 수 없는 기록(예: `trace.zip`)이나 읽지 못한 기록은 보고에 그 파일과 이유를 적습니다.
   - 로컬에서 재현되지 않는 실패도 테스트를 고치지 않고 `판단 못 함`으로 보고합니다. 보고에는 재현되지 않았다는 사실과 돌린 도구와 인자, 그 결과를 적고, CI 실패 기록(trace, error-context, 스크린샷)이 있으면 거기서 본 것을 적습니다.
   - 5번부터 9번은 로컬에서 재현된 실패에만 적용합니다.

### 기대값을 바꾸기 전에

5. 실패한 기대값(문구, 숫자, 상태)을 바꾸기 전에, 이 브랜치가 그 값을 직접 바꿨는지 확인합니다.

   ```sh
   git diff --merge-base origin/dev -S'<테스트가 기대하던 문구>' -- src ':!*.test.ts' ':!*.test.tsx' ':!*.typeTest.ts' ':!*.stories.tsx' ':!*.mock.ts'
   git status --short
   ```

   - 첫 명령은 브랜치의 커밋과 아직 커밋하지 않은 변경을 같이 봅니다. `git log -S`는 커밋한 변경만 찾으므로 쓰지 않습니다.
   - 단위 테스트, 타입 테스트, 스토리, 목 파일은 검색에서 뺍니다. 이 파일들은 제품 동작을 바꿀 때 같이 맞춰지는 경우가 많아서, 문구를 바꿨다는 근거가 되지 못합니다.
   - `git status --short`에서 `??`로 나온 새 파일은 첫 명령에 나오지 않습니다. 그 파일에서 문구를 따로 찾습니다(위에서 뺀 종류의 파일은 빼고).

6. 테스트를 고쳐도 되는 경우는 하나입니다. 제품 코드(5번에서 뺀 파일이 아닌 파일)의 diff `-` 줄에 테스트가 기대하던 리터럴이 있고, `+` 줄에 지금 화면에 보이는 값이 있을 때입니다. 단위 테스트의 기대값만 그렇게 바뀌었으면 이 경우가 아닙니다.
7. 로컬에서 재현된 실패를 6번으로 고칠 수 없으면, 테스트를 고치지 않고 가진 근거에 따라 보고합니다.
   - 이 브랜치의 diff(`git diff --merge-base origin/dev`, `src/` 밖 포함)에서 어긋난 값을 만드는 코드가 바뀐 줄을 찾았지만, 그 줄이 기대하던 리터럴을 직접 바꾼 것은 아닐 때(예: 계산, 조건, 데이터 변환이 바뀜): `제품 버그 의심`으로 보고하고, 그 줄을 원인으로 적습니다.
   - 어긋난 값을 만드는 코드가 바뀐 줄을 이 브랜치의 diff에서 찾지 못했을 때: 값의 종류(예: 계산된 좌표나 크기, 목 데이터에서 온 문구나 상태)와 상관없이 `판단 못 함`으로 보고합니다. 근거가 되는 줄이 없으면 제품 코드 문제인지 테스트 문제(기다림, 정밀도, 목 데이터)인지 가를 수 없기 때문입니다. 보고에는 어긋난 값(기대와 실제), 그 값을 만드는 코드 위치(찾을 수 있으면), CI 실패 기록에서 본 것을 적습니다.
   - 어느 경우든 이 브랜치에서 단위 테스트의 기대값도 지금 화면 값으로 바뀌었으면, 보고에 그 파일과 줄을 적습니다. 사람이 의도한 변경인지 가르는 데 씁니다.
8. git 명령을 돌리지 못하면(권한이 막히거나 다른 지시가 git을 금지하면) 테스트를 고치지 않고 `판단 못 함`으로 보고합니다.
9. 의도한 변경이어도 리터럴로 찾을 수 없으면(템플릿 문자열로 만든 문구, 계산 방식을 바꾼 숫자) healer는 테스트를 고치지 않고 7번에 따라 보고하고, 사람이 테스트를 고칩니다. 잘못 고친 테스트는 버그를 숨기고, 잘못된 보고는 사람이 한 번 확인하면 끝나기 때문입니다.

### 하지 않는 수정

10. `test.fixme`, `test.skip`, `test.fail`, `test.slow`를 더하지 않습니다.
11. 기대값을 정규식으로 넓혀서 통과시키지 않습니다. 목 데이터로 정해지는 값은 정확한 값으로 기대합니다.
12. 기다림을 늘리지 않습니다. `waitForTimeout`을 넣거나, timeout 값을 늘리거나, `toPass`나 `expect.poll`로 감싸거나, retries를 늘리지 않습니다. 시간 초과로 실패하면 화면이 그 상태에 머문 이유(콘솔 오류, 네트워크 요청, 스냅숏)를 근거로 보고합니다.
13. 목 데이터(`e2e/fixtures/`)의 응답 모양은 `contract/` 명세를 따릅니다.

### 보고 형식

14. 마지막에 아래 형식으로 보고합니다.

    ```text
    판정: 테스트 수정 | 제품 버그 의심 | 판단 못 함
    실패한 테스트:
    로컬 재현: 재현됨 | 재현 안 됨 | 돌리지 못함 (돌린 도구와 인자, 결과 또는 돌리지 못한 이유)
    CI 실패 기록에서 본 것: (기록이 있을 때, 읽지 못한 기록과 이유 포함)
    기대값과 실제값:
    돌린 git 명령과 결과:
    바꾼 파일과 줄: (없으면 없음)
    원인으로 보이는 파일과 줄: (제품 버그 의심일 때)
    값을 만드는 코드 위치: (판단 못 함일 때, 찾을 수 있으면)
    같이 바뀐 단위 테스트: (단위 테스트 기대값도 지금 화면 값으로 바뀌었을 때 파일과 줄)
    ```

    실패한 테스트가 여럿이고 판정이 서로 다르면, 테스트마다 이 형식으로 따로 보고합니다.
