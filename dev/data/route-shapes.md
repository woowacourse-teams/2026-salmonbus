# dev 노선 도로형상 저장본

`route-shapes.json`은 `routes.json` 8노선과 `catalog-routes.json` 33노선의 지도 API 재생에 쓰는 공개 정적 도로형상이다. 정류장 좌표를 직선으로 이어 만들거나 도로 탐색 서비스로 추정하지 않았다. 41노선, 노선별 정류장 방문 3,215건에 대응하는 형상점 35,542개를 포함한다. 방문 건수는 고유 물리 정류장 수가 아니다.

자료는 두 출처를 구별해 보존한다.

| 구분 | 노선 수 | 형상점 수 | 수집 시점과 처리 |
| --- | ---: | ---: | --- |
| `GBIS_RETAINED_STATIC_CAPTURE` | 8 | 7,063 | 2026-10-14 09:57:39 UTC 저장본의 `shape`를 원래 `lineSeq` 순서와 좌표 그대로 사용 |
| `GBIS_PUBLIC_WEB_STATIC` | 33 | 28,479 | 2026-10-15 UTC 공식 공개 지도에서 정적 형상만 GET으로 수집, 공식 지도와 같은 점 선택 후 좌표계 변환 |

기존 8노선은 `backend/api-app/src/test/resources/gbis/route-geometry-eight-20261014.json`의 공개 정적 자료다. 해당 파일의 캡처 시각과 SHA-256을 각 노선의 `source`에 기록한다. 원 저장본에 상세 요청 URL이 없어 URL을 추정해 덧붙이지 않았다. 기존 8노선의 좌표·점 개수는 변경하지 않았다.

추가 33노선은 [경기버스정보 공개 지도](https://www.gbis.go.kr/gbis2014/schBus.action)가 사용하는 다음 정적 조회에서 얻었다. 요청에는 인증키, 쿠키, 계정 정보가 없다. 실시간 버스 위치나 차량 식별정보를 조회하는 다른 명령은 사용하지 않았다.

```text
GET https://www.gbis.go.kr/gbis2014/schBusAPI.action?cmd=searchMapLineJson&routeId={routeId}
```

응답은 `result.gg.upLine`과 `result.gg.downLine`에 각 방향의 지도 형상을 제공한다. [공식 지도 스크립트](https://www.gbis.go.kr/gbis2014/js/map/searchTotal_2025.js?ver=1.17)의 수집 시점 구현을 따라 처리했다.

- 38–41, 129행은 지도 좌표계 `EPSG:3857`과 경위도 `EPSG:4326`를 명시한다. 반지름 6,378,137m의 표준 역 메르카토르 식으로 경위도로 변환하고 소수점 9자리까지 저장한다. 이 변환은 좌표계 변환이며 새 경로 계산이 아니다.
- `getRouteLineSuccess`의 2999–3056행은 양 방향 모두 `type != '2'`인 점만 표시한다. 저장본도 이 필터를 적용한다. `type=2`의 상세 의미는 공개 스크립트에서 확인되지 않아 임의로 이름 붙이지 않았다.
- 각 방향 응답의 배열 순서와 `seq` 증가 순서를 확인하고 상행 뒤 하행을 보존했다. 33노선 모두 상행 마지막 점과 하행 첫 점이 동일했다. 다른 경로를 끼워 넣거나 점을 보간하지 않았다.

각 노선의 `source`에는 실제 GET URL, UTC 수집 시각, 원본 응답의 SHA-256·바이트 수, 좌표계, 변환 방식, 방향별 원본·보존·제외 점 개수를 기록한다. 원본 응답과 수집 메타데이터는 무시되는 로컬 작업 경로에 보존하며, 이 저장본에는 정적 형상과 출처만 포함한다.

33개 원본과 시각·해시 메타데이터의 로컬 보존 위치는 `.work/sal206-geometry/shape-data/public-static/`이다. 공식 지도 스크립트 원본은 `.work/sal206-geometry/shape-data/searchTotal_2025.js`이며 SHA-256은 `483c04b8860c3f35ce6beafa3ada45249d5bc2f9e82aaadc16d7c79d034637c1`이다. URL·크기·근거 행 번호는 `.work/sal206-geometry/shape-data/source-evidence.json`, 노선별 거리 점검 결과는 같은 경로의 `validation.json`에 보존한다. 이 작업 경로는 버전 관리 대상이 아니다.

`referenceDigest`는 같은 저장소에서 배포하는 해당 노선 fixture의 `contentDigest`에 연결한다. GBIS가 이 digest를 발급하거나 같은 upstream 판본임을 보증하는 것은 아니다. API의 노선 판본을 선택할 때 이 연결을 검증해야 하며, 카탈로그 변경에 과거 형상을 무조건 재사용해서는 안 된다. 새 노선을 추가할 때도 동일한 원본 형상과 digest 연결이 필요하다.

확보한 41노선에서 모든 좌표는 유한한 경위도 범위에 있고 형상마다 서로 다른 점이 2개 이상이다. 정류장 3,215건 각각에서 원본 형상 선분까지의 최단 거리를 점검했으며 모두 100m 이내였다. 최대값은 1007·1009의 96.391m다. 이는 자료 대응에 대한 점검이며 실측 위치 정확도 보증은 아니다. 방향별 방문 순서에 따른 `paths` 분리와 HTTP 응답은 API 통합 검증으로 별도 확인한다.

원본 연속점 사이 최대 거리는 2,033.097m다. 긴 구간과 같은 좌표가 연속되는 경우도 원본대로 유지했다. 공개 지도용 형상은 측량 정밀도·최신 도로 상태·법적 주행 가능성을 보장하지 않는다. 이 저장본은 dev 재생 자료이며, 인증 API를 통한 운영 수집·지속적인 실시간 갱신을 대신하지 않는다.

재생성은 Python 표준 라이브러리만 사용한다. 이미 저장한 원본에서 재생성할 때는 네트워크 요청이 없다.

```sh
python3 dev/data/tools/build_route_shapes.py \
  --raw-dir .work/sal206-geometry/shape-data/public-static \
  --report .work/sal206-geometry/shape-data/validation.json
```

새로운 공식 공개 정적 원본을 확보해야 할 때만 `--capture-missing`을 추가한다. 기존 8노선 자료는 계속 재사용하며, 나머지 노선별로 없는 원본만 한 번씩 GET한다. 동시에 실행하는 요청은 최대 2개다. 이미 있는 원본의 해시가 맞지 않거나 파일 쌍이 불완전하면 자동으로 다시 조회하거나 덮어쓰지 않고 실패한다. 출력 파일은 모든 필요한 원본을 읽은 뒤 생성한다. 원본 시각이 다른 자료로 갱신할 때는 새 로컬 원본 디렉터리를 지정하고 결과와 API 동작을 함께 검증한다.

스크립트는 중복 노선 ID, reference digest 형식, 좌표 범위·0좌표 거절, 점 순번·개수, 원본 응답 해시를 검증한다. 보고서에는 노선별 정류장과 형상 사이 최대 거리·100m 초과 방문, 연속점 최대 거리·중복, 공개 지도 상하행 접점 간격을 남긴다. 100m 초과 방문이 있으면 종료 코드 2로 알리므로 해당 자료를 검토한 뒤 API 지원 여부를 판단한다.
