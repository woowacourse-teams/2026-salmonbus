# 공유 dev worker 부하 기준

공유 dev에서는 실제 GBIS 대신 WireMock을 사용하면서 worker의 수집 규모와 처리 주기를
운영에 가깝게 맞춘다. 사용자 API·채팅 부하 생성은 포함하지 않는다.

## 비교 기준

2026-10-15 저녁 운영 worker의 실행 설정과 공개 차량 API의 방향별 차량 수를 확인했다.
운영 실행 버전은 `52202b7`이었다. 브랜치의 기본 설정만으로 실제 운영 설정을 추정하지 않는다.
RDS 상태·지표와 DB 통계는 읽기 전용으로 확인했고, 차량 식별자·위치·원본 행은 복사하지 않았다.

이 관측을 바탕으로 배포할 설정은 다음과 같다.

- `worker.yml`의 고정 수집 간격을 제거해 운영과 같은 시간대별 수집 주기를 사용한다.
  예보와 정산 간격도 확인한 운영 설정에 맞춘다.
- `replay.json`에 노선별 상·하행 차량 규모를 둔다. 이 파일은 공유 dev 이미지에만 포함한다.
  개인 로컬의 `dev/scenarios/replay.json`은 계속 사용한다.
- 재생 차량의 종점 대기 때문에 설정한 규모가 크게 줄지 않도록 공유 dev의 대기 시간을
  짧게 둔다. 차량 이동은 기존 합성 재생이며 실제 차량 경로·속도를 복제하지 않는다.
- `routeVehicles`의 키는 재생 노선 번호이고 값은 `up`, `down`이다. 방향별 차량 수는
  0부터 64까지 허용한다. 알 수 없는 노선이나 범위 밖 값은 기동 시 거부한다.
  지정하지 않은 노선과 기존 로컬 시나리오는 이전 기본 동작을 유지한다.

노선별 차량 규모는 저녁 관측 표본을 반영한 고정 설정이다. 운영 차량 수를 실시간으로
따라가거나 하루 전체의 차량 수 변화를 재현하지는 않는다. 설정을 갱신할 때 관측 시간대와
차량 수를 다시 확인하며, 실제 GBIS 키를 dev에 넣지 않는다.

## 배포 후 확인

SAL-200의 자동 배포 경로로 basis·WireMock 이미지·worker 설정을 함께 반영한다.
이미 있는 dev RDS 데이터와 계정은 보존하며 데이터 이전이나 초기화를 반복하지 않는다.

배포·복원·백업의 영향이 없는 안정된 시간 구간에서 운영과 dev를 비교한다. 먼저 수집 성공,
활성 차량, 관측·예보·정산의 처리량을 확인하고 RDS의 읽기·쓰기 IOPS와 처리량, 연결 수,
CPU를 함께 본다. DB 누적 카운터는 동일한 통계 reset 기준에서 시간 차이로 나눠 비교한다.

운영의 누적 데이터·모델·사용자 요청량·캐시 상태는 dev와 다르다. worker 주기와 차량 수가
같아도 물리 I/O나 CPU가 같아진다고 보장하지 않는다. 비교 결과가 다르면 해당 작업 종류와
데이터 차이를 확인한 뒤 조정한다. 운영 원본 데이터를 복사하거나 무관한 쿼리를 반복해
지표를 맞추지 않는다.

크레딧 잔량은 부하 목표로 삼지 않는다. `EBSByteBalance%`는 남은 처리량 크레딧이며
DB 파일 외 root 볼륨의 활동도 포함한다. 지표 의미는
[AWS RDS 지표 문서](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-metrics.html)를 따른다.

문제가 생기면 이전의 dev worker 설정과 재생 이미지가 포함된 basis로 복구한다.
배포 설정 원복이 이미 저장한 데이터까지 되돌리는 것은 아니다.
