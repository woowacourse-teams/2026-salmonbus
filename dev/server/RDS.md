# 공유 dev PostgreSQL을 dev RDS로 전환

기본 구성은 EC2의 로컬 PostgreSQL이다. RDS는 AWS에서 확인한 별도 dev 인스턴스에만
연결한다. MongoDB와 GBIS WireMock은 기존 dev 구성을 유지한다.

## 연결 검증

- 목적지 식별자는 `salmonbus-dev-db`, 리전은 서울이다. 운영 DB를 목적지로 사용하지 않는다.
- DB가 Available이고 dev EC2와 같은 VPC에 있으며, 비공개이고 지정된 `project-db`를
  사용하는지 확인한다. 기존 공유 보안 그룹과 서브넷 그룹 자체는 수정하지 않는다.
- dev EC2에서 RDS CA로 인증서와 호스트명을 검증하는 `verify-full` 연결을 확인한다.
- 마스터 비밀번호는 보호된 파일로만 전달한다. 명령 인자, 로그, Git에 넣지 않는다.
- 앱에는 기존 dev 전용 계정을 사용한다. 마스터 계정을 API·worker에 설정하지 않는다.

## 기동 설정

서버의 `/etc/salmonbus-dev/database-target.json`은 root 소유, 권한 0600으로 둔다.
환경은 dev, 식별자는 위 dev DB, ARN은 dev EC2 marker와 같은 계정/리전/DB여야 한다.
`endpoint`와 `port`는 AWS에서 조회한 값이며, `certificateSha256`은 함께 설치한
`rds-ca.pem`의 SHA256이다. CA 파일은 root 소유, 쓰기 권한을 제한하고 앱이 읽을 수 있게 한다.
실제 endpoint·ARN·인증정보는 저장소에 기록하지 않는다.

기동 검증은 이 파일이 없으면 기존 로컬 DB만 허용한다. 파일이 있으면 검증된 dev RDS의
동일 URL을 API와 worker 모두 사용해야 하며, TLS 검증을 끌 수 없다. 두 앱의 DB 사용자와
비밀번호는 기존 dev PostgreSQL 계정과 일치해야 한다. systemd의 DB 주소 인자 강제는
제거하고, 검증된 환경 파일을 사용한다. GBIS의 loopback 고정과 실제 키 거부는 유지한다.

basis 설정 교체 시 대상 파일과 CA를 보존한다. RDS를 지원하지 않는 옛 도구로 basis를
되돌리려면 먼저 아래의 DB 원복 절차를 완료해야 한다.

## 데이터 이전과 전환 순서

1. 변경 중인 배포와 공유 dev 사용자를 확인하고 전환 시간을 정한다. 이번 작업은 사용자
   API/채팅 요청을 발생시키는 부하 시험을 포함하지 않는다.
2. 새 RDS에 기존 앱 DB·계정·데이터가 없는지 확인한다. 이미 있으면 덮어쓰지 않는다.
3. 새 도구와 unit 변경은 기존 승인 절차와 dev CodePipeline 경로로 반영한다. RDS 설정을
   켜기 전에 로컬 DB 설정으로 새 기동 검증이 통과하는지 확인한다.
4. dev API와 worker를 정지하고 기존 설정·unit·선택된 basis/app 버전을 보호된 경로에
   백업한다. 기존 PostgreSQL 컨테이너·데이터 디렉터리는 보존한다.
5. 기존 DB의 최종 일관된 pg_dump 백업을 만든다. 버전, 파일 크기, 체크섬, Flyway 이력,
   테이블별 정확한 행 수와 sequence 상태를 기록한다. 비밀이나 행 원문은 보고하지 않는다.
6. dev RDS에 앱 전용 계정과 DB를 준비하고, 백업의 소유권/ACL을 그대로 복원하지 않도록
   주의해 앱 소유로 복원한다. 복원 후 이력·행 수·sequence를 대조하고 권한을 확인한다.
7. 두 앱의 DB 설정과 검증용 대상 파일/CA를 함께 적용한다. 기동 검증을 통과한 뒤 API부터
   시작해 Flyway·health를 확인하고 worker를 시작한다. 재시작 과정에서 부분 설정을 읽지
   않도록 두 앱이 정지된 동안 교체한다.
8. 실제 DB 연결 대상, TLS, worker 수집/저장, REST 응답을 확인한다. 기존 DB 데이터는
   검증 직후 삭제하거나 자동 재초기화하지 않는다.

## 원복

실패 시 dev 앱을 정지하고 RDS 설정/대상 파일을 별도로 보존한 뒤 백업한 로컬 DB 설정과
그에 맞는 unit·도구·basis/app 조합을 복구한다. 기존 PostgreSQL의 상태를 확인한 뒤
API·worker를 재기동한다. RDS에서 새로 쓴 데이터도 삭제하지 않으며, 원복 후 자동으로
로컬에 합쳐진다고 가정하지 않는다. 운영 DB에는 어떤 원복 작업도 적용하지 않는다.

## worker 부하 맞추기

DB 전환이 안정된 후 운영의 실제 수집 스케줄·수집 노선·시간대별 차량 규모를 기준으로
WireMock 재생을 조정한다. 공개 노선 카탈로그 수와 수집 노선 수는 구별한다. 현재 재생은
방향당 차량 수 상한이 6대이므로 설정만 올려 해결할 수 없으며 별도 구현·검증이 필요하다.
동일 RDS 사양만으로 운영과 같은 성능·부하를 재현했다고 판단하지 않는다.
